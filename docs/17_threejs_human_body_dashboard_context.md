## 1. 원 대화의 요청과 진행

원 대화는 다음 순서로 진행되었다.

1. `three.js human body damage dashboard` 아이디어를 요청했다.
2. 신체 부위별 Mesh와 손상 데이터를 연결하는 구조를 제안했다.
3. 외부 인체 모델 없이 실행 가능한 최소 샘플을 요청했다.
4. Three.js 기본 Geometry로 구성한 절차형 인체 샘플을 제안했다.
5. 데모보다 완성도가 높은 프로토타입을 요청했다.
6. 3D 상호작용, 여러 보기 모드, 바이탈, 타임라인과 상세 패널을 포함하는 확장안을 제안했다.
7. 최종 단계로 실제 해부학 GLB 모델과 AI 추론을 연결하는 구조를 제시했다.

원 대화는 의료 제품 요구사항을 확정한 과정이 아니라 시각화 가능성과 프로토타입 범위를 탐색한 과정이다.

## 2. 원 대화에서 긍정적으로 선택한 방향

### 2.1 Three.js 기반 3D 인체 뷰어

- 웹에서 실행되는 Three.js 장면을 사용한다.
- 사용자는 인체를 회전하고 확대·축소할 수 있다.
- 신체 부위를 클릭하거나 hover하여 해당 영역을 선택한다.
- 선택 결과를 우측 상세 패널과 연결한다.

### 2.2 신체 부위 Mesh와 데이터의 명시적 매핑

실제 GLB/GLTF 모델을 사용할 경우 Blender 등 모델 제작 단계에서 신체 부위 이름을 안정적으로 부여하는 방식을 제안했다.

```text
Human
├─ head
├─ neck
├─ chest
├─ abdomen
├─ pelvis
├─ left_upper_arm
├─ left_lower_arm
├─ right_upper_arm
├─ right_lower_arm
├─ left_upper_leg
├─ left_lower_leg
├─ right_upper_leg
└─ right_lower_leg
```

이름이 고정되면 `mesh.name`을 애플리케이션의 `bodyRegionId`와 연결할 수 있다. 화면 문구나 한국어 명칭을 Mesh 이름에 직접 사용하지 않고 안정된 내부 식별자를 사용한다.

### 2.3 GLTFLoader와 Raycaster

- `GLTFLoader`로 GLB/GLTF scene graph를 로드한다.
- 로드 후 각 Mesh를 순회하여 내부 신체 부위 식별자를 부여한다.
- `Raycaster`로 포인터가 선택한 Mesh를 판별한다.
- 시각 상태와 원본 건강 데이터는 분리한다.

### 2.4 연속값 기반 색상 표현

원 대화에서는 손상도를 연속값으로 유지하고 색상 구간으로 표현하는 방식을 선택했다.

```text
정상·낮음 → 초록
주의      → 노랑
높음      → 주황
매우 높음 → 빨강
```

색상만으로 의미를 전달하지 않고 수치, 상태 문구와 범례를 함께 제공해야 한다.

### 2.5 절차형 인체로 시작하고 실제 모델로 교체

초기 샘플은 별도 3D 자산 없이 바로 실행하기 위해 `SphereGeometry`, `CapsuleGeometry`, `BoxGeometry` 등으로 인체를 조립하는 방향을 선택했다.

```text
초기 기술검증
절차형 인체
→ 부위 선택
→ 데이터 매핑
→ 색상·상세 패널

후속 제품 후보
해부학적 human.glb
→ Skin·Skeleton·Organs·Muscles
→ 신체 영역 분할
→ 건강 상태 시각화
```

절차형 인체는 상호작용 계약을 검증하기 위한 대체물이며 최종 시각 자산으로 확정된 것이 아니다.

### 2.6 확장 프로토타입에서 제안한 화면 기능

- Damage·Normal·X-Ray 보기 모드
- Front·Back 전환
- Auto Rotate
- 신체 부위별 점수와 상태
- finding과 confidence
- 환자 바이탈 패널
- 우선 확인할 부위 목록
- 시간에 따른 변화량
- 이벤트 타임라인
- 스캔 애니메이션과 강조 pulse

이 항목들은 한 화면에서 가능한 상호작용을 확인하기 위한 데모 범위로 제안되었다. 이어봄의 확정 기능 목록은 아니다.

## 3. 원 대화의 예시 데이터 구조

원 대화는 대략 다음 형태의 프론트엔드 데이터를 제안했다.

```ts
interface BodyRegionFinding {
  bodyRegionId: string;
  label: string;
  score: number;
  severity: "normal" | "minor" | "moderate" | "severe" | "critical";
  confidence?: number;
  findings: string[];
}
```

예시로 `head`, `chest`, `abdomen`, `left_arm`, `right_leg` 등에 가상 점수와 진단 문구를 넣었다. 이 값은 합성 데모 데이터이며 의료적 판단 기준이나 실제 사용자 기록으로 사용하면 안 된다.

이어봄에서 후보 계약을 정의한다면 렌더링 용어와 건강 도메인 용어를 분리하는 편이 낫다.

```ts
interface BodyRegionViewState {
  bodyRegionId: string;
  displayLabel: string;
  level: "none" | "info" | "attention" | "high";
  value?: number;
  unit?: string;
  sourceRecordIds: string[];
  updatedAt?: string;
}
```

`damage`, `critical`, `diagnosis` 같은 표현은 근거가 없는 위험 판정으로 오해될 수 있으므로 실제 요구사항이 확정되기 전에는 중립적인 표현을 사용한다.

## 4. 아직 선택하지 않았거나 이어봄에 그대로 적용하지 않는 항목

### 4.1 FastAPI AI inference

원 대화의 최종 그림에는 `FastAPI AI inference`가 포함되어 있었다. 이어봄에서는 이를 현재 설계로 채택하지 않는다.

이유:

- 건강 입력을 FastAPI로 전송하면 웹 로컬 우선 데이터 경계와 충돌할 수 있다.
- 서버 추론은 PostgreSQL 저장 여부와 무관하게 건강정보 외부 전송에 해당한다.
- 브라우저에서 실행할 수 있는 TypeScript 규칙, ONNX Runtime Web, Web Worker, Rust/WASM 후보를 먼저 검토해야 한다.
- 서버 추론이 필요하다면 처리 위치, 동의, 전송 범위, 비저장 증명과 대체 경로를 별도 결정해야 한다.

### 4.2 실제 해부학 GLB 모델

실제 `human.glb`는 원 대화에서 연결하지 않았다. 이후 2026-08-20 후속 검토에서 Vanatome `1.4.0 regional-anatomy` GLB만 제한적으로 기술검증에 채택했다. 아래 기준은 다른 계통이나 전체 모델을 추가할 때 계속 적용한다.

따라서 다음을 확인하기 전에는 저장소 자산으로 채택하지 않는다.

- 상업적·교육적 사용 라이선스
- 재배포 가능 여부
- 신체 부위 분할 수준과 안정된 Mesh 이름
- 저사양 기기 렌더링 성능
- 모바일 메모리 사용량
- 모델이 불필요하게 상세하거나 불안감을 유발하지 않는지
- 성별·연령·체형 표현이 사용자 경험에 미치는 영향

#### 개별 장기 모델 조사 여부

원 대화에서는 안구·뇌·코·폐·간·신장·심장 같은 개별 장기 3D 모델 파일을 실제로 검색하거나 후보로 선정하지 않았다.

확인된 내용은 다음 수준에 머물렀다.

- 최종 `human.glb`를 `Skin·Skeleton·Organs·Muscles` 계층으로 구성할 수 있다는 제안
- `Chest → Lung → Left Lower Lobe`처럼 신체 영역과 장기를 계층화할 수 있다는 예시
- 폐 좌상과 심박수 같은 합성 데모 데이터
- Three.js 기본 Geometry로 구성한 절차형 인체와 간이 골격 표현

당시 검색 범위도 Three.js 설치·버전, `GLTFLoader`, `Raycaster`, `OrbitControls`, Three.js 공식 문서와 npm 정보였다. 장기 모델 저장소, 의료 3D 자산 제공처 또는 장기별 파일의 라이선스는 조사하지 않았다.

따라서 다음 작업은 아직 수행되지 않았다.

- 안구·뇌·코·폐·간·신장·심장별 GLB/GLTF 모델 후보 검색
- 여러 장기를 포함하는 통합 해부학 모델 후보 검색
- 장기별 Mesh가 독립적으로 선택 가능한지 확인
- 자산의 사용·수정·재배포 라이선스 검토
- 파일 크기, 폴리곤 수, 텍스처 용량과 브라우저 성능 비교
- 장기별 안정된 `bodyRegionId`와 Mesh 이름 규격 결정
- 장기와 로컬 건강기록을 연결하는 데이터 계약 설계

즉, 원 대화는 장기 계층으로 확장할 수 있다는 아이디어까지 진행되었으며 실제 장기 모델 자산 조사는 별도 후속 작업으로 남아 있다.

### 4.3 X-Ray 모드

프로토타입의 X-Ray는 간이 skeleton layer를 보여주는 시각 모드다. 실제 방사선 영상이나 의학적 X-ray 판독 결과가 아니다.

이 모드를 제품에 넣을 경우 사용자가 의료 영상 기능으로 오해할 가능성이 있어 명칭과 목적을 다시 정해야 한다. 단순 구조 보기라면 `골격 보기`처럼 더 정확한 이름을 사용한다.

### 4.4 손상 점수와 진단 문구

`Chest 82%`, `Right leg 67%`, `rib fracture`, `pulmonary contusion` 등은 데모 표현이다. 실제 점수 계산식, 임상 근거, 입력 출처와 책임 범위가 정의되지 않았다.

이어봄의 현재 만성질환·건강기록 흐름에서는 다음과 같은 표현이 더 적합할 수 있다.

- 기록 있음
- 최근 변화 있음
- 사용자가 주의 표시함
- 연결된 검사 결과 있음
- 의료진 확인 필요 문구가 원본 기록에 있음

자동으로 질병이나 손상을 판정하는 문구는 별도 모델 검증 없이 사용하지 않는다.

### 4.5 실시간 바이탈과 환자 모니터 UI

원 대화의 HR, SpO2, BP와 실시간 pulse 표현은 응급·입원 환자 모니터에 가까운 데모다. 이어봄이 실제 웨어러블이나 의료기기 데이터를 연결하지 않는 한 확정 기능이 아니다.

가짜 실시간 데이터는 화면 완성도를 높일 수 있지만 사용자가 실제 측정값으로 오해할 수 있다. 합성 데이터 화면에는 명확한 데모 표시가 필요하다.

### 4.6 어두운 TraumaVision 스타일

원 대화의 확장 샘플은 어두운 의료 관제 대시보드 스타일을 사용했다. 현재 이어봄이 지향하는 밝고 차분한 가족 건강기록 UI와는 분위기가 다르므로 기본 디자인으로 채택하지 않는다.

3D 뷰어만 어두운 배경을 필요로 하더라도 전체 애플리케이션과 단절되지 않도록 현재 디자인 토큰과 shadcn 계열의 절제된 UI를 우선한다.

### 4.7 CDN 기반 실행

최소 샘플은 Three.js를 CDN과 import map으로 불러오는 방식을 설명했다. 이어봄의 로컬 실행과 재현성 요구에는 다음 문제가 있다.

- 첫 실행이나 런타임에 외부 네트워크가 필요할 수 있다.
- 라이브러리 또는 모델 버전이 변경될 수 있다.
- 외부 요청 여부를 사용자가 구분하기 어렵다.
- CSP와 공급망 관리가 복잡해진다.

실제 구현 시 라이브러리는 프로젝트 의존성으로 고정하고, 3D 자산도 라이선스와 해시를 관리하며 자체 배포한다.

### 4.8 Three.js 버전 고정

원 대화는 당시 기준으로 Three.js `0.185.1`을 제시했다. 이 문서는 해당 버전을 프로젝트 결정으로 고정하지 않는다.

구현 착수 시 다음을 다시 확인한다.

- 현재 프론트엔드 빌드 도구와 호환성
- WebGL·WebGPU 지원 범위
- 사용하는 loader와 controls API
- 번들 크기와 tree shaking
- 보안 및 라이선스 상태

### 4.9 원 대화에서 생성됐다고 언급한 파일

원 대화에는 다음 sandbox 파일 링크가 등장했다.

```text
sandbox:/mnt/data/threejs-human-damage-dashboard.html
sandbox:/mnt/data/human-damage-dashboard-pro.html
sandbox:/mnt/data/human-damage-dashboard-pro.zip
```

이 링크는 원 ChatGPT 실행 환경에 속하며 현재 저장소로 이관된 파일이 아니다. 메시지에 포함된 코드와 설명은 읽을 수 있지만, 파일 링크가 있다는 이유만으로 완성 산출물이 현재 프로젝트에 존재한다고 간주하지 않는다.

## 5. 이어봄에서의 현재 해석

Three.js 인체 화면은 현재 이어봄의 핵심 저장·인증 기능이 아니라 로컬 건강기록을 탐색하는 선택적 시각화 계층으로 본다.

```text
IndexedDB의 암호화 건강기록
→ Local Domain API
→ 신체 부위별 파생 ViewState
→ Three.js 렌더러
→ 선택 부위 상세 기록 목록
```

이 기본 흐름에서는 건강기록이나 파생 결과가 서버 API로 전달되지 않는다.

### 서버가 처리할 수 있는 것

- 서비스 계정과 인증 상태
- 구독·라이선스

## 6. 권장 적용 단계

### 단계 0: 용어와 사용 목적 확정

- `손상 대시보드`가 이어봄의 실제 사용자 문제에 맞는지 확인한다.

- 의료 판정이 아니라 기록 탐색 도구인지 명시한다.

### 단계 1: 2D 계약과 접근성 우선

- 신체 부위 식별자 목록을 정의한다.
- 동일 데이터를 목록·표 형태로 먼저 표시한다.
- 키보드로 모든 부위를 선택할 수 있게 한다.
- 색상을 보지 못해도 상태와 기록 수를 이해할 수 있게 한다.

### 단계 2: 절차형 3D 기술검증

- 기본 Geometry로 신체 영역을 구성한다.
- 회전·확대·선택과 상세 패널 연결만 구현한다.
- 실제 의료 데이터 대신 합성 fixture를 사용한다.
- Three.js가 없어도 2D 목록으로 같은 작업을 수행할 수 있게 한다.

### 단계 3: 로컬 건강기록 연결

- Local Domain API에서 `BodyRegionViewState`를 만든다.

- 렌더링 상태를 TanStack Query 서버 캐시나 전역 영속 상태에 저장하지 않는다.
- 원본 기록은 기존 암호화 IndexedDB 경계를 유지한다.

### 단계 4: 실제 GLB 자산 평가

- 라이선스와 용량을 통과한 후보만 비교한다.
- Mesh 이름을 내부 `bodyRegionId`에 매핑한다.
- 데스크톱·모바일·저사양 환경의 프레임률과 메모리를 측정한다.
- 로딩 실패와 WebGL 미지원 시 2D 화면으로 자동 전환한다.

### 단계 5: 로컬 추론 후보 연결

- 규칙 또는 브라우저 로컬 모델이 실제 가치를 제공할 때만 연결한다.
- Worker 경계에서 실행하고 UI thread를 막지 않는다.
- 결과에는 모델 버전, 입력 기록과 사용자 확인 상태를 연결한다.
- 서버 추론은 별도 승인 전까지 구현하지 않는다.

## 8. 채택 판단 기준

다음 조건을 만족할 때 Three.js 인체 화면을 제품 로드맵에 올린다.

- 3D 화면이 2D 목록보다 기록 위치 이해를 실제로 개선한다.
- 테스트 사용자에게 의료 판정 화면으로 오해되지 않는다.
- 서버로 건강정보를 보내지 않고 동작한다.
- 합의한 기준 기기에서 초기 표시 시간과 프레임률이 허용 범위다.
- 키보드·스크린리더용 대체 경로가 있다.
- 3D 자산 라이선스와 재배포 권한이 명확하다.
- 로딩·렌더링 실패 시 기존 건강기록 기능을 방해하지 않는다.

다음 상황이면 후순위로 유지하거나 기각한다.

- 시각 효과 외에 사용자 작업이 개선되지 않는다.
- 실제 건강기록을 신체 부위에 신뢰성 있게 연결할 수 없다.
- 모델 자산이 너무 크거나 저사양 기기에서 불안정하다.
- 색상과 점수가 불필요한 불안 또는 잘못된 의료 해석을 만든다.
- 구현 때문에 백업·건강기록 입력·OCR·가족 연결 등 핵심 흐름이 지연된다.

## 9. 현재 결론

현재 확정된 결론은 다음과 같다.

1. Three.js 기반 신체 부위 선택과 로컬 기록 탐색은 검토 가치가 있다.
2. 절차형 인체는 상호작용 검증용으로 적합하지만 최종 디자인은 아니다.
3. 실제 GLB는 Vanatome `regional-anatomy`만 제한적으로 채택했으며 X-Ray, 실시간 바이탈, 손상 점수와 서버 AI 추론은 채택하지 않았다.
4. 구현한다면 건강 데이터는 IndexedDB와 Local Domain API 경계를 유지한다.
5. 브라우저 로컬 규칙·ONNX·Rust/WASM을 서버 추론보다 먼저 검토한다.
6. 3D가 실패하거나 비활성화되어도 동일 기능을 제공하는 2D 화면이 필수다.
7. 원 대화의 sandbox 파일은 현재 저장소 산출물이 아니다.

다음 의사결정은 `이어봄에서 인체 화면으로 해결하려는 실제 사용자 작업이 무엇인가`를 확정하는 것이다. 이 질문이 정해지기 전에는 화려한 Trauma 대시보드를 그대로 구현하지 않는다.

### 2026-08-20: Vanatome regional-anatomy 프리뷰 채택

절차형 인체보다 사용자가 해부 구조를 직접 선택하기 쉬운 샘플로 Vanatome을 채택했다. 전체 해부학 모델을 한 번에 싣지 않고 `regional-anatomy` 묶음만 가족 홈 프리뷰에 적용한다.

적용 범위:

- Vanatome의 버전 고정 카탈로그와 GLB 자산을 사용한다.
- Vanatome React 뷰어의 로딩 완료 상태가 현재 Vite SPA에서 갱신되지 않아 해당 통합 계층은 기각하고 기존 Three.js `GLTFLoader`로 자산을 직접 렌더링한다.
- Three.js는 기존 기술검증 버전 `0.185.1`을 유지한다.
- 약 6MB인 Vanatome `1.4.0 regional-anatomy` GLB와 메타데이터만 자체 정적 자산으로 배포한다.
- 런타임에 Vanatome CDN이나 다른 외부 서버를 호출하지 않는다.
- 모델 선택 결과는 GLB Mesh 이름에서 만든 표시 이름까지만 UI 상태로 유지한다. 이 이름은 아직 건강기록의 영속 식별자로 사용하지 않는다.
- 개별 외형 Mesh 선택과 선택 해제를 제공한다.
- 모델 출처와 CC BY-SA 4.0 라이선스를 화면에서 확인할 수 있게 한다.
- 모델 또는 WebGL 로딩 실패 시 기존 절차형 인체와 2D 부위 버튼으로 전환한다.
- 건강기록, 사용자 식별정보와 프로필 정보는 모델 로더에 전달하지 않는다.

Vanatome 뷰어 코드는 MIT 라이선스지만 Z-Anatomy 기반 GLB와 메타데이터는 CC BY-SA 4.0이다. 수정·재배포 시 출처, 변경 내용, 라이선스 링크와 ShareAlike 조건을 보존해야 한다.

현재 선택하지 않은 범위:

- 해부 구조의 한국어 번역 카탈로그
- 해부 구조와 건강기록의 영속 연결

31.8MB 고해상도 전체 인체 모델을 그대로 전송하지 않는다. 같은 1.4.0 상세 모델에서 현재 화면에 표시하는 외피·골격·심혈관·호흡기·소화기·비뇨기·내분비 Mesh만 추출한 약 15.6MB 파생 GLB를 기본 화면에 사용한다. 신경계·근육계·림프계·생식계는 후속 계층 선택 기능으로 남긴다.

Vanatome React·React Three Fiber 의존성을 제거한 뒤 Three.js 지연 청크와 GLB를 별도 정적 자산으로 유지한다. 가족 홈 초기 번들에는 포함하지 않지만, 저사양·모바일 기기 적용 전에는 실제 로딩 시간과 메모리·프레임률 측정이 필요하다.

## 11. 목표 시각 방향: 계층형 홀로그램 해부학 뷰어

Vanatome 대표 이미지에서 채택을 검토하는 스타일은 단순한 `wireframe` 하나가 아니다. 가장 정확한 설명은 **반투명 외피 안에 해부 구조를 계층적으로 보여주는 홀로그램 해부학 시각화**다.

### 11.1 권장 명칭

문맥에 따라 다음 명칭을 사용한다.

| 사용 위치 | 권장 명칭 |
| --- | --- |
| 개발·설계 문서 | 계층형 홀로그램 해부학 뷰어 |
| 기술 설명 | 반투명 와이어프레임 인체 + 계층형 장기 시각화 |
| 사용자 메뉴 | 인체 내부 구조 |
| 영문 표현 | Holographic Anatomy Viewer |

Vanatome에서 사용하는 `holographic anatomy`, `ghost mode`, `x-ray mode`, `translucent body shell`도 유사한 표현이다. 다만 이어봄 사용자 화면에서는 실제 의료 영상으로 오해할 수 있는 `X-Ray`보다 `내부 구조 보기`를 우선한다.

### 11.2 현재 외형 화면과 목표 화면의 차이

| 구분 | 현재 기술검증 화면 | 목표 홀로그램 해부학 화면 |
| --- | --- | --- |
| 외피 | 불투명한 단색 인체 | 반투명 또는 와이어프레임 외피 |
| 내부 구조 | 표시하지 않음 | 골격·장기·세부 구조를 선택적으로 표시 |
| 배경 | 밝은 제품 UI | 뷰어 내부에 한정한 어두운 청록·남색 배경 후보 |
| 주요 작업 | 인체 외형과 표면 위치 선택 | 장기의 위치와 구조 간 관계 파악 |
| 계층 | 외피 중심 | 외피 → 골격 → 계통 → 장기 → 세부 구조 |
| 강조 | 선택한 표면 Mesh 색상 변경 | 선택 장기는 선명하게, 주변 구조는 반투명하게 표시 |

현재 화면은 실제 GLB 로딩, 회전, 확대와 Mesh 선택을 검증하는 단계다. 단색 외피 자체를 최종 디자인으로 확정하지 않는다.

### 11.3 시각 구성 요소

#### 반투명 외피

- 피부와 신체 윤곽은 내부 장기의 위치를 이해하는 공간적 문맥으로 사용한다.
- 외피의 불투명도를 낮추고 필요하면 `depthWrite`를 비활성화한다.
- 외피는 기본 선택 대상에서 제외하거나 낮은 우선순위를 부여할 수 있다.

#### 와이어프레임 표현

- 인체 표면의 삼각형 또는 선 구조를 청록색 계열로 표현한다.
- Three.js Material의 `wireframe` 또는 별도의 Edge·Line 렌더링을 사용할 수 있다.
- 선이 너무 조밀해 장기를 가리거나 시각적 피로를 만들지 않도록 밀도와 투명도를 조절한다.

#### 고스트·내부 구조 보기

- 외부 구조는 흐리게 하고 선택한 내부 구조는 더 불투명하게 표시한다.
- 실제 방사선 영상이나 판독 기능이 아니라 3D 장면의 가시성 모드다.
- 사용자에게는 `내부 구조 보기` 또는 `주변 구조 흐리게`로 설명한다.

#### 장기별 선택과 강조

- 심장, 폐, 간, 신장, 위장 등은 독립적인 안정 ID와 Mesh를 가져야 한다.
- 선택한 장기는 원래 색이나 강조색으로 표시한다.
- 선택하지 않은 구조는 숨기거나 반투명하게 처리한다.
- 색상만으로 선택 상태를 전달하지 않고 장기명, 계통명과 텍스트 상태를 함께 표시한다.

#### 홀로그램 조명과 배경

- 외피에는 cyan 계열 색상과 제한적인 emissive 효과를 적용할 수 있다.
- 어두운 배경은 전체 애플리케이션이 아니라 3D 뷰어 영역 안에서만 사용한다.
- bloom, scanline과 격자 효과는 성능과 가독성을 검증한 뒤 최소한으로 사용한다.

#### 의료 HUD 장식

- 초점 괄호, 스캔 표시와 상태선은 실제 선택·로딩·집중 상태를 나타낼 때만 사용한다.
- 클릭 기능이나 상태 의미가 없는 배지·점·괄호를 장식 목적으로 반복하지 않는다.
- 기능 없는 장식이 늘어나면 AI 생성 UI처럼 보이고 사용자가 조작 요소로 오해할 수 있다.

### 11.4 권장 보기 모드

```text
외형 보기
├─ 불투명 또는 낮은 투명도의 인체 외피
└─ 표면 위치 탐색

내부 구조 보기
├─ 반투명·와이어프레임 외피
└─ 선택한 장기 계통 표시

선택 구조만 보기
├─ 선택 장기 또는 하위 구조 강조
└─ 주변 구조 숨김 또는 고스트 처리

전체 구조 보기
├─ 여러 계통을 함께 표시
└─ 성능과 시각 복잡도를 고려해 명시적으로 실행
```

`Damage`, `Critical`, `Trauma` 같은 표현은 의료적 근거 없이 위험도나 진단을 암시하므로 기본 보기 모드로 사용하지 않는다.

### 11.5 권장 구현 계층

```text
반투명·와이어프레임 외피
    ↓ 신체 위치와 공간적 문맥 제공
골격·장기 계통 GLB
    ↓ 사용자가 계통 또는 장기 선택
선택 구조 강조·주변 구조 고스트 처리
    ↓ Local Domain API의 기록 위치와 연결
관련 건강기록 목록 표시
```

외피, 골격과 장기 계통은 서로 다른 정적 자산으로 지연 로딩할 수 있어야 한다. 기본 가족 홈에서는 외피만 표시하고 사용자가 `내부 구조 보기`를 실행했을 때 필요한 계통 GLB만 추가로 불러오는 방식을 우선한다.

### 11.6 채택 전 확인할 사항

- 대표 이미지 수준의 외피와 장기 합성이 실제 브라우저에서 안정적으로 렌더링되는가
- 기본 외피, 단일 장기 계통과 전체 구조의 초기 로딩 시간이 각각 허용 가능한가
- 모바일과 저사양 기기에서 메모리·프레임률이 허용 범위인가
- 장기별 안정 ID와 한국어 표시 명칭을 제공할 수 있는가
- 외피 때문에 장기 선택이 방해되지 않는가
- 키보드와 2D 구조 목록으로 동일한 선택 작업을 수행할 수 있는가
- 홀로그램 표현이 의료 판정 화면으로 오해되지 않는가
- 추가하는 모든 GLB와 메타데이터가 자체 호스팅되고 출처·ShareAlike 조건을 유지하는가

### 11.7 1차 적용 결과

내부 구조 보기를 기본 화면으로 적용했다.

- 별도의 외형 보기 전환은 제공하지 않는다.
- Three.js 코드는 가족 홈의 다른 코드와 분리된 지연 청크로 유지한다.
- 1.4.0 상세 모델의 표시 계층만 추출한 약 15.6MB 파생 모델을 사용하며 HTTP 압축 시 약 11MB 수준이다.
- 버전이 고정된 `/vendor/` 자산에는 장기 immutable 캐시를 적용한다.
- 외피는 청록색 반투명 와이어프레임으로 렌더링하고 선택 대상에서 제외한다.
- 골격은 옅은 반투명 재질, 주요 장기는 원본 계통 색을 살린 불투명 재질로 겹쳐 표시한다.
- 내부 구조 Mesh를 클릭하면 메타데이터의 구조명과 계통명을 표시한다.
- 어두운 배경과 약한 scanline은 3D 뷰어 내부에만 적용하며 기능 없는 HUD 장식은 추가하지 않는다.
- 이 단계에서도 건강기록과 장기 선택은 자동 연결하거나 저장하지 않는다.

이는 Vanatome 대표 이미지의 시각 원리를 브라우저에서 검증하기 위한 1차 구현이다. 다음 단계는 한국어 구조명, 계통별 표시 전환, 2D 접근성 목록, 실제 기기 성능 측정이며, 의료적 위험도·진단 표현은 여전히 범위에서 제외한다.

### 11.8 기본 내부 구조 화면의 부하 절감 결정

계통 GLB를 각각 조합하면 외피 약 6.3MB에 골격·심혈관·호흡기·소화기·비뇨기 파일이 중복되어 전체 다운로드가 30MB를 넘는다. 따라서 첫 화면에서 계통 파일을 병렬로 받는 방법은 채택하지 않는다.

Vanatome의 별도 경량 전체 인체 모델은 약 11.1MB지만 349개 Mesh와 114개 구조 ID만 포함해 현재 1.4.0 내부 구조 보기의 시각 정밀도와 구성이 달라진다. 초기 용량을 이유로 이 모델로 교체하는 방법은 기각한다.

대신 984개 Mesh와 749개 구조 ID를 포함하는 1.4.0 상세 전체 모델 약 31.8MB에서 화면에 실제 표시하는 512개 Mesh만 추출한다. 결과 모델은 약 15.6MB이며 외피 236개, 골격 181개, 심혈관 64개, 소화기 12개, 내분비 10개, 호흡기 6개, 비뇨기 3개 Mesh를 보존한다. 따라서 기존 내부 구조 보기의 재질·형태·구조 ID는 유지하면서 원본 대비 약 51%의 파일 크기를 줄인다.

파생 모델은 `frontend/scripts/build-hologram-model.mjs`로 재생성한다. 원본 상세 GLB를 갱신할 때 동일한 추출 규칙을 반복 적용할 수 있어야 하며, 수작업으로 모델을 편집하지 않는다.

초기 비용은 다음 세 층으로 관리한다.

1. 가족 홈의 일반 UI와 로컬 기록을 먼저 렌더링한다.
2. 분리된 Three.js 청크와 상세 계층 추출 모델로 홀로그램 내부 구조를 표시한다.
3. 상세 해부 구조가 필요한 기능에서만 고해상도 모델 또는 개별 계통 모델을 추가로 불러온다.

정적 포스터는 체감 로딩을 개선할 수 있지만 실제 전송량을 줄이지 않으므로 현재 필수 자산으로 추가하지 않는다. 추가 최적화가 필요하면 Meshopt·Draco 압축, 저해상도 LOD 생성, 실제 모바일 메모리 측정을 순서대로 검토한다.

### 11.9 부위별 빠른 확대

전체 인체를 처음 표시한 상태에서 `머리`, `상반신`, `하반신`, `손` 네 가지 빠른 확대를 제공한다. 이 기능은 이미 렌더링한 동일 모델의 카메라 위치와 OrbitControls 회전 중심만 이동하므로 추가 모델이나 네트워크 요청을 만들지 않는다.

- 머리: 얼굴·두개골·머리 내부 구조를 중심으로 확대한다.
- 상반신: 머리·흉부·복부 상단을 중심으로 확대한다.
- 하반신: 골반·다리·발을 중심으로 확대한다.
- 손: 한쪽 손을 가까이 표시하고 사용자가 회전과 휠 확대를 계속 사용할 수 있게 한다.
- 전체 보기: 확대 후 최초 전신 구도로 복귀한다.

카메라는 즉시 점프하지 않고 짧은 ease-out 전환으로 이동한다. 확대 상태에서도 구조 클릭과 회전 기능은 유지하며, 확대 선택 자체는 건강기록에 저장하지 않는다.
