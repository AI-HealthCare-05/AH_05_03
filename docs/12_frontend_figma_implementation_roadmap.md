# Figma 기반 프론트엔드 구현 로드맵

> 관련 문서: [04_wireframe.md](04_wireframe.md), [07_roadmap.md](07_roadmap.md), [10_local_data_contract.md](10_local_data_contract.md), [ADR-005](adr/0005-vite-spa-local-first-frontend-foundation.md)
> 목적: 정적 Figma 와이어프레임을 이어봄의 데이터 경계를 지키는 React 화면과 기능으로 단계적으로 전환한다.

## 1. 문서 역할

- `04_wireframe.md`는 무엇을 보여주고 어떤 상태가 필요한지 정의한다.
- `07_roadmap.md`는 일정과 담당자를 관리한다.
- 이 문서는 Figma 화면을 어떤 순서와 완료 기준으로 프론트엔드에 옮길지 정의한다.
- Figma에서 생성되는 예시 코드는 참고 자료이며 프로젝트 코드에 그대로 복사하지 않는다.

## 2. Figma 기준과 버전 구분

| 노드 | 용도 | 구현 기준 |
|---|---|---|
| `5:2` | Manyfast·가족력·로컬 우선 정책 반영 버전 | 현재 제품의 화면·문구·데이터 경계 기준 |
| `0:1` | 앱·모바일 버전 | 모바일 레이아웃과 입력 패턴 참고 |
| `1:2` | 기존 데스크톱 버전 | 색상·타이포그래피 등 시각 요소 참고 |

- 현재 Figma는 정적 와이어프레임이므로 프로토타입 연결 여부를 구현 선행조건으로 삼지 않는다.
- 구버전의 개인 건강관리·위험도·챌린지 정보구조를 현재안에 자동으로 합치지 않는다.
- 구현 티켓에는 반드시 기준 Figma 노드 ID와 화면 상태를 기록한다.
- 이름이 `Frame`인 최상위 노드는 구현 전에 목적이 드러나는 이름으로 변경한다.

## 3. 구현 전 결정 게이트

다음 항목을 결정하거나 명시적으로 보류한 뒤 기능 화면 구현을 시작한다.

1. 서비스 계정과 가족 구성원 로컬 프로필의 화면상 구분
2. 삭제·첨부파일·변경 이력·복구 가능 여부의 일관된 정책
3. OCR·대화형 기록 도우미·예측 기능의 실제 브라우저 로컬 실행 경계
4. 암호화 키 생성·변경·분실·새 기기 연결 정책
5. 모바일을 반응형 웹으로 제공할 범위와 PWA 도입 시점
6. UI 구현 방식

`04_wireframe.md`는 Shadcn/ui와 Tailwind CSS를 명시하지만 현재 `frontend/`에는 두 의존성이 없다. 도입 여부를 팀에서 결정하기 전에는 새 UI 프레임워크를 임의로 추가하지 않고, 기존 CSS 변수와 React 컴포넌트를 사용한다. 도입을 확정하면 의존성·스타일 전략·마이그레이션 범위를 별도 결정 기록으로 남긴다.

## 4. 화면 계약 작성

각 화면을 구현하기 전에 다음 항목을 짧은 표 또는 티켓으로 작성한다.

| 항목 | 내용 |
|---|---|
| 화면·Figma 노드 | 화면명과 노드 ID |
| 경로 | React Router URL |
| 진입 조건 | 최초 방문, 구성원 선택, 로그인 필요 여부 등 |
| 정본 데이터 | 로컬 또는 서버 |
| 주요 작업 | 저장, 수정, 병합, 내보내기 등 |
| 상태 | 기본, 로딩, 빈 상태, 오류, 저장공간 부족, 오프라인 |
| 파괴적 영향 | 삭제 대상, 첨부파일 영향, 복구 가능 여부 |
| 반응형 규칙 | 모바일·태블릿·데스크톱 배치 |
| 완료 검증 | 단위·통합·E2E·시각 검토 조건 |

## 5. 프론트엔드 공통 기반

### 5.1 기존 기반 유지

- React·TypeScript·Vite SPA와 React Router를 유지한다.
- Zustand는 메뉴·모달·필터처럼 비민감 UI 상태에만 사용한다.
- TanStack Query는 계정·구독·초대·기기 연결 같은 서버 상태에만 사용한다.
- 건강정보는 Local Domain API를 통해서만 접근한다.
- 검증용 시작 화면과 데이터 경계 화면은 제품 화면 구현 중에도 개발자 확인 경로로 유지한다.

### 5.2 공통 UI 구성요소

기능 화면보다 먼저 다음 공통 요소와 상태를 구현한다.

```text
shared/ui/
├── Button
├── TextField
├── TextArea
├── Select
├── Checkbox
├── Radio
├── Modal
├── Card
├── DataTable
├── StatusBadge
├── LocalStorageNotice
├── EmptyState
├── ErrorState
└── ConfirmDialog
```

- 색상·타이포그래피·간격·테두리·그림자는 CSS 토큰으로 관리한다.
- 버튼과 입력에는 기본·호버·포커스·비활성·오류 상태를 제공한다.
- 아이콘과 이미지는 Figma 원본 자산을 내려받아 프로젝트 자산으로 관리한다.
- 화면별 일회성 CSS보다 공통 컴포넌트와 토큰을 우선한다.

### 5.3 앱 셸과 권장 라우트

```text

```

## 6. 데이터 경계

### 6.1 로컬 건강정보

```text
React UI
  → Local Domain API
    → Web Crypto
      → IndexedDB / OPFS
```

- 프로필, 건강기록, 가족력, 통증 기록, OCR 결과와 모델 결과는 서버 API Client를 통과하지 않는다.
- 복호화된 건강정보를 Zustand, TanStack Query key·cache, URL, 로그에 넣지 않는다.
- UI에서 IndexedDB·OPFS·Web Crypto를 직접 호출하지 않는다.

### 6.2 서버 메타데이터

```text
React UI
  → TanStack Query
    → Server API Client
      → 계정·구독·초대·연결 상태
```

- 서비스 계정이 존재한다는 이유만으로 건강정보 접근 권한을 부여하지 않는다.
- 초대·프로필 연결과 건강정보 전송을 서로 다른 작업으로 구현한다.
- 선택형 동기화가 도입되기 전까지 서버에 건강정보 암호문을 저장하는 코드를 추가하지 않는다.

## 7. 수직 기능별 구현 순서

### 단계 1 — 앱 셸과 가족 프로필 기본 흐름

1. 서비스 시작·개인정보 안내
2. 가정 생성
3. 홈·구성원 목록
4. 구성원 등록·수정
5. 구성원 건강 대시보드

합성 데이터로 라우팅·반응형·접근성을 먼저 완성한 뒤 Local Domain API를 연결한다.

### 단계 2 — 로컬 건강기록

1. 건강기록 작성
2. 건강 이력 목록·상세·수정
3. 가족력 관리
4. 삭제·변경 이력
5. 건강 변화 차트

`가정 생성 → 구성원 등록 → 기록 작성 → 암호화 저장 → 다시 조회`가 실제로 끝까지 동작해야 단계 완료로 본다.

### 단계 3 — 원본서류와 백업·복구

1. OPFS 원본 서류 저장
2. OCR 로컬 실행과 결과 검토
3. 암호화 백업 내보내기
4. 백업 파일 가져오기
5. 충돌 비교·병합
6. 변경 이력과 시점 복구

백업 내보내기 후 로컬 데이터를 비우고 다시 가져오는 왕복 테스트를 통과해야 한다.

### 단계 4 — 서비스 계정과 프로필 연결

1. 가입·로그인·구독 상태
2. 기존 로컬 프로필 선택
3. 연결 생명주기용 불투명 참조값 생성과 `pending` 상태 저장
4. 가족 서비스 계정 초대·수락과 동일 작업 재시도
5. 기존 프로필과 서비스 계정 연결 및 `active` 전환
6. 연결 해제·초대 종료·병합 시 참조값 `retired` 처리
7. 재초대·재연결 시 새 참조값 생성
8. 중복 프로필 감지·비교·병합
9. 병합 완료와 되돌리기

계정 연결만으로 건강정보가 서버에 업로드되거나 상대 기기에 복사되지 않도록 한다.
타임아웃 재시도에는 같은 참조값과 멱등성 키를 사용하고, 폐기된 참조값이 든 오래된 백업을 복구해도 서버 연결에는 재사용하지 않는 테스트를 포함한다.

### 단계 5 — 접근 범위와 동기화

1. 구성원·기록 유형별 접근 범위
2. 암호화 이전 파일 또는 승인된 기기 전송
3. 선택형 암호화 동기화
4. 연결 기기 관리
5. 동기화 충돌·삭제 전파·키 복구

### 단계 6 — 로컬 모델 기능

1. 대화형 통증 기록 도우미
2. 건강 변화 예측
3. 가족 유전정보 참고

- 외부 AI API 없이 실행되는 제품 런타임을 먼저 확정한다.
- 합성 데이터와 golden fixture로 결과를 검증한다.
- 의료 진단·응급 판단으로 오인될 문구와 수치를 별도로 검토한다.

단계 4~6은 제외 기능이 아니라 후순위 목표다. 앞 단계가 조기에 완료되면 즉시 앞당길 수 있도록 화면 계약과 와이어프레임을 유지한다.

## 8. 화면 단위 반복 절차

1. 구현할 Figma 노드의 디자인 컨텍스트와 스크린샷을 조회한다.
2. 기존 공통 컴포넌트·토큰·라우트와 중복 여부를 확인한다.
3. 합성 데이터로 화면과 모든 상태를 구현한다.
4. Local Domain API 또는 Server API 중 하나의 경계에만 연결한다.
5. 데스크톱·모바일 레이아웃을 확인한다.
6. 키보드 탐색·포커스·모달·레이블 접근성을 검사한다.
7. Figma와 브라우저 화면을 비교해 차이를 수정한다.
8. 단위·통합·E2E 테스트를 통과시킨다.
9. 하나의 사용자 기능 단위로 커밋하고 리뷰한다.

## 9. 필수 자동 검증

- 로컬 건강정보 작업 중 `/api` 요청이 발생하지 않는다.
- IndexedDB와 OPFS에 평문 건강정보가 남지 않는다.
- 건강정보가 Zustand·TanStack Query·URL·로그에 포함되지 않는다.
- 암호화 백업의 내보내기·가져오기 왕복이 성공한다.
- 삭제·첨부파일·복구 정책이 모든 화면과 테스트에서 동일하다.
- 320px 모바일부터 1440px 데스크톱까지 주요 작업을 완료할 수 있다.
- 로딩·빈 상태·오류·저장공간 부족·오프라인 상태를 처리한다.
- 모달 포커스 이동과 키보드 조작이 가능하다.
- 로컬 모델 실행 중 외부 AI·서버 요청이 발생하지 않는다.

## 10. 단계별 완료 조건

기능은 다음 조건을 모두 충족해야 완료로 표시한다.

- 화면 계약과 Figma 노드가 연결되어 있다.
- 정상 상태와 필수 예외 상태가 구현되어 있다.
- 데이터 정본과 호출 경계가 코드 리뷰에서 확인되었다.
- 반응형·접근성·시각 비교를 통과했다.
- 관련 자동 테스트가 추가되고 기존 테스트가 통과했다.
- 사용자에게 데이터 저장 위치와 파괴적 작업의 영향을 정확히 설명한다.

## 11. 첫 번째 구현 목표

전체 Figma 화면을 동시에 옮기지 않는다. 첫 목표는 다음 하나의 수직 흐름이다.

```text
서비스 시작 → 로컬 보관 안내 → 가정 생성
→ 가족 구성원 로컬 프로필 생성 → 건강기록 작성
→ 암호화 저장 → 종료 후 다시 조회
```

이 흐름의 데이터 경계와 테스트가 안정된 뒤 동일한 구조로 가족력, 서류, 백업, 계정 연결과 동기화를 확장한다.
