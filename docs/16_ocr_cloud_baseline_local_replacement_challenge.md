# OCR 클라우드 기준선·로컬 대체 챌린지

> 상태: 실행 계획
> 기준일: 2026-08-20
> 상위 결정: [ADR-008 개발 검증용 클라우드 OCR 기준선 허용](adr/0008-temporary-cloud-ocr-baseline.md)
> 이 문서의 후보·수치·일정은 실험 결과에 따라 변경할 수 있다. 확정 정책은 ADR-008을 따른다.

## 1. 목적

한국어 건강검진표의 입력부터 사용자 검토, 구조화 건강기록과 차트 반영까지 제품 흐름을 먼저 완성하면서 건강문서가 사용자 기기를 떠나지 않는 로컬 OCR 대안을 병렬로 검증한다.

- 트랙 A는 Naver CLOVA OCR로 비교 기준과 제품 흐름을 만든다.
- 트랙 B는 브라우저·사용자 기기에서 실행되는 OCR·문서 VLM으로 트랙 A를 대체할 가능성을 검증한다.
- 두 트랙은 같은 입력 계약, 출력 계약과 평가 데이터셋을 사용한다.
- 어떤 엔진도 사용자 검토 없이 OCR 결과를 건강기록으로 확정하지 않는다.

## 2. 공통 경계

```text
문서 선택
→ 엔진 선택과 처리 위치 확인
→ OCR 실행
→ 공통 OcrResult 변환
→ 사용자 검토·수정
→ 확정된 구조화 결과만 IndexedDB 암호화 저장
→ 로컬 집계·차트 반영
```

```ts
interface OcrEngine {
  readonly id: string;
  readonly processingLocation: "device" | "self-hosted-server" | "external-provider";
  recognize(input: OcrInput): Promise<OcrResult>;
}

interface OcrResult {
  engineId: string;
  engineVersion: string;
  pages: OcrPage[];
  fields: OcrField[];
  warnings: string[];
  processingTimeMs: number;
}
```

- `processingLocation`이 셋이다. 처음엔 `device`와 `external-provider` 둘이었고, [ADR-010](adr/0010-checkup-document-ocr-path.md) §3이 우리 서버 ai-worker를 기본 경로로 정하면서 `self-hosted-server`가 생겼다. 화면은 이 값을 사용자에게 그대로 보여준다 — 어디서 처리되는지가 동의의 대상이다.
- UI는 엔진 구현체가 아니라 `OcrEngine`만 사용한다.
- 원본 파일, 전체 OCR 텍스트와 건강 필드값을 TanStack Query·Zustand 영속 상태에 넣지 않는다.
- 모델 자산은 버전과 해시를 고정하고 실행 중 외부 CDN에서 동적으로 받지 않는다.
- 테스트·벤치마크 원본은 Git에 커밋하지 않고 데이터 생성법과 비민감 기대값만 보존한다.

## 3. 트랙 A: Naver OCR 기준선

### 목표

- 한국어 건강검진표 OCR 제품 흐름을 조기에 완성한다.
- 로컬 후보의 정확도와 처리 시간을 비교할 기준값을 만든다.
- 외부 전송 예외가 서버 저장으로 확대되지 않는지 검증한다.

### 범위

1. 외부 전송 안내와 명시적 엔진 선택
2. FastAPI 메모리 중계 어댑터
3. Naver 응답을 공통 `OcrResult`로 변환
4. 사용자 검토·수정 UI
5. 확정값의 브라우저 로컬 저장과 차트 반영
6. PostgreSQL·Redis·파일·로그 비저장 자동 검증

### 금지 사항

- 개인정보가 포함된 실제 건강문서 전송
- Redis Stream·캐시·PostgreSQL에 원본 또는 OCR 결과 저장
- Object Storage 중계
- 요청·응답 본문과 파일명을 로그·APM·오류 보고에 첨부
- 로컬 OCR 실패 후 묵시적 Naver fallback
- Naver 결과의 자동 건강기록 확정

### 완료 산출물

- `NaverCloudOcrEngine` 어댑터와 계약 테스트
- 합성·비식별 입력의 성공·오류·타임아웃 시나리오
- 서버 비저장과 브라우저 확정 저장을 증명하는 테스트
- 트랙 B가 비교할 기준선 결과 리포트

## 4. 트랙 B: 로컬 OCR·VLM 대체

### 후보 단계

| 단계 | 후보 | 실행 위치 | 목적 | 예상 위험 |
|---|---|---|---|---|
| B1 | Tesseract 한국어 + 전처리 | 기기 | 가벼운 오프라인 기준선 | 표 구조·촬영 품질에 취약 |
| B2 | PaddleOCR 한국어·PaddleOCR.js | 기기 | 브라우저 한국어 인식 개선 | 모델 변환·브라우저 호환성 검증 필요 |
| B3 | ONNX Runtime Web WASM·WebGPU | 기기 | 자체 호스팅 브라우저 추론 | 연산자 지원·메모리·초기 다운로드 |
| B4 | PaddleOCR-VL 계열 로컬 실행 | 기기 | 표·문서 구조·복합 요소 인식 | 브라우저 포팅과 저사양 기기 비용 |
| B5 | OCR + 건강검진 규칙 결합 | 기기·서버 공통 | 검사명·숫자·단위 검증 | 병원별 서식 편향과 유지보수 |
| **B6** | **클라우드 멀티모달 VLM 직송** | **외부 사업자** | 전처리·규칙 없이 문서에서 바로 구조화 JSON | **근거 좌표가 없어 검토·수정 화면이 성립하지 않는다.** 문서 전체가 외부로 나가고 이미지 토큰 비용이 붙는다 |
| **B7** | **서버 자체 호스팅 PP-OCR ONNX** | **우리 서버 ai-worker** | 외부 전송 없이 상용급 인식 | 홈서버 가동률과 동시 처리량이 우리 몫. `mem_limit: 4G` 한 대가 상한 |

큰 VLM을 모든 문서의 첫 엔진으로 사용하지 않는다. 가벼운 OCR과 전처리·규칙으로 해결하지 못한 표나 복합 문서를 VLM 후보로 평가한다.

### B6·B7을 추가한 경위와 트랙 이름 재해석

**B6은 [ADR-010](adr/0010-checkup-document-ocr-path.md) §2가 등재만 하고 채택하지 않기로 한 후보다.** 이 표에 넣는 이유는 하나다 — 후보에 없으면 "왜 안 썼는지"가 아니라 "검토조차 안 했다"가 된다. 기각 근거는 정확도가 아니라 근거 좌표다. 우리는 인식 결과를 사용자가 검토·수정해야 확정하는데(§2 공통 경계), 직송은 bounding box를 주지 않아 검사 항목 30개 중 어느 값이 틀렸는지 지목할 수 없다.

**B7은 ADR-010 §3이 제품 기본 경로로 채택한 엔진이다.** 원래 이 표에 없었다. 트랙 B를 `로컬 = 기기 안`으로 전제하고 썼기 때문이다. ADR-009가 서버 추론을 열면서 전제가 바뀌었다.

그래서 **트랙 B의 이름을 `Naver 대체`로 읽는다.** `로컬`이 `기기 안`에서 `우리 통제 안`으로 넓어졌다. 기기 실행(B1~B4)은 폐기가 아니라 보류이고, 오프라인 요구나 서버 전송을 거부하는 사용자 경로가 생기면 다시 1순위가 된다.

지연 시 우선순위도 다시 적는다 — `B7 → B5 → B1·B2 → B3 → B4 → B6`. B6은 채점 비교용이라 일정에서 가장 먼저 빠진다.

### 브라우저 실행 원칙

- 추론 입력은 브라우저 메모리와 Worker 경계를 벗어나지 않는다.
- 가능한 경우 WASM fallback과 WebGPU 가속을 함께 제공한다.
- 모델 최초 설치 후 OCR 실행 중 네트워크 요청이 없어야 한다.
- 브라우저 미지원·메모리 부족·시간 초과는 사용자에게 알려 직접 입력과 다른 엔진 선택 경로를 제공한다.
- 사용자 기기에 로컬 추론 서버를 별도로 설치하는 방식은 브라우저 단독 경로와 구분해 기술검증으로만 평가한다.

## 5. 평가 데이터셋

### 구성

- 합성 건강검진표: 병원명·이름·식별번호가 실제 인물과 연결되지 않도록 생성
- 비식별 검증 문서: 사용 권한을 확인하고 재식별 가능 필드 제거
- 깨끗한 PDF, 스캔, 휴대폰 촬영, 회전·왜곡·그림자·저해상도 변형
- 검사명, 결과값, 단위, 기준범위, 판정, 날짜와 표 구조 정답

### 분리

- 개발 세트: 전처리와 규칙 조정
- 검증 세트: 후보 선택과 오류 분석
- 고정 평가 세트: 최종 비교 전까지 정답을 수정하지 않음

동일 문서와 정답으로 모든 엔진을 평가한다. Naver 출력으로 로컬 모델의 정답을 만들지 않는다.

## 6. 평가 지표

### 정확도

- 한국어 문자 오류율(CER)
- 핵심 숫자 정확 일치율
- 검사명·결과값·단위 연결 정확도
- 표 셀·행·열 복원 F1
- 핵심 필드 누락률
- 저신뢰 결과 감지율

`120 → 170`, `5.6 → 56`, `mg/dL → mmol/L`, `음성 → 양성`처럼 의미가 바뀌는 오류는 일반 글자 오류보다 높은 위험으로 분류한다.

### 실행성

- 페이지당 p50·p95 처리 시간
- 최초 모델 다운로드 크기와 준비 시간
- 최대 메모리 사용량과 OOM·탭 종료율
- Chrome·Edge·Safari 및 저사양 기기 지원 범위
- 모델 설치 후 오프라인 재실행 성공 여부

### 개인정보 경계

- OCR 실행 중 외부 네트워크 요청 수
- 서버·Redis·PostgreSQL·로그에 남은 민감 payload 수
- 원본·결과가 브라우저 암호화 보관함 외부에 남는지 여부

### 외부 전송 여부 — 경로를 가르는 축

앞의 세 항목은 실행 결과를 세는 것이고, 이 축은 **설계상 나가는지**를 판정한다. 두 경로가 정확도에서 비슷할 때 여기서 갈린다.

| 값 | 뜻 | 해당 후보 |
|---|---|---|
| `none` | 문서가 사용자 기기를 벗어나지 않는다 | B1~B4 |
| `self-hosted` | 우리가 운영하는 인프라까지만 간다 | B7 (채택), B5 |
| `third-party` | 외부 사업자 서버로 나간다 | 트랙 A(Naver), B6 |

`self-hosted`는 `none`이 아니다. Redis payload TTL과 로그 마스킹이 실제로 지켜지는지를 [ADR-010](adr/0010-checkup-document-ocr-path.md) §6의 네 조건으로 따로 증명한다.

### 처리량과 비용

같은 정확도를 내도 시연 부하를 못 받치면 채택할 수 없다. API 경로끼리 비교할 축이 없어서 추가했다.

- 동시 요청 1·4·16에서의 p50·p95 처리 시간과 큐 대기 시간
- 큐가 밀리기 시작하는 동시 요청 수 — `ai-worker` 컨테이너 `mem_limit: 4G` 기준
- 초당 처리 페이지 수와 워커 1대 기준 시간당 처리량
- 외부 API의 계약 rate limit과 초과 시 동작
- **문서 1건당 비용** — 외부 경로는 호출·이미지 토큰 단가, 자체 호스팅은 서버 상시 비용을 월 처리량으로 나눈 값
- 실패·재시도가 비용에 얹히는 배수

자체 호스팅은 호출당 과금이 0이지만 상시 비용이 있다. 두 과금 구조를 같은 단위(문서 1건당)로 환산해야 비교가 성립한다. 이 축의 수치가 없으면 "로컬 모델이 싸다"는 주장은 근거가 없다.

## 7. 로컬 기본 엔진 채택 게이트

초기 목표값은 첫 고정 평가 결과 뒤 조정하되 다음 조건을 모두 확인한다.

- 핵심 숫자 정확도가 Naver 기준선보다 2%p를 초과해 낮지 않다.
- 검사명·숫자·단위 연결 정확도 95% 이상을 목표로 한다.
- 표 구조 F1 0.90 이상을 목표로 한다.
- 사용자 검토·수정 단계와 직접 입력 대체 경로가 동작한다.
- 심각 오류 유형별 실패 사례와 방어 규칙을 문서화한다.
- **인식 결과에 근거 좌표가 실려 검토 화면이 원문의 해당 위치를 지목할 수 있다.** B6을 기각한 조건이므로 다른 후보에도 같게 적용한다.

여기까지는 실행 위치와 무관하다. 아래 두 항목은 위치마다 다르다.

**기기 실행(B1~B4)의 추가 게이트**

- 합의한 기준 기기의 Chromium에서 페이지당 p95 15초 이내를 목표로 한다.
- 모델 설치 후 OCR 실행 네트워크 요청이 0건이다.

**서버 실행(B7)의 추가 게이트**

- 동시 요청 4건에서 페이지당 p95 8초 이내를 목표로 한다. 사용자가 업로드하고 기다리는 시간이라 기기 실행보다 기준이 빡빡하다.
- 큐가 밀리기 시작하는 동시 요청 수를 측정해 기록한다. 목표값이 아니라 아는 것이 조건이다 — 모르면 시연에서 막힌다.
- 외부 네트워크 요청이 0건이다. Naver·B6 경로가 아닌 이상 문서가 우리 인프라를 벗어나지 않는다.
- [ADR-010](adr/0010-checkup-document-ocr-path.md) §6의 Redis payload 네 조건을 자동 테스트가 증명한다. 이건 목표값이 아니라 통과 필수 항목이다.

목표값 미달은 챌린지 실패가 아니다. 사용 가능한 문서 범위, 성능 병목과 다음 대체 전략을 결과로 남긴다. 다만 근거 좌표와 Redis 네 조건은 목표값이 아니라 게이트라서, 미달이면 그 경로를 켜지 않는다.

## 8. 프로젝트 일정과 의사결정 게이트

공식 일정과 배포 마감은 [로드맵](07_roadmap.md)을 따른다. OCR 챌린지는 제품 기능을 막지 않는 병렬 작업으로 운영하며, 각 주차 종료 시 계속·축소·중단을 판단한다.

| 기간 | 공통 | 트랙 A | 트랙 B | 종료 게이트 |
|---|---|---|---|---|
| 8/20~8/23 | 공통 계약, 합성 데이터 명세, 보안 경계 테스트 설계 | Naver 호출 최소 기술검증 | 현재 Tesseract 기준선 재현 | 같은 입력·출력 계약으로 두 엔진을 호출할 수 있음 |

## 10. 저장소 산출물 구조

구현을 시작할 때 다음 구조를 기준으로 하되 기존 코드 구조와 충돌하면 같은 책임을 유지하는 범위에서 경로만 조정한다.

```text
frontend/src/shared/ocr/
├─ contracts.ts
├─ engineRegistry.ts
├─ engines/
│  ├─ browserTesseractEngine.ts
│  ├─ paddleOcrEngine.ts
│  └─ naverCloudOcrEngine.ts
└─ workers/
   └─ localOcr.worker.ts

app/integrations/naver_ocr/
├─ client.py
├─ schemas.py
└─ redaction.py

benchmarks/ocr/
├─ README.md
├─ dataset_manifest.json
├─ ground_truth.schema.json
├─ synthetic/
├─ expected/
└─ runs/                 # 비민감 결과 요약만 Git 추적

scripts/
```

- 실제 문서와 비식별 여부를 증명할 수 없는 파일은 저장소에 넣지 않는다.
- 모델 바이너리는 Git에 직접 넣지 않고 버전, 라이선스, 다운로드 출처와 SHA-256 manifest를 보존한다.
- 원시 벤치마크 결과에 OCR 전문이 포함되면 로컬 비추적 디렉터리에 저장하고 집계 결과만 커밋한다.

## 11. 벤치마크 데이터 명세

### 11.1 v0.1 목표 규모

- 6개 이상의 건강검진표 레이아웃
- 총 120페이지 목표
- 조정용 40, 검증용 40, 최종 고정 평가용 40페이지
- 깨끗한 PDF 30, 스캔 30, 휴대폰 촬영 40, 고난도 변형 20페이지
- 각 레이아웃에 정상·경계·이상 수치, 소수점, 음수, 양성·음성, 복합 단위를 포함

120페이지를 준비하지 못해도 레이아웃과 난이도별 최소 5페이지 없이 전체 점수를 발표하지 않는다. 특정 병원 서식 하나의 반복 생성본만으로 모델 우위를 주장하지 않는다.

### 11.2 정답 스키마

```json
{
  "document_id": "synthetic-checkup-001",
  "page": 1,
  "fields": [
    {
      "field_id": "fasting_glucose",
      "label": "공복혈당",
      "value": "103",
      "unit": "mg/dL",
      "reference_range": "70-99",
      "judgement": "경계",
      "critical": true
    }
  ]
}
```

- 문자열 전문과 구조화 필드 정답을 분리한다.
- 숫자·소수점·부호·단위·양성/음성 필드는 `critical=true`로 표시한다.
- 최종 평가 세트의 critical 정답은 작성자 외 1인이 다시 대조한다.
- Naver 결과를 정답으로 복사하지 않는다.

### 11.3 입력 정규화

- 정확도 비교의 기본 입력은 같은 페이지를 같은 해상도·색상 규칙으로 rasterize한 이미지다.
- PDF 직접 입력처럼 엔진 고유 기능은 별도 보조 실험으로 기록한다.
- 회전·자르기·명암 보정은 공통 전처리와 엔진 전용 전처리를 구분해 결과에 표시한다.

## 12. 벤치마크 실행 절차

1. Git commit, 데이터셋 버전, 모델 버전·해시, 브라우저와 기기 사양을 기록한다.
2. 정확도 평가는 고정 입력마다 한 번 수행하고 원시 결과 해시를 보존한다.
3. 처리 시간은 대표 20페이지에서 cold 1회, warm 3회 측정한다.
4. 브라우저 후보는 DevTools network 또는 Playwright로 외부 요청을 기록한다.
5. warm 실행 사이에 문서 상태는 초기화하되 모델 캐시는 유지한다.
6. p50·p95, 최대 메모리, 실패·시간 초과·OOM 수를 계산한다.
7. 잘못된 critical 필드는 글자 오류와 별도로 전부 오류 목록에 남긴다.
8. 동일한 채점기 버전으로 Naver와 로컬 후보를 비교한다.

### 지표 계산 기준

- `CER = (치환 + 삭제 + 삽입) / 정답 문자 수`
- 핵심 숫자 정확도는 공백 정규화만 허용하고 소수점·부호 변경은 오답이다.
- 필드 연결 정확도는 검사명·값·단위가 모두 같은 행에 연결돼야 정답이다.
- 표 F1은 정답 셀과 예측 셀의 행·열·내용 매칭으로 계산한다.
- 실패·빈 결과·시간 초과는 해당 페이지 정확도 0점으로 포함하고 별도 실패율도 보고한다.

종합 순위만으로 채택하지 않는다. critical 정확도, 개인정보 경계와 사용자 검토 흐름은 다른 점수로 상쇄할 수 없는 필수 게이트다.

## 13. AI 도구 실행 규칙

AI 도구는 코드 생성과 실험 자동화를 도울 수 있지만 개인정보 문서와 채택 판단을 위임하지 않는다.

### 금지

- 실제 건강문서, 비식별 전 원본, Naver Secret을 프롬프트·첨부·외부 AI 도구에 제공
- ADR-008을 읽지 않은 상태에서 서버 저장·Redis queue·Object Storage를 편의상 추가
- golden fixture의 기대값을 모델 출력에 맞춰 자동 수정
- 한 작업에서 공통 계약, 두 엔진과 UI를 동시에 대규모 변경
- 테스트 실패를 삭제·skip하여 완료 처리

### 작업 단위

AI에는 위 작업 패키지 ID 하나만 전달한다. 요청에는 다음을 반드시 포함한다.

```text
작업 ID:
목표:
읽어야 할 문서와 코드:
수정 허용 경로:
수정 금지 경로:
데이터 경계:
입력 fixture:
기대 산출물:
필수 테스트 명령:
완료 조건:
결과 보고 형식:
```

### 권장 프롬프트 예시

```text
OCR-B-002를 수행한다.
먼저 docs/adr/0008-temporary-cloud-ocr-baseline.md와
docs/16_ocr_cloud_baseline_local_replacement_challenge.md를 읽는다.
합성 fixture만 사용하고 실제 문서나 외부 API로 전송하지 않는다.
frontend/src/shared/ocr 아래에 공통 OcrEngine 계약을 지키는 최소 후보를 만든다.
모델은 자체 호스팅 경로와 SHA-256 manifest를 사용하고 런타임 CDN 요청을 금지한다.
기존 Naver adapter와 UI는 수정하지 않는다.
계약 테스트, 네트워크 요청 0건 테스트, 실행 명령과 측정 결과를 보고한다.
```

### AI 결과 검토

- 담당자가 변경 파일과 네트워크 경계를 직접 검토한다.
- 정확도 결과는 구현자가 재실행하고 다른 팀원이 결과 파일을 교차 확인한다.
- 보안 경계 변경은 PM 또는 백엔드 담당의 교차 리뷰를 받는다.
- AI가 주장한 성능 수치는 저장된 실행 결과 없이 문서에 확정값으로 옮기지 않는다.

## 16. 챌린지 완료 조건

- ADR-008의 클라우드 예외와 비저장 경계가 코드와 테스트에서 확인된다.
- 합성·비식별 고정 데이터셋, 정답 스키마와 공통 채점기가 재현된다.
- Naver, 현재 브라우저 OCR과 로컬 후보 1개 이상을 같은 조건으로 비교한다.
- 사용자 검토 전 결과가 건강기록·차트에 반영되지 않는다.
- 로컬 후보의 외부 네트워크 요청, 성능, 메모리와 브라우저 지원 범위를 보고한다.
- 채택·제한적 사용·보류 중 하나를 근거와 함께 선택하고 기각 대안을 남긴다.
- 팀원이 문서의 명령만으로 대표 실험을 다시 실행할 수 있다.
- 발표 자료에는 최고 점수만이 아니라 개인정보 경계, 실패 사례와 최종 선택 이유를 포함한다.
