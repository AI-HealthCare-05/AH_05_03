# 34. 프로젝트 규칙과 공통 작업 절차

> 작성일: 2026-08-25
> 근거: 2026-08-25 멘토링 — "팀원마다 쓰는 AI 툴이 달라도 결과가 흔들리지 않도록 공통 플랜·검토·실행 절차와 프로젝트 규칙을 맞춰보기 (비결정성 이슈)"
> 선행 초안: [18_core_feature_gap_and_mentoring_action_plan](18_core_feature_gap_and_mentoring_action_plan.md) §8

이 문서는 취향을 정하지 않는다. **실제로 사고가 난 자리만** 규칙으로 만든다. 규칙이 많으면 아무도 안 읽고, 근거 없는 규칙은 지켜지지 않는다.

## 0. 오늘 실측한 사고 네 건 — 규칙의 근거

전부 2026-08-25 하루에 한 저장소에서 나왔다. 네 건 모두 **테스트도 리뷰도 통과할 수 있는 형태**였다는 게 요점이다.

| # | 사고 | 왜 안 잡혔나 |
|---|---|---|
| 1 | 같은 판단이 **네 곳에 복사**돼 있었다. 단조 제약 적용 조건이 `ensemble.py`·`export_ensemble.py` 에 각각 있어서, 한 곳을 고쳤는데 AUROC 가 소수 넷째 자리까지 똑같이 나왔다 | 바꾼 코드가 실행 경로에 없었다. 테스트는 통과한다 — 아무것도 안 바뀌었으니까 |
| 2 | **주석이 거짓말을 했다.** `export_multi.prepare()` 에 "이 타깃이 쓸 수 있는 것만 남긴다"는 주석이 붙은 줄이 `design_columns = list(frame.columns)`, 즉 아무것도 안 걸러내는 코드였다 | 주석을 읽으면 필터가 있다고 믿는다. 실행해도 결과가 그럴싸하다 |
| 3 | **유령 입력.** DTO 가 `veg_fruit_daily` 를 받는데 서빙 번들 20 개 어디에도 그 특징이 없었다. 켜고 끈 결과 차이가 0.0%p | 사용자가 답한 값이 조용히 버려진다. 예외도 경고도 없다 |
| 4 | **순수 계산 테스트가 DB 를 요구했다.** 상위 `conftest.py` 의 autouse 픽스처 때문에 참조표 조회 테스트가 PostgreSQL 없이는 112 개 error 로 죽었다 | 컨테이너가 꺼진 상태에서 안 돌면 아무도 안 돌린다 |

AI 도구가 만드는 코드의 특징이 그대로 보인다. **그럴싸한 이름, 그럴싸한 주석, 실행되지 않는 경로.** 사람이 쓴 코드는 보통 반대로 실패한다 — 이름이 엉성하고 동작은 한다.

그래서 이 문서의 검증 규칙은 "코드를 읽어서 판단한다"가 아니라 **"바꾼 것이 실제로 결과를 바꿨는지 숫자로 확인한다"** 쪽에 무게를 둔다.

## 1. 문서 채번

### 규칙

- 설계·조사 문서는 `docs/NN_snake_case_title.md`. `NN` 은 두 자리, 001 부터 순차.
- ADR 은 `docs/adr/000N-kebab-case-title.md`. 번호는 [adr/README.md](adr/README.md) 인덱스 표의 마지막 + 1.
- **새 문서를 만들기 전에 `git ls-tree --name-only origin/dev docs/` 로 원격 번호를 먼저 확인한다.** 로컬 브랜치만 보면 충돌한다.
- 번호를 비워 두지 않는다. 문서를 폐기할 때도 번호는 남기고 본문에 폐기 사유를 적는다.

### 왜

충돌이 실제로 났다. OCR 정렬 문서가 `17_ocr_implementation_alignment.md` 로 만들어졌는데 `dev` 의 17 번은 three.js 대시보드 문서였다. 24 번으로 옮겨서 해결했고, 그때까지 두 문서를 "17번"으로 인용한 곳이 여럿이었다.

ADR 쪽은 다른 사고였다. **인덱스가 없어서 ADR-004 가 `제안` 상태인 채로 다른 문서들이 확정처럼 인용했다.** 인덱스 표를 만들고 상태 칸을 판단 기준으로 명시했다.

## 2. 브랜치 규칙

### 현재 상태 — 접두어가 여섯 가지다

`origin` 의 브랜치를 세어 보면 이렇다.

| 접두어 | 개수 |
|---|---:|
| `feat/` | 5 |
| `agent/` | 3 |
| `feature/` | 2 |
| `fix/` · `docs/` · `chore/` | 각 1 |
| `issue-3-...` | 1 |

`feat/` 와 `feature/` 가 같은 뜻으로 섞여 있고, `agent/` 는 AI 도구가 자동으로 만든 것이며 `issue-3-...` 는 접두어가 없다.

### 규칙

- 접두어는 넷만 쓴다 — `feat/`, `fix/`, `docs/`, `chore/`. **`feature/` 는 쓰지 않는다** (`feat/` 로 통일).
- 이름은 `접두어/영역-요약` 형태. 예: `feat/ml-blood-pressure-direction`, `fix/ocr-relay-timeout`.
- AI 도구가 만든 `agent/*` 브랜치는 사람이 이름을 바꿔 PR 을 연다. 도구 이름이 브랜치에 남으면 나중에 누가 뭘 했는지 추적이 안 된다.
- **기준 브랜치는 항상 `dev`.** 다른 기능 브랜치 위에 얹지 않는다.
- 병합 금지 브랜치는 이 문서에 적는다. 현재 `feat/OCR_n_ai-worker` 는 **부분 병합 대상**이다 ([ADR-010](adr/0010-checkup-document-ocr-path.md) §3 이후 상태가 바뀌었다) — 통째로 병합하지 않고 살릴 파일만 옮긴다.

### 착수 전 확인 한 줄

```bash
git fetch origin && git rev-list --count origin/dev ^HEAD
```

`0` 이 아니면 내 브랜치에 `dev` 의 커밋이 빠져 있다. 그 상태로 계속 가면 나중에 충돌이 커진다.

## 3. 커밋 단위

### 현재 상태 — 이건 이미 일관된다

최근 40 커밋의 접두어를 세면 `feat:` 12(`feat(frontend):` 4, `feat(ml):`·`feat(local):`·`feat(api):` 각 1 포함), `fix:` 5, `docs:` 4, `chore:` 2. Conventional Commits 를 이미 지키고 있다.

### 규칙

- `타입(범위): 요약` 형태를 유지한다. 타입은 `feat`·`fix`·`docs`·`chore`·`refactor`·`test`.
- 범위는 실제 디렉터리에서 고른다 — `ml`, `api`, `frontend`, `ocr`, `local`, `infra`, `docs`.
- **한 커밋에 한 가지 변경.** 오늘처럼 "결함 수정 + 회귀 테스트 추가 + 문서 갱신"은 세 커밋이다. 되돌릴 때 하나만 되돌릴 수 있어야 한다.
- 재학습·재내보내기로 바뀐 모델 번들은 **별도 커밋**으로 낸다. 코드 변경과 섞으면 성능 차이의 원인이 코드인지 번들인지 못 가른다.
- 커밋 메시지에 측정값을 적는다. "혈압 방향 수정"보다 "임상 진행 경로 단조 위반 1건 → 0건, AUROC 0.8190 → 0.8173" 이 쓸모 있다.

## 4. 공통 작업 절차 — 여섯 단계

AI 도구가 Claude Code 든 Codex 든 Cursor 든, 이 순서를 공통으로 밟는다. 도구가 다른 건 문제가 아니고 **검증하는 방식이 다른 게 문제**다.

### 1단계 — 계약 확인

착수 전에 읽는다. 안 읽으면 이미 기각된 설계를 다시 제안한다.

- [01_requirements.md](01_requirements.md) 의 REQ·NFR
- [adr/README.md](adr/README.md) 인덱스 — **`제안` 상태를 확정으로 인용하지 않는다**
- 건드리는 영역의 짝 문서
- [TODO_멘토링_후속.md](../../TODO_멘토링_후속.md) §7 "하지 않기로 한 것"

### 2단계 — 공백 선언

"이번 작업이 채우는 칸"을 한 줄로 적는다. `사용자 입력 → 데이터 탐색·처리 → 출력 → 실패 처리` 중 어디인지. [32_core_feature_gap_matrix](32_core_feature_gap_matrix.md) 의 표에서 고르면 된다.

### 3단계 — 계획

변경 파일, 마이그레이션, 테스트, 되돌리는 방법을 적는다. **되돌리는 방법이 없으면 착수하지 않는다.**

### 4단계 — 작은 수직 흐름

화면·API·모델을 따로 끝내지 않는다. 하나의 사용자 흐름을 작게 완성한다. 세 개를 각각 80% 만들면 사용자에게 도달하는 것은 0 이다 — 32번 문서의 "점선 10개 중 7개가 두 묶음에 몰려 있다"가 그 상태다.

### 5단계 — 공통 검증

아래 §5 의 명령을 **같은 순서로** 돌린다.

### 6단계 — 증거 제출

PR 본문에 성공 경로만 적지 않는다. 아래 §6 체크리스트를 채운다.

## 5. 검증 명령 한 벌

CI(`.github/workflows/checks.yml`)가 돌리는 것과 같아야 한다. 로컬에서 통과하고 CI 에서 떨어지면 절차가 무의미해진다.

### 파이썬

```bash
cd project
uv sync --frozen            # lock 이 어긋나면 여기서 즉시 실패한다
uv run ruff check .         # 경로 필터 없음 — modeling/ 도 포함이다
uv run ruff format . --check
uv run mypy app
uv run python -m pytest app/tests/model -q     # DB 불필요. 항상 돌릴 수 있다
uv run python -m pytest app/tests -q           # PostgreSQL 필요 (docker compose up postgres)
uv run alembic check                            # 모델과 마이그레이션 드리프트
```

**`ruff check .` 에 경로 필터가 없다는 점이 중요하다.** 오늘 확인해 보니 `modeling/` 의 위반 15 건과 포맷 20 파일 때문에 **이 브랜치는 CI lint 에서 떨어지는 상태였다.** 정리해서 초록으로 만들었다. `modeling/` 이 실험 코드라고 예외가 아니다.

### 프론트엔드

```bash
cd project/frontend
npm ci && npm run lint && npm run typecheck && npm test && npm run build && npm run test:e2e
```

### 테스트를 두 갈래로 나눈 이유

`app/tests/model/` 은 **DB 를 붙이지 않는다.** 상위 `conftest.py` 의 `_override_session` 이 autouse 라서 참조표 조회처럼 I/O 가 없는 테스트까지 PostgreSQL 을 요구했고, 컨테이너가 꺼진 상태에서 표시 회귀 테스트가 무더기 error 가 됐다. 같은 이름 no-op 픽스처로 그 디렉터리에서만 껐다.

**모델 채점·참조표·등급 사상·중재 규칙은 여기 둔다.** 라우터·세션·인증이 끼면 상위로 옮긴다. 이 구분이 있으면 Docker 를 켜지 않고도 가장 중요한 회귀를 잡을 수 있다.

## 6. 리뷰 체크리스트 — 오늘 나온 실패 유형 그대로

PR 을 올리는 사람이 먼저 채운다. 리뷰어는 빈칸을 지적하는 것이 아니라 **빈칸을 근거로 반려**한다.

### 필수

- [ ] **바꾼 코드가 실행 경로에 있는가.** 같은 판단이 다른 파일에 복사돼 있지 않은지 `grep` 으로 확인했는가. (사고 1)
- [ ] **숫자가 실제로 바뀌었는가.** 성능·출력이 전과 소수점까지 같으면 아무것도 안 바뀐 것이다. "바뀔 것으로 예상된다"는 증거가 아니다. (사고 1)
- [ ] **주석이 코드와 맞는가.** 특히 "~만 남긴다", "~를 검증한다" 류의 주석은 실제로 그 일을 하는지 확인한다. (사고 2)
- [ ] **받는 입력이 전부 쓰이는가.** DTO·폼에 새 필드를 넣었으면 그 값이 결과를 바꾸는지 확인했는가. (사고 3)
- [ ] **추가한 테스트가 의존성 없이 도는가.** DB·네트워크가 필요하면 왜 필요한지 적었는가. (사고 4)
- [ ] 실패 경로를 확인했는가 — 오류, 재시도, 중복 요청, 권한, 타임아웃.
- [ ] 민감정보가 로그·APM payload 에 안 남는가.
- [ ] 되돌리는 방법을 적었는가.

### 모델·데이터 변경일 때 추가

- [ ] 라벨 누출 차단 집합이 그대로인가.
- [ ] 학습과 서빙이 같은 특징을 쓰는가. (`app/tests/model/test_serving_feature_parity.py` 가 자동으로 본다)
- [ ] 보정(ECE·기울기)을 판별력(AUROC)과 **함께** 적었는가.
- [ ] 방향 계약을 깨지 않는가. (`test_blood_pressure_direction.py`)
- [ ] 번들 크기 변화를 적었는가.

### AI 도구를 썼을 때 추가

- [ ] 도구가 "했다"고 말한 것과 저장소 실물을 대조했는가.
- [ ] 도구가 만든 브랜치·커밋 이름을 사람 규칙으로 바꿨는가.
- [ ] 도구가 인용한 문서 번호·파일 경로가 실제로 존재하는가.

마지막 항목이 실질적이다. **AI 가 생성한 설명을 구현 증거로 간주하지 않는다.** 판단 기준은 실행 가능한 테스트, 고정된 모델·데이터 버전, manifest·해시, 재현 명령이다.

## 7. 이 문서를 고쳐야 하는 조건

- 규칙이 지켜지지 않는 항목이 생긴다. 그러면 규칙을 강제하거나 지운다. 지켜지지 않는 규칙을 남기면 문서 전체의 신뢰가 떨어진다.
- 새 사고 유형이 나온다. §0 표에 한 줄 추가하고 §6 체크리스트에 대응 항목을 넣는다.
- CI 가 돌리는 명령이 바뀐다. §5 를 같이 고친다. **두 곳이 어긋나면 이 문서가 아니라 CI 가 정본이다.**
