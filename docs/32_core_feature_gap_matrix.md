# 32. 핵심 피처 공백 매트릭스 — 요구사항·API·저장·코드 4열 대조

> 작성일: 2026-08-25 · **갱신: 2026-08-25 오후**
> 근거: 2026-08-25 멘토링 — "화면을 더 만드는 것보다 사용자 input부터 데이터 탐색·처리·output까지 피쳐별 공백을 먼저 채우는 게 중요"
> 짝 문서: [18_core_feature_gap_and_mentoring_action_plan](18_core_feature_gap_and_mentoring_action_plan.md) (서술형 분석) · [ADR-009](adr/0009-per-disease-models-and-server-inference-path.md) · [ADR-010](adr/0010-checkup-document-ocr-path.md)

18번 문서가 세 축을 서술로 풀었다. 이 문서는 같은 대상을 저장소 실물과 한 칸씩 맞춰 **어디가 비었는지 판정만** 한다. 판정의 근거는 문서가 아니라 파일이다.

## 0. 세 줄

1. **화면은 있는데 화면이 없다.** 프론트엔드 라우트 8개 중 5개가 같은 `HomePage` 컴포넌트를 렌더한다. `members/:profileId/records`, `records/:recordId`, `family-history`는 URL만 있다.
2. **같은 판정이 두 곳에 있고 한쪽이 모의다.** 서버에는 규칙 엔진·ML·매트릭스가 실제로 돌고, 브라우저 워커는 `mockAssessmentEngine.ts` 26줄을 부른다. 정본이 어디인지 코드로는 알 수 없었고, ADR-009가 서버로 확정했다. **그날 오후에 중재자가 서버에 붙어 정본이 실물로 생겼다** — 이제 브라우저 모의 엔진은 죽은 경로다.
3. **세 축 중 하나는 파일이 0개다.** 챗봇·RAG는 `pyproject.toml`의 `ai` 그룹 선언(`torch`·`sentence-transformers`)만 있고 쓰는 코드가 없다.

### 열 밖에서 확인한 것

- 서버 라우터 10개가 `/api/v1`에 등록돼 있다 — `auth`, `account`, `subscription`, `households`, `family-invitations`, `profile-links`, `predictions`, `predictions/jobs`, `assessments/rules`, `assessments/summary`.

- 프론트엔드 features 디렉터리 5개 — `account`, `data`, `home`, `architecture`, `ui-preview`. 뒤 둘은 개발용이다.
- ~~`predictions`·`assessments` 라우터가 인증 없이 건강 수치를 받는다~~ → **해결됐다.** 네 라우터 전부 `require_active_account` + 계정별 고정창 레이트리밋을 통과한다. ADR-009 §10 이 건 공개 선행조건이 채워졌다. 로그·APM 마스킹은 아직 남았다.

## 3. 세 축을 input → 처리 → output으로 세로로 파본 결과

멘토가 물은 형태로 다시 세운다. 표의 가로줄이 하나라도 끊기면 그 피처는 사용자에게 도달하지 않는다.

### 축 A — 만성질환 위험 판정

| 단계 | 있어야 하는 것 | 실물 | 판정 |
|---|---|---|---|
| 사용자 input | 나이·성별·키·몸무게·주관적 건강 + 선택 문항 + 검사값 입력 화면 | `frontend/src/features/assessment/` — 36필드 7그룹, 선언형 스펙 | **이어짐** |
| 입력 검증 | 타입·범위·단위·누락, 출처(직접/OCR) 기록 | `AssessmentSummaryRequest` 가 36필드 범위 검증 + 두 엔진 이름 사상. **출처 기록만 없다** | 부분 |
| 데이터 탐색 | 어떤 값이 있으면 어떤 엔진이 답하는지 판단 | `app/services/assessment.py`. 3단계 우선순위, 계약 테스트 23건 | **이어짐** |
| 처리 | 규칙 엔진·ML·공식 실행 | 규칙 10영역 · ML 20번들 · E3 공식(eGFR·HSI·대사증후군 5요소) | **이어짐** |
| output | 질환별 등급·근거·비진단 문구 화면 | `/assessment` 라우트. 등급·엔진 근거·밀려난 확률·정확도·매트릭스 축 | **이어짐** |
| 저장 | 확정 결과를 로컬 보관함에 | `recordType: "assessment"` 스냅샷. 입력값·등급·정본 엔진을 함께 남긴다 | **이어짐** |
| 실패 | 입력 부족·모델 로딩 실패·타임아웃 | 번들 미적재면 규칙·공식만으로 답하고 `model_available: false` 를 싣는다 | 부분 |

**축 A 가 입구에서 출구까지 뚫렸다.** 2026-08-25 오후에 `frontend/src/features/assessment/` 가 붙어 마지막 두 끊김(입력 화면·결과 화면)이 이어졌다. 화면은 등급만 띄우지 않고 **어느 엔진이 왜 답했는지**(`engine_reason`), **무엇에 밀렸는지**(`superseded_by`), **밀려난 확률과 그 정확도**(경보 적중률·발견율)를 함께 그린다 — 검사값을 넣었을 때 숫자가 왜 바뀌었는지 사용자가 읽을 수 있어야 하기 때문이다.

남은 부분은 하나다. 입력 화면이 **직접 입력만** 받는다 — 검진결과지 업로드는 축 B, 일일 체크는 챌린지 대기다.

시점별 누적과 차트는 같은 날 붙었다. 판정 결과를 `recordType: "assessment"` 스냅샷으로 로컬 보관함에 남기고, 두 시점 이상이 모이면 수치 시계열·등급 궤적·정본 엔진이 바뀐 시점을 그린다. **등급까지 같이 남기는 이유는 재채점하면 값이 달라지기 때문이다** — 번들은 재학습으로 갱신되고 임계값도 지침 개정으로 바뀐다. 추적은 그날 사용자가 본 것을 이어야 뜻이 있다.

여기서 걸린 것 하나를 적어 둔다. **로컬 건강기록의 payload 가 지금 메모 문자열뿐이다** (`CreateHealthRecordInput.note`). 그래서 기존 혈압·혈당 기록으로는 시계열을 그릴 수 없고, 판정 스냅샷이라는 별도 레코드 종류를 세워야 했다. 건강기록 일반의 구조화 payload 는 아직 남은 일이다.

같은 사람에게 검진결과지 한 장을 얹으면 무엇이 바뀌는지가 계약 테스트에 고정돼 있다 (`test_labs_actually_change_who_answers`).

| | 판정된 칸 | 정본 엔진 분포 | 최고 등급 |
|---|---|---|---|
| 필수 5개만 | 8 / 13 | E2 7 · E1 1 | HIGH (비만) |
| 검진결과지 한 장 | **13 / 13** | E1 7 · E2 3 · E3 3 | VERY_HIGH (대사증후군 5/5) |

### 단서 — `/api/demo` 는 이미 동작한다

**축 A 의 `input`·`output` 을 `끊김` 으로 판정하면서 빠뜨린 것이 있다.** `app/apis/demo_routers.py` 가 **934줄**이고 `app/main.py` 가 등록한다. `GET /api/demo` 가 HTTP 200 · 65 KB 를 낸다. 안에는 수치 프로필 7개 그룹 입력 폼(기본·혈압·혈당·지질·간신장혈액·생활습관·진단이력), 두 엔진 결과 카드, **수치→질환 매트릭스**, 로그인 처리가 다 들어 있다.

판정을 뒤집지는 않는다 — 이것은 **제품 SPA 가 아니라 서버 렌더 데모**라서 사용자 경로가 아니다. 다만 §5 의 `A3`(입력 화면)·`A4`(결과 화면)를 **신규 구축이 아니라 이식**으로 다시 잡아야 한다. 934줄에 담긴 입력 검증·단위 표기·카드 배치·문구가 이미 한 번 결정된 것들이다. 자세한 판정은 [36번 문서](36_feature_scope_vs_talos_requirements.md) §7-1 B.

가장 값진 칸은 빈혈이다. ML 은 혈색소를 입력에서 차단당해(라벨 누출) 확률 3.3%·의학등급 `낮음` 을 낸다. 그런데 같은 요청의 혈색소 12.1 g/dL 은 WHO 남성 기준(13.0) 미만이라 규칙 엔진이 `CAUTION` 을 낸다. **답을 확정하는 값을 넣었는데 화면이 안심시키는 것** — `risk.py` 의 `judge()` 독스트링이 "선별 제품에서 가장 비싼 종류의 오류"라고 적어 둔 그 상황이고, 중재가 붙기 전까지 실제로 그렇게 동작했다.

### 축 B — 건강문서 OCR·구조화

**브랜치를 구분해야 한다.** 아래 `실물` 칸은 이 작업 브랜치(`feat/ML_enhance`) 기준이다. 괄호 안이 `feat/OCR_n_ai-worker` 에 있는 것.

| 단계 | 있어야 하는 것 | 실물 (이 브랜치) | 판정 |
|---|---|---|---|
| 사용자 input | 파일 선택, 형식·크기 검사, 엔진 선택 | `/data` 화면에 파일 선택 있음 | 부분 |
| 처리 | 인식 → 표 행 조립 → 항목 사전 매칭 | `browserOcrAdapter.ts` 전체 페이지 → 평문뿐 (서버 인식기는 타 브랜치) | **끊김** |
| 데이터 탐색 | 검사명·값·단위·기준범위 연결 | **없음.** `app/services/ocr/` 에 `__pycache__` 만 남아 있고 `.py` 는 추적 파일 0건 (`lexicon.py` 252줄·`extractor.py` 206줄은 타 브랜치) | **끊김** |
| 검증 | 위험 변환 오류(`120→170`, `mg/dL→mmol/L`) 검사 | 없음 (어느 브랜치에도 없음) | **끊김** |
| output | 원문과 추출 필드를 나란히 놓는 검토·수정 화면 | 없음 | **끊김** |
| 저장 | 확정값만 로컬 보관함에 | `localDocumentService.ts` 있음, 확정 흐름 미연결 | 부분 |
| 큐·워커 | Redis 작업 큐 + 소비자 | **돈다.** `app/core/jobs/` 신설, `ai_worker/consumer.py` 194줄, 워커 3대. 다만 지금 흐르는 것은 **예측**이고 OCR 작업은 아직 없다 | 부분 |
| 비교 근거 | 채점 데이터셋 | **0건** | **끊김** |

**부품은 있지만 이 브랜치에는 하나도 없다.** 인식기·사전·행 조립기·큐·소비자가 전부 `feat/OCR_n_ai-worker` 에 있고, 이 브랜치에는 브라우저 평문 어댑터와 루트의 Naver spike 두 개뿐이다. `ai-worker` 컨테이너는 이름만 있다 — CMD 가 `echo 'hello world'` 이고 `restart: always` 라서, 프로파일을 켜면 무한 재시작한다.

그래서 축 B 의 첫 작업은 구현이 아니라 **이식**이다. ADR-010 이 그 브랜치를 `병합 금지` 에서 `부분 병합 대상` 으로 바꾼 이유가 여기 있다.

### 축 C — 개인 이력 챗봇·RAG

| 단계 | 있어야 하는 것 | 실물 | 판정 |
|---|---|---|---|
| 사용자 input | 질문 입력, 잘못된 값 정제("혈당 500") | 없음 | 없음 |
| 데이터 탐색 | 구성원·기간·기록 종류를 특정하는 질의 정제 | 없음 | 없음 |
| 검색 | 구조화 수치는 범위 조회, 의학 지식은 벡터 검색 | 없음 | 없음 |
| 기억 | 현재 턴 / 대화 요약 / 건강기록 / 전송 문맥 4계층 분리 | 없음 | 없음 |
| 처리 | 생성 모델 실행 위치 | 미결정 | 없음 |
| output | 근거 기록·날짜·불확실성 표시, 근거 없을 때 답변 제한 | 없음 | 없음 |
| 선제 알림 | 트리거 조건과 실행 주체 | 없음 | 없음 |

**이 축은 공백을 채우는 문제가 아니라 시작하는 문제다.** 배포까지 3주이고 로드맵 Sprint 4~5에 챗봇 항목이 없다. 담당자도 정해지지 않았다.

## 4. 지금 당장 막고 있는 것 넷

1. **판정 결과를 보여주는 화면이 없다.** 축 A의 모델 작업 전부가 사용자에게 도달하지 않는다. 매트릭스 6번(차트)과 9번(결과 화면)이 같은 뿌리다. **중재자가 붙으면서 이 항목의 무게가 커졌다** — 서버가 내는 정보가 확률 10개에서 근거 붙은 판정 13칸으로 늘었는데 받을 화면이 그대로다.
2. ~~**엔진 중재의 정본이 화면 스크립트에 있다.**~~ → **해결됐다.** `app/services/assessment.py` + `POST /assessments/summary`. 남은 것은 데모 화면의 `mockAssessmentEngine.ts` 처분이다(아래 §6-5).
3. **OCR 자산이 병합 안 된 브랜치에 갇혀 있다.** 이식 없이는 축 B 의 어떤 칸도 못 채운다. 다만 큐·워커 배선이 예측으로 먼저 증명돼서 **이식 범위가 인식기로 좁아졌다.**
4. **채점 데이터셋 0건.** ADR-010의 세 경로 비교표가 숫자로 채워지지 않는다.
5. **챗봇 축의 담당자와 요구사항 항목이 둘 다 없다.** REQ 번호가 없으니 완료 조건도 없다.

### 도커 스택 실물 — 기본 기동은 4종이다

`docker-compose.yml` 에 7개 서비스가 있지만 프로파일 없이 뜨는 것은 넷이다.

| 서비스 | 프로파일 | 상태 |
|---|---|---|
| `nginx` :80 | 없음 (기본) | `/api/` 와 `/` 를 모두 `fastapi:8000` 으로 넘긴다. **SPA 는 nginx 가 아니라 FastAPI 가 서빙한다** (`spa.mount`). `static_volume` 을 마운트하는데 conf 가 쓰지 않는다 — 잔재 |
| `fastapi` :8000 | 없음 (기본) | 기동 시 `alembic upgrade head`. 모델 번들을 `modeling/artifacts/models → /app/models:ro` 로 마운트하므로 **재학습해도 이미지 재빌드가 없다.** 규칙 엔진도 ro 마운트 |
| `postgres` :5432 | 없음 (기본) | 9 테이블. 건강정보 없음 |
| `redis` :6379 | 없음 (기본) | 세 역할 — 토큰, 레이트리밋 카운터, 예측 작업 큐. 건강 수치가 통과하므로 **지속화를 껐다** |
| `ai-worker` | `ai` | **돈다.** `consumer.py` 194줄, `--scale ai-worker=3`. 30건 → 11·10·9 분산, 재시도 0 |
| `email-worker` | `mail` | 초대 메일 워커. 건강정보 아님 |
| `mailpit` | `mail` | 로컬 SMTP 수신함. 운영 배포 제외 |

멘토가 말한 `nginx → FastAPI → DB → Redis → ai-worker` **다섯이 이제 다 떠 있다.** 이 문서를 처음 쓸 때 비어 있던 마지막 하나가 그날 오후에 채워졌다 — 다만 흐르는 것은 예측이고 OCR 은 아직이다. 자세한 실측은 [35번 문서](35_prediction_queue_and_workers.md).
