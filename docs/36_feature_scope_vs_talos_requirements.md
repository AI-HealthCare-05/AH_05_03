# 36. 핵심 기능 정리와 추천 — Talos 필수 기능 대비 실물

> 작성일: 2026-08-25
> 근거: [참여기업 주제 안내 (세부평가 기준 포함)](../../docs/참여기업_주제_안내_세부평가기준포함.md) §1-3 Talos 필수 구현 기능, §3 평가 항목 20개
> 짝 문서: [32 공백 매트릭스](32_core_feature_gap_matrix.md) (파일 단위 판정) · [33 흐름도](33_core_feature_flowchart.md) §1 기능 지도 · [06 평가기준 대응 계획](06_evaluation_plan.md)
> 판정 기준일: 배포 마감 **2026-09-14** (남은 기간 3주)

32번이 "코드가 있나"를 판정했다면 이 문서는 **"채점표에 있는 칸을 채웠나"** 를 판정한다. 둘은 다른 질문이고, 답도 다르게 나왔다.

## 0. 세 줄

1. **Talos 필수 기능 3개 중 2개가 코드 0줄이다.** 만성질환 추적 대시보드와 생활습관 챌린지다. 채점 기준상 0점 칸이다.
2. **로드맵이 그 둘을 아예 다루지 않는다.** `07_roadmap.md` Sprint 4~5 어디에도 챌린지·대시보드 항목이 없다. 요구사항(REQ-01~15)에도 없다 — 요구사항서가 다른 제품(이어봄)을 기준으로 쓰였기 때문이다.
3. **반대로 평가 항목 쪽은 실물이 문서보다 앞서 있다.** `06_evaluation_plan.md` 20항목 중 19개가 `계획됨`인데, 실제로는 최소 5개가 정량 근거까지 확보된 상태다. 표만 갱신하면 점수가 오르는 자리다.

## 1. 우리가 지금 가진 핵심 기능

먼저 있는 것부터 정확히 적는다. 없는 것 이야기는 그다음이다.

### 1-1. 만성질환 위험 판정 — 이 제품의 심장

| 구성 | 실물 | 규모 |
|---|---|---|
| **E1 규칙 엔진** | 국내 학회 임계값으로 영역 판정 | 10영역. 벤더 엔진 4 + `lab_staging.py` 6 |
| **E2 ML 시드 앙상블** | 질환별 독립 모델. XGBoost 3시드 + CatBoost 3시드 | 번들 20개 = 10질환 × 일반형·정밀형 |
| **E3 공개 공식** | eGFR(CKD-EPI 2021) · HSI · 대사증후군 5요소 카운트 | 3종 |
| **엔진 중재자** | 질환마다 누가 정본인지 결정 | `assessment.py`. 질환 13칸, 계약 테스트 23건 |
| **수치→질환 매트릭스** | 영역 판정의 전치 — 수치 하나가 여러 질환에 걸쳐 뭐를 가리키나 | 질환 축 4개 |

경쟁 서비스와 갈리는 지점이 셋이다.

- **어느 엔진이 왜 답했는지가 응답에 실린다.** `engine` · `engine_reason` · `superseded_by`. "확률 47%" 만 던지는 서비스와 여기서 갈린다.
- **잰 값이 안 잰 값을 이긴다.** 검사값을 넣으면 정본이 규칙 엔진으로 넘어간다. 확률은 지우지 않고 참고로 내려간다.
- **모르는 걸 모른다고 한다.** 재료가 없으면 `INSUFFICIENT_DATA` 와 함께 **무엇을 넣어야 답이 나오는지**를 적는다. 대사증후군은 부분 입력으로도 확정·배제가 가능한 경우를 갈라낸다.

### 1-2. 서버 인프라 — 평가 항목에 직접 걸리는 자산

| 구성 | 실물 | 걸리는 평가 항목 |
|---|---|---|
| 예측 작업 큐 + 워커 3대 | Redis Streams, 소비자그룹, `XAUTOCLAIM` 회수, 재시도 상한 | 3-2 · 5-5 |
| 동기·비동기 결과 동일성 | 12,410 B 바이트 단위 일치 | 3-3 |
| 인증 + 계정별 레이트리밋 | JWT + 고정창 제한, 4개 라우터 | 5-4 |
| 무저장 계약 | 건강 수치가 DB·로그·Redis 지속화 어디에도 안 남는다. 테스트 12건이 증명 | 2-3 · 5-4 |
| 응답 지연 | 동기 왕복 26~29 ms (기준 3초) | 5-1 |

### 1-3. 건강문서 OCR — 투자했지만 Talos 필수 목록에는 없다

정직하게 적어야 하는 부분이다. OCR·구조화는 **Uponati 트랙의 필수 기능**이고 Talos 필수 3개에는 들어 있지 않다. 우리 팀은 Talos 트랙이다(`06_evaluation_plan.md` 머리말).

버리자는 말이 아니다. 공통 평가 항목 2-1(기술 스택 선정 근거)·2-3(아키텍처)·3-2(비동기)에 재료로 쓰이고, [ADR-010](adr/0010-checkup-document-ocr-path.md)의 후보 비교표는 "비교해서 골랐다"는 근거가 된다. 다만 **필수 칸을 채우지는 않으므로 필수 두 칸보다 뒤에 놓아야 한다.**

### 1-4. 계정·가족 도메인

계정·구독·가정·초대·프로필 연결이 서버에서 돌고 화면도 있다. 14기능 중 input→output이 닫힌 유일한 축이다. 다만 이것도 Talos 필수 목록에는 없다.

## 2. Talos 필수·선택 대비 판정

| 필수 | 기능 | 요구 내용 | 우리 실물 | 판정 |
|---|---|---|---|---|
| **필수** | 만성질환 예측 모델링 | 공개 데이터셋으로 발병 가능성 예측 모델 구축 | 10질환 × 2tier, 번들 20개, 홀드아웃 AUROC 기록 | **강함** |
| **필수** | 만성질환 추적 대시보드 | 건강 데이터 시각화 + 예측 기반 **변화 추이** + 그래프·차트 | `TrendChart.tsx` — 판정 스냅샷의 수치 시계열 · 등급 궤적 · 정본 엔진 변경 시점 | **채워짐** (아래 단서) |
| **필수** | 생활습관 챌린지 | 걸음·물·운동 등 자유 구현 | 요구사항·API·ERD·코드 전부 없음 | **0점 칸** |
| 선택 | LLM 기반 예방 행동 추천 | 건강·행동 데이터로 매일 행동 추천 | 없음. 재료(판정 결과·권고 문구)는 있다 | 미착수 |
| 선택 | 이미지 분류 기반 식단 분석 | 식단 사진 분류 + 부족 영양소 | 없음. 새 데이터셋·새 모델이 필요 | 미착수 |
| 선택 | 알림 기능 | 입력 알림 · 챌린지 체크 알림 | 없음. 트리거 재료는 있다 | 미착수 |

**남은 0점 칸은 생활습관 챌린지 하나다.** 추적 대시보드는 2026-08-25 오후에 채웠다. 다만 로드맵은 그대로다 — `07_roadmap.md` Sprint 4~5(8/31~9/13)는 초대 수락·프로필 병합·WebRTC 기술검증으로 채워져 있고 전부 이어봄 요구사항이다.

### 대시보드에 붙은 단서 둘

**하나 — 확률선을 그리지 않았다.** Talos 문구는 "**발병** 가능성의 변화율"인데 우리 라벨은 단면이라 발병이 아니다. 그래서 확률 곡선 대신 **입력한 수치 자체**와 **등급의 변화**를 겹쳤다. 감추는 것보다 정확한 것을 그리는 편이 채점 기준(정량 근거)에도 맞다.

**둘 — 로컬 건강기록의 payload 가 메모 문자열뿐이었다.** `CreateHealthRecordInput` 이 `note` 만 받아서 기존 혈압·혈당 기록으로는 시계열을 그릴 수 없었다. 그래서 판정 스냅샷(`recordType: "assessment"`)이라는 별도 레코드를 세웠다. **건강기록 일반의 구조화 payload 는 아직 남은 일**이고, 그게 붙으면 REQ-05 의 "구성원별 수치 변화 차트"가 판정과 무관하게도 그려진다.

### 왜 이렇게 됐나

요구사항서(`01_requirements.md`)가 **이어봄**(가족 건강기록 로컬 우선)을 정의한다. REQ-01~15 어디에도 챌린지·대시보드·알림이 없다. 반면 평가 계획서는 **Talos 트랙**을 대상으로 쓰였다. 두 문서가 서로 다른 제품을 가리키고 있고, 이 불일치는 [TODO §6](../../TODO_멘토링_후속.md)에 "9/14에 배포하는 제품이 이어봄인가 정상수치 원정대인가"로 이미 올라와 있다. **이 판정표가 그 질문의 비용을 숫자로 보여준다.**

## 3. 평가 항목 20개 — 표가 실물보다 낡았다

`06_evaluation_plan.md` 는 20항목 중 19개를 `계획됨`으로 두고 있다. 아래는 실제로 근거가 확보된 것들이다. **공통 채점 기준의 5점이 "정량적 근거·문서·테스트 결과가 명확하게 제시된 경우"인데, 근거는 있고 표에 반영이 안 돼 있다.**

| 항목 | 표의 상태 | 실물 | 근거 |
|---|---|---|---|
| 3-2 비동기로 추론 성능 개선 | 계획됨 | **개선 수치까지 있다** — 요청당 계산 27.75 → 21.57 ms(−22.3%), nginx 왕복 46~48 → 26~29 ms(−43%) | [35번](35_prediction_queue_and_workers.md) §7 |
| 3-3 동일 입력 결과 편차 최소화 | 계획됨 | **시드 앙상블 채택 근거가 정확히 이것.** 30건 재현 결과 종류 1개, 동기·비동기 12,410 B 일치 | [29번](29_seed_ensemble_model_comparison.md) · 35번 §7 |
| 5-1 P95 < 3초 | 계획됨 | 동기 왕복 26~29 ms | 35번 §7 |
| 5-4 인증·인가 | 계획됨 | JWT + `require_active_account` + 계정별 레이트리밋, 4개 라우터 | `app/apis/v1/*` |
| 5-5 비동기 응답 속도·자원 효율 | 계획됨 | 워커 3대, 30건 1.90 s, 재시도 0, `XAUTOCLAIM` 회수 | 35번 §4·§7 |
| 3-1 지속적 모델 성능 검증 | 계획됨 | 지표 2종 이상 + 실험 비교가 문서 19·22·27·28·29번에 걸쳐 있다. **MLflow 는 없다** | — |

그리고 표의 "우리 팀 대응" 칸 자체가 낡은 것이 둘 있다. 3-2 와 5-5 가 "**로컬** OCR·예측을 UI 스레드와 분리"라고 적혀 있는데, ADR-009·010이 서버 추론으로 뒤집었다.

**남은 진짜 공백은 3-4다.** "사용자 피드백 반영 구조 — 수집→저장→개선/재학습까지 구현". 무저장 정책과 정면으로 걸리고, 아직 답이 없다.

## 4. 추천 — 무엇을 더 만들 것인가

3주 남았고 필수 두 칸이 비어 있다. 우선순위는 그 사실이 정한다.

### 1순위 — 필수 칸 두 개 (선택의 여지 없음)

> **A 는 2026-08-25 오후에 완료됐다.** 아래 설계 판단이 그대로 구현됐고, 구현하면서 나온 것 둘은 §2 "대시보드에 붙은 단서"에 적었다. B 챌린지는 여전히 비어 있다.

**A. 추적 대시보드.** 재료가 이미 다 있다. 필요한 것은 ① 시점별 저장 호출부, ② 차트 컴포넌트, ③ 두 시점 비교 화면.

정직하게 처리할 지점이 하나 있다. Talos 문구는 "**발병** 가능성의 변화율"인데 우리 라벨은 단면(prevalent)이라 발병이 아니라 **"지금 재면 기준을 넘을 가능성"** 이다. 감추지 말고 축 이름과 문구를 그대로 쓰는 편이 낫다 — 이미 `disclaimers` 에 그렇게 적혀 나가고 있고, 채점 기준 5점이 요구하는 것도 화려한 주장이 아니라 명확한 근거다. 대신 변화 추이는 세 가지를 겹쳐 그릴 수 있다.

- 입력한 수치 자체의 시계열 (혈압·혈당·체중) — 이건 논란의 여지가 없다
- 질환별 **등급**의 시계열 (NORMAL → CAUTION → HIGH)
- 정본 엔진이 바뀐 시점 표시 (검사값을 넣은 날)

**B. 생활습관 챌린지.** 유일하게 재료가 없는 필수 칸이라 가장 먼저 착수해야 한다. 최소 형태는 챌린지 정의 · 일일 체크 · 달성률 셋이다.

먼저 정할 것이 하나 있다. **일일 체크 기록이 NFR-01의 "건강정보"에 해당하는가.** 답에 따라 저장 위치가 서버 DB냐 로컬 보관함이냐로 갈리고, 건너뛰면 마이그레이션을 두 번 만든다. 걸음 수·물 섭취는 검진 수치와 성격이 다르므로 서버 저장이 합리적이라고 보지만, 이건 팀 결정이다.

**⚠ 챌린지 항목을 ML 기여도(`top_factors`)로 고르지 않는다.** 단면 데이터에서 금연·절주가 당뇨 위험을 **올리는** 방향으로 나온다 — 이미 아픈 사람이 끊기 때문이다. 챌린지 항목은 학회 권고에서 가져오고, 기여도는 설명 재료로만 쓴다.

### 2순위 — 우리 자산이라 싸게 되고 차별점이 되는 것

**C. "무엇을 더 넣으면 답이 나오나" 안내.** 중재자가 이미 `missing_fields` 를 칸마다 낸다. 이걸 "지금 8칸 판정됨 / 크레아티닌을 넣으면 만성콩팥병이 열립니다" 같은 진행형 안내로 바꾸면 **입력을 유도하는 장치**가 된다. 새 모델도 새 데이터도 필요 없다. 평가 항목 4-1·4-3(화면 흐름·3~5회 접근)에 직결된다.

**D. 판정 근거 표시.** `engine_reason` · `superseded_by` · `reference` 가 이미 응답에 실려 나가는데 읽는 화면이 없다. "혈압을 재셨기 때문에 규칙 엔진이 답했습니다. ML 추정치 46%는 참고로 내려갔습니다" 를 그대로 보여주면 3-1(검증)과 UI/UX 항목을 동시에 먹는다. 이만한 설명력을 가진 헬스케어 데모는 흔하지 않다.

**E. 재측정·미입력 알림 (Talos 선택).** 트리거 재료가 이미 있다 — `INSUFFICIENT_DATA` 칸, `needs_attention` 목록, 마지막 입력 이후 경과일. 다만 **서버가 건강정보를 모른다**는 제약과 정면으로 걸리므로(ADR-002 §4) "무엇을 알아야 알림을 보낼 수 있는가"를 먼저 적어야 한다. 가장 싼 형태는 서버가 날짜만 알고 내용은 모르는 재측정 리마인더다.

### 3순위 — 축 C가 살아나면

**F. LLM 기반 예방 행동 추천 (Talos 선택).** 판정 결과·권고 문구·부족 항목이 이미 구조화돼 있어 프롬프트 재료가 갖춰져 있다. 챗봇 축(문서 32 축 C)과 같은 배선을 쓰고, 큐·워커도 이미 서 있다. 다만 축 C는 담당자도 REQ 번호도 없는 상태라 그 결정이 선행이다.

### 추천하지 않는 것

**이미지 분류 기반 식단 분석 (Talos 선택).** 새 데이터셋·새 모델·새 라벨 체계가 필요하고 3주에 들어가지 않는다. 게다가 OCR 축과 같은 사람·같은 시간을 두고 경쟁한다. 필수 두 칸이 빈 상태에서 선택 항목에 모델 하나를 더 세우는 건 순서가 뒤집힌 것이다.

**의료 영상(X-ray·CT) 분류.** [ADR-010 §1](adr/0010-checkup-document-ocr-path.md)이 이미 기각했다. 데이터셋·라벨·평가 방법·규제 위험·사용자 출력이 전부 다르다.

**모델 성능을 더 올리기.** [TODO §7](../../TODO_멘토링_후속.md)에 근거가 있다 — 표본을 두 배로 늘렸을 때 AUROC가 0.002 움직였다. 천장은 표본이 아니라 정보량이고, 지금 점수를 올리는 건 모델이 아니라 **판정을 화면에 도달시키는 일**이다.

## 6. 2026-08-25 — 핵심 기능 넷으로 좁혔다

팀이 핵심 기능을 넷으로 정했다. 배선도는 [33번 문서](33_core_feature_flowchart.md) §1 "목표 배선도" 에 있다.

| | 기능 | 4장 대비 위치 | 지금 상태 |
|---|---|---|---|
| ① | 만성질환 예측 | Talos **필수** — 이미 강함 | 서버 경로 완성. 화면 없음 |
| ② | LLM API 로 문서 이미지 분석·정리 | Talos 필수 아님 (Uponati 쪽) | **ADR-010 §2 를 뒤집는다** — 아래 참조 |
| ③ | 챗봇으로 질환·증상 요약 | Talos 필수 아님 (선택 LLM 추천에 가까움) | 파일 0개 |
| ④ | 예측에 따른 챌린지 자동 생성 | Talos **필수** | 파일 0개 |

**넷은 병렬이 아니라 사슬이다.** ②가 ①의 입력을 만들고 ③·④가 ①의 출력을 쓴다. 이 순서가 그대로 착수 순서는 아니다 — ①이 이미 서 있으므로 **④부터 시작하는 것이 맞다.** ④는 필수 칸이고 ①의 출력만 있으면 되는데 그 출력이 이미 나온다.

### 넷에서 빠진 것 둘을 더할 것을 권한다

**⑤ 추적 대시보드 — 넣어야 한다.** Talos 필수 셋 중 하나인데 넷에 없다. 빠지면 채점표에 0점 칸이 그대로 남는다. §2 표 참조.

**⑥ 부족 항목 안내 — 거의 공짜다.** 중재자가 칸마다 `missing_fields` 를 이미 낸다. "지금 8칸 판정됨 / 크레아티닌을 넣으면 만성콩팥병이 열립니다" 로 바꾸면 입력을 유도하는 장치가 되고, 평가 항목 4-1·4-3 에 직결된다. 새 모델도 새 데이터도 필요 없다.

### ②가 건드리는 결정 — 좌표를 잃는다

"LLM API 로 문서 이미지 분석" 은 [ADR-010](adr/0010-checkup-document-ocr-path.md) §2 가 **기본 엔진에서 기각한 경로**다. 기각 근거 셋 중 결정타를 그대로 옮긴다.

> 우리 제품은 인식 결과를 자동 확정하지 않는다. 사용자가 검토하고 고쳐서 확정한 값만 기록이 된다(ADR-008). 그 검토 화면이 성립하려면 "이 숫자가 원본 이미지의 어디에서 나왔는지"를 알아야 한다. OCR은 bounding box를 준다. 멀티모달 직송은 JSON만 주고 좌표를 주지 않는다. **검사 항목이 30개인 결과지에서 하나가 틀렸을 때, 사용자가 그것을 찾을 방법이 사라진다.**

바꾸는 것 자체는 팀의 권한이다. 다만 **두 가지가 선행**한다.

1. ADR-010 §2 를 대체하는 후속 ADR. 좌표 없이 검토·수정 화면을 어떻게 성립시킬지가 그 결정문의 본문이 된다.
2. 외부 멀티모달 API 사용 근거. ADR-008 은 Naver CLOVA 를 **콕 집어** 허용했지 일반 외부 LLM API 를 다루지 않는다. 같은 형식의 예외 ADR 이 필요하다.

**대안이 하나 있고, ADR-010 이 이미 "가장 유망한 후속안" 으로 적어 뒀다.**

> OCR 먼저 돌리고 저신뢰 항목만 VLM으로 재확인하는 하이브리드 — 근거 좌표는 OCR이 이미 갖고 있고 VLM은 판독이 어려운 셀에만 호출하므로 비용도 통제된다.

이 구성이면 "LLM API 로 문서 이미지 분석·정리" 라는 목표를 **좌표를 잃지 않고** 달성한다. OCR 이 좌표와 원문을 주고, LLM 이 검사명 정규화·표 구조 해석·단위 변환처럼 규칙으로 짜기 번거로운 부분을 맡는다. 이식할 인식기(`services/ocr/engine.py`)와 사전(`lexicon.py` 252줄)이 `feat/OCR_n_ai-worker` 에 이미 있으므로 추가 구현량도 직송보다 크게 늘지 않는다.

ADR-010 이 이 안을 이번 릴리스에서 뺀 이유는 하나였다 — **저신뢰 판정 기준을 만들 채점 데이터셋이 없다.** 그 데이터셋은 여전히 0건이다. 데이터셋 없이 간다면 "저신뢰만 골라내기" 대신 "전 항목을 LLM 에 함께 보내되 좌표는 OCR 것을 쓴다" 로 단순화할 수 있다.

### ③이 건드리는 결정

챗봇은 [32번 문서](32_core_feature_gap_matrix.md) 축 C 다. 파일이 0개인 것보다 **결정이 0개인 것**이 문제다 — 무엇을 기억할지, 어디에 저장할지, 검색을 어떻게 할지가 전부 미정이고 담당자와 REQ 번호도 없다. 코드보다 결정이 먼저다.

한 가지는 이미 분명하다. **개인 이력은 구조화된 수치 시계열이라 벡터 검색이 오히려 나쁠 수 있다.** 인덱스 범위 조회나 툴콜링 DB 조회가 맞을 가능성이 높고, 의학 지식 문서는 벡터 검색이 맞는다. 검색을 두 갈래로 나눠 결정해야 한다.

그리고 ③의 재료는 이미 서버가 낸다 — 질환별 등급, 어느 엔진이 왜 답했는지, 무엇이 부족한지. **요약할 것이 있는 상태에서 요약을 붙이는 것과 없는 상태에서 붙이는 것은 다른 작업이다.** ①의 화면이 먼저 서는 편이 ③에도 유리하다.

### ④를 안전하게 만드는 법

"예측에 따른 챌린지 자동 생성" 에서 자동 생성의 **재료를 어디서 가져오느냐**가 갈림길이다.

**써야 하는 것**: 판정 결과의 `risk_level` 과 영역 이름. 고혈압이 `HIGH` 면 나트륨·체중·유산소, 대사증후군이 `HIGH` 면 허리둘레·중성지방. 학회 권고에서 항목을 가져와 표로 고정하고 `services/challenge.py` 에 둔다.

**쓰면 안 되는 것**: ML 기여도(`top_factors`). 단면 데이터에서 금연·절주가 당뇨 위험을 **올리는** 방향으로 나온다 — 이미 아픈 사람이 끊기 때문이다. 그대로 챌린지로 바꾸면 "당뇨 위험을 낮추려면 담배를 피우세요" 가 된다. `ConditionRisk.top_factors` 필드 설명이 "개선 조언으로 그대로 쓰면 안 된다" 고 이미 적어 두었다.

**선행 결정**: 일일 체크 기록이 NFR-01 의 건강정보인가. §4 1순위 B 참조.

## 7. 넷 + ⑤⑥ 위에 더 점검한 결과 — 만들 것보다 **안 보이는 것**이 많다

세 곳을 대조했다. Talos 필수·선택 목록, 평가 항목 20개, 그리고 **저장소에 이미 있는 자산**. 마지막에서 가장 많이 나왔다.

### 7-1. 이미 만들었는데 화면·그림·엔드포인트에서 빠진 것

| | 자산 | 어디에 있나 | 무엇이 빠졌나 | 비용 |
|---|---|---|---|---|
| **A** | **수치→질환 매트릭스** | `services/disease_risk_matrix.py` 36 KB | `/assessments/rules` 에만 실린다. **화면용 `/assessments/summary` 에 없다** | 반나절 |
| **B** | **데모 화면** | `apis/demo_routers.py` **934줄**, `/api/demo` HTTP 200 | 입력 폼·두 엔진 결과·매트릭스가 다 있는데 SPA 밖이다 | 이식 |
| **C** | 가족·계정 도메인 | 라우터 6개 + 화면 | 10개 라우터 중 6개가 배선도에 상자가 없다 | 그림 한 상자 |
| **D** | 모델 신뢰도 | `ModelAccuracy` · `RuleAnchor` | 응답에 실려 나가는데 읽는 화면이 없다 | 카드에 한 줄 |
| **E** | 백업·복구·보관함 | `localBackupService` · `localKeyVault` · `localDocumentService` | 배선도에서 `VAULT` 하나로 뭉개졌다 | 그림 |

**A가 가장 급하다. 만성질환 서비스인데 심혈관질환이 화면용 응답에 없다.** 매트릭스의 질환 축은 넷(당뇨·**심혈관질환**·만성콩팥병·고혈압)인데 중재자의 13칸에는 `cvd` 가 없다. 매트릭스는 영역 판정의 전치라서 — 영역 판정이 "여러 수치 → 이 장기의 현재 상태"라면 이쪽은 "수치 하나 → 여러 질환의 앞날"이다 — γ-GTP 가 간 영역에서 읽히면서 제2형 당뇨 발생도 예측하고, 알부민뇨가 eGFR 과 독립적으로 심혈관 사망을 예측한다는 종류의 정보가 이 축에만 있다. `RiskContributor` 가 효과크기·출처·인과 여부(`causal` 가 `false` 와 `null` 을 구분한다)까지 싣는다. **중재자에 축을 하나 더 붙이면 끝난다.**

**B는 판정을 뒤집는 발견이다.** 이 문서와 32·33번이 "입력 화면 없음 / 결과 화면 없음"으로 판정했는데, `/api/demo` 가 실제로 뜬다 — 수치 프로필 7개 그룹(기본·혈압·혈당·지질·간신장혈액·생활습관·진단이력) 입력 폼, 두 엔진 결과, 매트릭스, 로그인까지 붙어 있다. 판정이 틀린 것은 아니다 — **제품 SPA 가 아니라 서버 렌더 데모**라서 사용자 경로가 아니다. 다만 A3·A4 를 **신규 구축이 아니라 이식**으로 다시 잡아야 한다. 934줄에 담긴 입력 검증·단위 표기·카드 배치·문구가 이미 한 번 결정된 것들이다.

**빠뜨렸다가 실측으로 잡은 것 둘.** 하나, `gzip_types` 에 `application/javascript` 만 적었는데 FastAPI 의 `FileResponse` 는 `.js` 를 **`text/javascript`** 로 낸다 — 그래서 제일 큰 파일이 그대로 나갔다. 둘, `proxy_buffering off` 면 압축이 안 될 것이라 적었는데 실제로는 된다. 둘 다 "켰다"에서 멈추지 않고 바이트를 세 보고 나서야 드러났다.

**건드리지 않은 것.** `/api/` 의 `proxy_buffering off` 는 네 설정 파일이 모두 쓰는 의도된 값이라 유지했다. 압축이 그것과 무관하게 걸리므로 뒤집을 이유도 없었다.

**4-3 이 중요한 이유.** 숫자를 느슨하게 한 것이 아니라 **대리 지표를 실제 불변식으로 바꾼 것**이다. 원래 주석은 "화면은 소수 4자리로 반올림하므로 2e-5 는 표시에 영향이 없다. 이보다 크면 구조가 틀린 것"이라고 적었는데, 앞 문장은 맞고 뒤 문장은 추론이었다. 재 보니 2.352e-05 에서도 표시가 갈리는 행이 0개다. 구조 오류(트리 뒤집힘·설계 행렬 어긋남)는 `1e-2` 규모로 나타나므로 `5e-5` 도 충분한 덫이다.

**4-2 를 왜 지금까지 아무도 못 봤나.** 이 경로는 **SPA 가 마운트될 때만** 탄다. `spa.mount()` 는 빌드 산출물(`frontend/dist` 또는 이미지의 `/app/static`)이 있을 때만 라우트를 등록하고, 로컬 개발과 CI 는 프런트를 빌드하지 않으므로 catch-all 이 아예 없다. **즉 개발에서는 정상이고 운영에서만 깨진다.** 오늘 `vite build` 를 돌리면서 `frontend/dist` 가 생기자 봉투 계약 테스트 세 건이 한꺼번에 빨개져 드러났다.

같은 뿌리로 테스트 두 건도 고쳤다. `test_every_apiroute_response_model_is_api_response` 는 `/healthz` 와 catch-all 을 봉투 위반으로 셌고(둘 다 API 가 아니다 — 허용 목록으로 갈랐다), `test_unhandled_exception_renders_internal_error_envelope` 는 임시 라우트를 catch-all **뒤에** 붙여 영원히 안 잡히는 상태였다(맨 앞에 끼우게 바꿨다). **셋 다 "프런트를 빌드한 사람만 깨지는" 환경 의존 테스트였다** — 그런 테스트는 아무도 믿지 않게 되므로 환경과 무관하게 통과하도록 고쳤다.

**5·6 을 구현하지 않은 이유를 적어 둔다.** 둘 다 코드가 아니라 결정이 없어서다.

**H 피드백**은 서버에 새 테이블을 만드는 일이고, ADR-002 가 서버 저장 대상을 "인증·구독·초대·프로필 연결·기기 상태에 필요한 최소 정보"로 못 박았다. 피드백은 그 목록에 없다. 건강 수치를 안 담더라도 **목록을 늘리는 것 자체가 ADR-002 의 개정**이므로 마이그레이션을 먼저 만들 일이 아니다. 로컬 보관함에 넣는 방법도 있지만 그러면 집계가 안 되고, 평가 항목 3-4 가 요구하는 것은 "수집→저장→개선"이라 집계가 핵심이다.

**F 알림**은 두 결정에 동시에 걸린다 — 서버가 무엇을 알아야 알림을 보낼 수 있는가(ADR-002 §4), 그리고 Service Worker 를 쓸 것인가(ADR-005 보류). 트리거 재료는 있으니 결정이 나면 빠르다.

**G 일일 예방행동 추천**은 ③ 챗봇과 같은 배선을 쓰고, ③은 외부 LLM API 예외 ADR 이 선행이다(ADR-008 이 Naver CLOVA 만 허용). §6 의 ② 결정과 같은 문서에서 함께 다루면 된다.

## 8. 팀 결정이 필요한 것

1. **9/14에 배포하는 제품이 이어봄인가 Talos 챌린지 서비스인가.** 이 답이 위 표 전체의 전제다. 지금은 요구사항서와 평가계획서가 서로 다른 제품을 가리킨다.
2. **일일 체크 기록이 NFR-01의 건강정보인가.** 챌린지 저장 위치가 여기서 갈린다.
3. **OCR 축을 어디까지 가져갈 것인가.** Talos 필수가 아니므로 필수 두 칸 뒤로 미룰지, 아키텍처 근거용으로 현 상태를 유지할지.
4. **3-4 사용자 피드백 반영 구조를 어떻게 할 것인가.** 무저장 정책과 걸린다. 저장 안 하면 못 만들고, 만들면 동의와 보관기간이 필요하다.
5. **MLflow 를 실제로 쓸 것인가.** 평가계획서 3-1이 약속했는데 저장소에 없다. 안 쓸 거면 대응 칸을 실제 산출물(문서 19·22·27·28·29번)로 바꿔야 한다.
6. **⑤ 추적 대시보드를 핵심 기능에 넣을 것인가.** §6 의 넷에 빠져 있는데 Talos 필수다. 안 넣으면 0점 칸이 남는다.
7. **② 를 멀티모달 직송으로 갈 것인가, 하이브리드로 갈 것인가.** 직송이면 ADR-010 §2 대체 ADR + 외부 LLM API 예외 ADR 둘이 선행이고 근거 좌표를 잃는다. 하이브리드면 좌표를 지키면서 같은 목표에 닿는다. §6 참조.
8. **심혈관질환을 화면에 넣을 것인가.** 매트릭스에 있고 `/assessments/rules` 로는 나가는데 화면용 `/assessments/summary` 에 없다. 넣기로 하면 중재자에 축 하나 추가로 끝난다. §7-1 A 참조.
9. **브라우저 모의 판정 엔진 3파일을 지울 것인가.** `mockAssessmentEngine.ts` → `assessment.worker.ts` → `assessmentWorkerClient.ts` 체인인데 **아무도 `assessmentWorkerClient` 를 import 하지 않는다** — 완전히 죽은 코드다. 이제 진짜 화면(`/assessment`)이 서버 중재자를 쓰므로 남길 이유가 더 줄었다. 위험을 분명히 적으면 — **모의 건강 판정이 import 한 줄로 살아난다.** 32번 문서 §6-5 가 올린 항목이라 판단은 팀이 한다.
10. **`/api/demo` 934줄을 이식 원본으로 쓸 것인가.** 입력 폼·결과 카드·매트릭스가 이미 있다. 쓰기로 하면 A3·A4 가 신규 구축에서 이식으로 바뀐다. 안 쓰기로 하면 그 판단 근거를 적어야 한다 — 지금은 아무 문서도 이 화면을 자산으로 세지 않는다. §7-1 B 참조.
