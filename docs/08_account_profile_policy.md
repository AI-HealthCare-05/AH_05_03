## 1. 선택한 제품 방향

이어봄은 **가족 계정 포함** 방향으로 설계한다. 서비스 계정을 통해 가족을 초대하고, 초대받은 가족의 서비스 계정을 기존 가족 구성원 로컬 프로필과 연결할 수 있다.

단, 서비스 계정과 건강정보 권한은 분리한다. 서비스 계정이나 초대 관계만으로 다른 가족의 건강정보에 자동으로 접근할 수 없다. 기록의 **저장 위치**는 ADR-011 이후 PostgreSQL이다.

## 2. 핵심 개념

### 2.1 서비스 계정

사용자가 직접 가입하고 로그인하는 서버 계정이다.

- 인증과 로그인
- 구독·라이선스 관리
- 가족 초대 및 수락 상태 관리
- 프로필 연결에 필요한 최소 식별정보 관리
- 연결 기기 상태 관리

서비스 계정은 건강기록의 저장 단위가 아니며, 계정 보유만으로 다른 가족의 건강정보 접근 권한을 얻지 않는다.

### 2.2 가족 구성원 프로필

건강기록의 대상을 구분하는 프로필이다. 문서와 화면에서 `로컬 계정`이 아니라 `가족 구성원 프로필`로 표기한다.

- **서비스 계정 비밀번호는 없다.** 이메일이 붙기 전까지는 슬롯이다.
- 이름, 관계, 생년 정보와 건강기록을 연결한다.
- 건강정보 정본은 인증된 서버 API → PostgreSQL이다(ADR-011).
- 공용 벽에서 쓰는 **위임 PIN**은 로그인 비밀번호가 아니다(ADR-012). 열린 가구 기기에서 행위자만 가른다.

## 3. 데이터 저장 경계

### 3.1 현재 정본 (ADR-011)

프로필·건강기록·가족력·통증·OCR 확정값·예측은 인증된 서버 API로 PostgreSQL에 둔다. 서버는 요청마다 계정·가구 멤버십·프로필 권한을 검사한다.

### 3.2 서버가 다루는 계정·가구 메타데이터

- 서비스 계정 인증정보
- 구독·라이선스 상태
- 가족 초대 및 수락 상태
- 프로필 연결에 필요한 최소 식별정보
- 연결 기기 상태(벽 기기 등록은 #190)

### 3.3 ADR-011 이전 문장 (신규 기능 기준 아님)

아래는 로컬 우선 시절의 목표다. IndexedDB를 신규 기능의 정본으로 쓰지 않는다.

- 건강정보를 기기에만 두고 서버로 올리지 않는다
- 초대만으로 건강정보가 서버에 생기거나 내려오지 않는다

암호화 이전 파일·WebRTC는 후순위 기술검증으로 남긴다.

### 3.4 공용 벽 기기

같은 Origin을 가족이 함께 쓸 수 있다. **마스터 재인증**이 기기를 가구에 묶고, **구성원 PIN**이 그 기기 안에서 행위자를 가른다. PIN으로 새 기기를 등록하지 않는다. 브라우저 `localStorage` PIN 해시는 로그아웃 임시 경로다. 로그인·벽 기기는 서버 `member_pin_credentials`(#191)가 정본이다.

구현: `POST /households/{id}/device-pairings` → 벽의 `/wall/pair`에서 claim → `/wall` 개요. 기기 토큰은 `ieobom:wall-device`에 두고 계정 refresh와 섞지 않는다. 새로고침은 구성원 PIN 세션을 복원하지 않는다. 원격 철회 다음 요청은 `DEVICE_REVOKED`다.

## 4. 가족 계정 초대와 프로필 연결

처음에는 서비스 계정 사용자가 가족 구성원 프로필을 대신 생성하고 건강기록을 관리할 수 있다. 해당 가족이 직접 서비스를 사용하게 되면 기존 프로필을 선택해 서비스 계정 초대를 보낸다.

초대받은 사용자는 로컬 프로필을 만든 경험이 없어도 된다. 기존 서비스 계정으로 로그인하거나 새 서비스 계정을 만든 뒤 초대를 수락한다. 수락 후 새 프로필을 자동 생성하지 않고 초대 대상인 기존 로컬 프로필에 서비스 계정을 연결한다.

연결 대상은 초대를 보내는 사람이 기존 로컬 프로필을 선택할 때 확정한다. 초대받은 사람은 수락 화면에서 자신의 기기에 보이는 다른 로컬 프로필을 다시 선택하지 않는다. 초대 수락은 서비스 계정과 초대에 포함된 불투명 프로필 참조값을 연결하며, 수신 기기의 로컬 프로필 생성·변경이나 건강정보 다운로드를 자동으로 수행하지 않는다. 수락 직후 상태는 `계정 연결 완료·기기 연결 대기`다.

1. 기존 가족 구성원 로컬 프로필 선택
2. 서비스 계정 초대 발송
3. 초대받은 사용자의 로그인 또는 신규 가입
4. 초대 수락
5. 초대에 지정된 기존 프로필 참조와 서비스 계정 연결
6. 기기 연결 대기 및 공유할 건강정보와 접근 범위 확인
7. 허용된 건강정보로 암호화 이전 파일 생성
8. 사용자가 선택한 외부 방법으로 이전 파일 전달
9. 초대받은 사용자가 파일을 가져와 브라우저 로컬 저장소에 저장

하나의 서비스 계정은 같은 가정 안에서 하나의 가족 구성원 로컬 프로필에만 연결할 수 있다.

서버용 불투명 프로필 참조값은 영구 프로필 ID가 아니라 한 번의 연결 생명주기에만 사용한다. 초대가 종료되거나 연결 해제·계정 변경·프로필 병합이 일어나면 기존 값을 폐기하고, 재초대·재연결에는 새 값을 만든다. 같은 요청의 재시도에서는 값을 바꾸지 않는다.

## 5. 잘못 만든 새 프로필의 복구

초대받은 사용자가 기존 프로필에 연결하지 않고 새 구성원 프로필을 만든 경우 기본 복구 동작은 `삭제 후 다시 연결`이 아니라 `기존 프로필과 합치기`로 제공한다.

### 5.1 새 프로필에 건강정보가 없는 경우

1. 서비스 계정과 잘못 만든 프로필의 연결 해제
2. 연결할 기존 로컬 프로필 선택
3. 서비스 계정을 기존 프로필에 연결
4. 잘못 만든 빈 프로필 삭제

### 5.2 새 프로필에 건강정보가 있는 경우

1. `기존 프로필과 합치기` 선택
2. 병합할 기존 로컬 프로필 선택
3. 두 프로필의 기본정보와 건강기록 비교
4. 이름·생년·관계 및 중복 기록 충돌 검토
5. 건강기록·원본 서류·가족력·메모를 기존 프로필로 이전
6. 서비스 계정을 기존 프로필에 연결
7. 병합 결과 확인
8. 잘못 만든 프로필을 영구 삭제하지 않고 숨김 처리
9. 일정 기간 병합 취소 제공

병합 전 자동 복구 지점을 만들고 병합 성공을 확인하기 전까지 기존 데이터를 삭제하지 않는다.

## 6. 프로필 병합 규칙

| 충돌 항목 | 처리 원칙 |
|---|---|
| 이름·생년·관계 | 사용자가 유지할 값을 선택한다. |
| 동일 날짜·동일 건강지표 | 기존 기록, 새 기록 또는 둘 다 유지 중 선택한다. |
| 동일 원본 서류 | 파일 해시를 비교하고 중복 여부를 확인한다. |
| 가족력 | 동일 친족·질환 여부를 확인한 뒤 병합한다. |
| 접근 범위 | 더 넓은 권한을 자동 적용하지 않고 다시 확인한다. |

- 서로 다른 사람일 가능성이 있으면 병합을 중단한다.
- 병합 작업과 변경 전후 상태를 로컬 변경 이력에 기록한다.
- 병합된 프로필 식별자를 재사용하지 않는다.
- 병합된 원본 프로필의 서버용 참조값도 폐기하고 다른 연결에 재사용하지 않는다.
- 다른 브라우저의 데이터를 가져올 때는 중복 프로필을 먼저 확인하고 필요한 경우 프로필 병합을 완료한다.

## 7. 필요한 화면

- 기존 프로필 연결 또는 새 구성원 추가 선택

- 중복 프로필 감지
- 병합할 기존 프로필 선택
- 프로필 및 건강기록 비교
- 중복·충돌 기록 검토

## 8. 구현 우선순위

후순위 기능도 전체 제품 범위와 기능명세에 유지한다. 개발 속도가 계획보다 빠르면 선행조건 충족 후 즉시 앞당길 수 있다.

### 1순위

- 서비스 계정 가입과 로그인
- 구독·라이선스 관리
- 가족 구성원 프로필 생성
- 프로필별 건강정보 저장 및 관리(서버 정본)

### 2순위

- 기존 로컬 프로필에 가족 서비스 계정 초대
- 신규 가입 또는 기존 계정으로 초대 수락
- 기존 로컬 프로필과 서비스 계정 연결
- 잘못 생성한 프로필의 재연결과 병합

### 3순위

- 구성원별 건강정보 접근 범위(서버 capability #189, 벽·계정 PIN 세션 #191, claim·공유 해제 #192)
- 선택 건강정보 암호화 이전 파일 생성·가져오기
- WebRTC 직접 전송과 충돌 처리 기술검증

## 9. 미확정 사항

`대표 관리자`, `공동 관리자` 등 별도의 관리자 역할과 권한 체계는 현재 단계에서 확정하거나 임의로 추가하지 않는다(#62). 연결된 성인을 가족 공유에서 제외하는 마스터 API는 [#192](https://github.com/AI-HealthCare-05/AH_05_03/issues/192) `POST /profiles/{id}/household-unshares`다.

## 10. 위임 PIN (ADR-012, 제안)

허용: 등록된 가구 기기에서 구성원 전환, 역할에 따른 화면 권한, 임시 PIN 1회 표시, 본인 변경, 마스터 재발급, 미성년 재설정, 실패 잠금.

금지: 건강정보 DEK, 계정 비밀번호, 패스키 대체, 새 벽 기기 등록, 관리자 재인증, PIN 원문 재조회, 다른 기기·다른 가구에서 재사용(#191).

흐름: 마스터가 프로필·역할을 만든다 → 시스템이 임시 PIN을 한 번 보여 준다 → 본인이 바꾼다 → 레일 선택 시 그 사람 PIN → `profileId` + 역할.

## 11. 생명주기 용어

서버 `lifecycle_status`: `active` · `hidden` · `archived` · `unshared` · `pending_delete` · `deleted`. 목록 필터 `status`와 짝을 맞춘다. 숨김·보관·공유 제외·휴지통·계정 폐쇄는 서로 다른 동작이다.

| 용어 | 소유·데이터 | 화면 복사 |
|---|---|---|
| 벽에서 숨기기 | 소속·기록 유지 | `벽에서 숨기기` |
| 프로필 보관 | 일반 목록 제외, 복구 가능 | `프로필 보관하기` |
| 가족 공유에서 제외 | 이 집 구성원에서 뺌. 상대 계정·개인 기록 유지 | `가족 공유에서 제외`. `가구에서 빼기`는 쓰지 않음 |
| 빈 미연결 슬롯 파기 | 기록 0건 local_slot | `POST /profiles/{id}/deletion-requests` → 204 |
| 보관(휴지통) | 기록 있는 프로필 30일 유예 후 파기 | `pending_delete`. 복구는 `POST .../restorations` |
| 회원탈퇴 | 서비스 계정 | 프로필 삭제와 별개(#64, `DELETE /account`) |

멤버십 `LEFT`는 참여 이력이다. 프로필 행 삭제와 같지 않다(#74).

`DELETE /account`(#64)는 서비스 계정을 닫는다. `purge_health_data=true`일 때만 이 계정이 **만든** 서버 프로필을 지운다. 가족 공유에서 제외·휴지통 파기와 섞지 않는다. 의료기관 법정 보존기간 자체는 이 제품이 정하지 않으며, `purge_hold_reason`이 있으면 워커가 건너뛴다.

## 12. 소유권과 삭제 권한

| 대상 | 숨김 | 가족 공유 제외 | 프로필·기록 영구 삭제 |
|---|---|---|---|
| 이메일 없는 로컬 슬롯 | 마스터 | 마스터 | 빈 슬롯 즉시 파기. 기록 있으면 30일 휴지통 후 `POST /profile-purge-jobs` |
| 이메일 있는 성인 | 마스터 | 마스터(`POST /profiles/{id}/household-unshares` + 재인증) | **본인만**. 계정·개인 보관함은 손대지 않음 |
| 만 14세 미만 보호자 관리형 | 마스터·제품 보호자 | 마스터 | 법정대리인 **확인 절차**(`verified`) 뒤 삭제 *검토 요청*. 제품 보호자·자가 표시만으로는 불가. 승인되어도 즉시 파기 아님 |
| 만 14세 이상 19세 미만 | 마스터·제품 보호자 | 마스터 | 개인정보 자기결정은 본인 claim+재인증. 성년 아님. 삭제는 여전히 법정대리 확인 |
| 만 19세, 계정 없음 | 공용 요약·claim만 | 마스터 | `adult_transition_pending`. 상세 건강 읽기·쓰기·내보내기·삭제·공유 확대 중지. PIN·보호자 체크로 전환 불가 |
| 만 19세 성년 전환 후 | 본인이 공유 재승인 | 마스터 | 본인만 삭제. 전환은 claim+계정 비밀번호 |

제품 보호자(`product_guardian`)와 법정대리인 확인(`legal_representative`)은 다른 링크다. 연령은 `kr-household-minor-v2`다. 기본 확인 공급자는 `verified`를 주지 않는다.

프런트의 버튼 숨김은 권한이 아니다. 민감 API는 서버가 거절해야 한다(#189).

## 16. 삭제·복구·파기 실패 런북

운영자는 건강수치를 로그에 남기지 않는다. 재처리는 서버 API만 쓴다.

1. **휴지통 복구 실패** — 프로필이 `pending_delete`인지 확인한다. `POST /profiles/{id}/restorations`. `purge_hold_reason`이 있으면 파기 워커가 건너뛴다. hold를 임의로 지우지 않는다.
2. **파기 재처리** — `POST /profile-purge-jobs`. due인데 안 지워지면 hold·법정대리 미확인·성년 대기(`adult_transition_pending`)를 먼저 본다. 미성년은 즉시 파기하지 않는다.
3. **벽 기기 잔류** — `DELETE /households/{id}/devices/{device_id}` 후 다음 벽 요청이 `DEVICE_REVOKED`인지 확인. 다대 침해면 `POST /households/{id}/emergency-device-revocations`.
4. **PIN 잠금** — 마스터가 계정에서 알림을 확인한 뒤 `POST /profiles/{id}/pin-credentials`로 재발급. 원문을 티켓에 붙이지 않는다.
5. **롤백** — 마이그레이션은 `alembic downgrade` 경로가 있는 리비전만. 감사 행은 삭제하지 않고 후속 이벤트로 정정한다.
6. **잘못된 성년 전환** — 가구 마스터가 되돌리지 않는다. `OPS_RECOVERY_ENABLED=true` 인 개발·스테이징에서만 `POST /ops/civil-majority-invalidations` + `X-Ops-Recovery-Key`. 본문의 `operator_id`·`ticket_ref`는 주장값이며 검증된 신원이 아니다. 감사에는 `asserted_operator_id`·`asserted_ticket_ref`·`authentication_method=ops_recovery_key`·`identity_verified=false`만 남긴다. 전환 행은 남기고 `invalidated_at`만 찍는다. 삭제 진행 중이면 `needs_review`만.
7. **복구 키 회전** — Secret Manager에 새 값을 `OPS_CIVIL_MAJORITY_RECOVERY_KEY`로 넣고, 옛 값은 `OPS_CIVIL_MAJORITY_RECOVERY_KEY_PREVIOUS`와 `OPS_CIVIL_MAJORITY_RECOVERY_KEY_PREVIOUS_EXPIRES_AT`에 둔 뒤 배포한다. 만료 시각이 없거나 비어 있거나 ISO 형식이 아니면 이전 키는 거절한다(잘못된 문자열은 기동 실패). 원문은 티켓·로그·저장소에 붙이지 않는다. `production`/`prd`/`prod` 계열 환경에서 `OPS_RECOVERY_ENABLED=true`이면 서버가 기동하지 않는다. 프로덕션은 이 라우터를 등록하지 않고 OpenAPI 도 끈다.
8. **프록시 IP** — 이 저장소 nginx는 `$proxy_add_x_forwarded_for`로 hop을 **뒤에 붙인다**. 맨 오른쪽은 직전 프록시일 수 있다. `OPS_RECOVERY_TRUSTED_PROXY_IPS`에 nginx·CDN 등 신뢰 주소를 넣고, 앱은 오른쪽부터 그 목록을 건너뛰어 첫 비신뢰 hop을 클라이언트로 쓴다. 소켓 peer가 목록 밖이면 전달 헤더는 무시한다. 전역 시간당 한도는 IP 위장의 뒷받침이다. 로드밸런서가 헤더를 단일 사용자 IP로 **덮어쓰는** 배포는 목록을 그 프록시만 두면 된다.
