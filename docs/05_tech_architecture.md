# 기술 스택 및 로컬 우선 아키텍처

> 관련 문서: [01_requirements.md](01_requirements.md), [02_erd.md](02_erd.md), [03_api_spec.md](03_api_spec.md), [브라우저 로컬 데이터 계약](10_local_data_contract.md), [로컬 규칙·ML 모델 실행 구현 가이드](11_local_model_runtime_implementation.md), [ADR-001](adr/0001-web-local-first-architecture.md), [ADR-002](adr/0002-separate-server-api-and-local-domain-contract.md), [ADR-003](adr/0003-web-authentication-token-transport.md), [ADR-004](adr/0004-family-invitation-state-and-redis-boundary.md), [ADR-006](adr/0006-lifecycle-scoped-profile-reference.md)

## 1. 핵심 아키텍처 원칙

- 서비스 계정 메타데이터와 건강정보를 물리적으로 분리한다.
- 서버는 인증·구독·초대·최소 연결정보만 처리한다.
- 가족 프로필과 건강정보는 사용자 기기의 로컬 저장소에 보관한다.
- OCR·예측·대화형 입력은 가능한 범위에서 기기에서 수행한다.
- 계정 연결과 건강정보 전송은 서로 다른 작업이다.
- 프로필 병합은 복구 지점과 로컬 트랜잭션을 사용한다.
- 제품은 반응형 웹 서비스로 제공하며, 브라우저 로컬 저장과 웹서버 저장을 명확히 구분한다.

## 2. 기술 스택

| 영역 | 채택 | 역할 |
|---|---|---|
| 프론트엔드 | React + TypeScript + Vite SPA | 화면, 로컬 도메인 로직, 브라우저 기능 연동 |
| 클라이언트 상태 | Zustand | 화면·선택·병합 진행 상태 |
| 서버 상태 | TanStack Query | 계정·구독·초대·연결 상태 |
| 로컬 저장 | IndexedDB 우선 + OPFS 단계 도입 | 구조화된 건강기록과 큰 원본 파일 보관 |
| 로컬 암호화·백업 | Web Crypto API + 외부 암호화 파일 | 민감 로컬 데이터 암호화와 독립적인 복구 |
| 백엔드 | FastAPI + SQLAlchemy 2.x Async + Alembic | 인증·구독·초대·최소 연결 API와 스키마 관리 |
| 서버 DB | PostgreSQL | 건강정보를 제외한 계정 메타데이터 |
| 임시 상태 | Redis | 인증 토큰 회전, 초대 토큰 1회성 소비·전송 신호·속도 제한 등 비건강정보 |
| 로컬 AI/OCR | TypeScript·Rust/WASM·ONNX Runtime Web·Tesseract 계열 검토 | 기기 내 규칙 평가, 예측과 문서 인식 |
| 인프라 | Docker, AWS EC2, Nginx | 계정 API 배포 |

건강정보를 외부 API나 서버 AI 워커로 보내는 구조는 현재 로컬 보관 원칙과 맞지 않으므로 사용하지 않는다.

Python 규칙·학습 모델은 개발자 PC와 CI의 참조 구현으로만 유지한다. FastAPI와 서버 AI worker에서 참조 모델을 import하지 않으며, 제품 런타임 선택과 포팅 조건은 [로컬 규칙·ML 모델 실행 구현 가이드](11_local_model_runtime_implementation.md)를 따른다.

## 3. 시스템 경계

```text
┌──────────────────────── 사용자 기기 ────────────────────────┐
│ React UI                                                  │
│   ├─ 가족 구성원 로컬 프로필                              │
│   ├─ 건강기록·가족력·원본 서류                            │
│   ├─ 로컬 OCR·예측                                        │
│   ├─ 병합·복구 지점                                       │
│   └─ IndexedDB / OPFS / Web Crypto                        │
└───────────────┬───────────────────────────────┬────────────┘
                │ 계정·초대 메타데이터          │ 암호화 백업·이전 파일
                ▼                               ▼
       FastAPI → PostgreSQL              사용자가 브라우저 밖에
       인증·구독·초대만 저장             직접 내려받고 가져오기
```

## 4. 서버 저장 허용 목록

- 서비스 계정 인증정보
- 구독·라이선스 상태
- 초대 대상 이메일과 초대 상태
- 건강정보를 포함하지 않는 불투명 가정·프로필 참조값
- 공개 기기 키, 기기 이름 등 연결에 필요한 최소 상태

서버 금지 항목:

- 이름·생년·가족관계가 포함된 로컬 프로필 원문
- 건강기록, 통증 기록, 가족력과 유전정보
- 원본 건강서류와 OCR 결과
- 예측 결과와 로컬 변경 이력
- 건강정보의 요약·통계·기록 개수

## 5. 계정·프로필 연결

초대 생성 시 서버에는 이번 연결 생명주기에만 사용하는 불투명 `target_profile_ref`만 전달한다. 초대 수락 후 계정과 참조값을 연결하되, 실제 프로필 내용과 건강정보는 움직이지 않는다. 연결 종료·프로필 병합·계정 변경 뒤에는 참조값을 폐기하고 재연결 시 새 값을 만든다. 폐기 이력과 재사용 금지는 Redis TTL이 아니라 PostgreSQL이 보장한다.

초기 버전에서 건강정보를 다른 브라우저나 기기로 옮기려면 사용자가 접근 범위를 확인한 뒤 허용 데이터로 암호화 이전 파일을 생성하고, 상대 기기에서 직접 가져온다. WebRTC 기반 기기 직접 전송은 [ADR-001](adr/0001-web-local-first-architecture.md)의 후순위 기술검증을 통과한 뒤 적용 여부를 결정한다.

## 6. 프로필 병합 트랜잭션

```text
중복 감지 → 동일인 확인 → 복구 지점 생성 → 충돌 계산
→ 사용자 선택 → 로컬 병합 → 서버 참조 연결 변경
→ source 숨김 → 되돌리기 기한 시작
```

- 서버 연결 변경 실패 시 병합을 완료로 확정하지 않는다.
- source와 target 원본은 성공 확인 전까지 보존한다.
- 파일 중복은 콘텐츠 해시로 확인한다.
- 병합 작업은 중단·재시도·롤백할 수 있어야 한다.

## 7. 보안 고려사항

- 비밀번호는 Argon2id 또는 검증된 비밀번호 해시로 서버에 저장한다.
- Access Token은 15분의 짧은 JWT로 유지하고 클라이언트 메모리에만 보관한다.
- Refresh Token은 Secure HttpOnly SameSite 쿠키로만 전달하고 Redis allowlist에서 매번 회전한다.
- 이미 소비된 Refresh Token 재사용 시 해당 계정의 Refresh Token 패밀리를 폐기한다.
- 초대 최종 상태는 PostgreSQL에 두고 Redis는 초대 원문 토큰 allowlist, 소비 마커, 워커 인계와 속도 제한에만 사용한다.
- 인증 라우트는 허용된 브라우저 Origin만 받아 CSRF 공격면을 제한한다.
- 로컬 백업은 인증된 암호화(AES-GCM 등)와 강한 키 파생 함수를 사용한다.
- 후순위 WebRTC 기술검증에서 기기 연결을 채택하면 상대 기기 확인 코드 또는 QR 검증을 사용한다.
- 서버 로그·분석 도구에 이메일 외의 프로필 및 건강정보를 남기지 않는다.
- 서비스 계정 해지와 구독 종료가 로컬 데이터 삭제를 유발하지 않게 한다.

## 8. 성능·용량 대응

- 구조화된 건강정보는 IndexedDB에 저장하고 대용량 원본 파일은 OPFS에 한 번만 저장한다.
- OPFS 내부의 백업 사본은 독립적인 백업으로 간주하지 않고 암호화 파일을 브라우저 밖으로 내보낸다.
- 이력·차트 조회에는 로컬 인덱스와 증분 집계를 사용한다.
- 병합 전 예상 용량을 검사하고 부족하면 작업을 시작하지 않는다.
- OCR·로컬 모델은 지원 기기 기준을 정하고 실행 불가 시 직접 입력으로 전환한다.
- 서버 API 성능 측정은 인증·구독·초대 엔드포인트만 대상으로 한다.

## 9. 단계별 기술 의존성

| 우선순위 | 구현 | 선행조건 |
|---:|---|---|
| 1 | 계정, 로컬 프로필, 건강기록, 외부 암호화 백업 | IndexedDB 스키마·암호화 포맷 확정 |
| 2 | 초대, 프로필 연결, 병합 | 불투명 참조값·복구 지점·충돌 규칙 |
| 3 | 접근 범위, WebRTC 직접 전송 기술검증 | 시그널링·키 교환·기기 인증·중계 여부·충돌 해결 |

후순위 기능도 아키텍처와 테스트 계획에 유지하고 선행조건이 충족되면 앞당긴다.
