## 1. 목적

이 문서는 건강 평가 규칙과 학습 모델을 현재 Python으로 검증하면서도 다음 조건을 지키기 위한 구현 기준이다.

- 건강정보와 건강 모델 실행을 원격 FastAPI 서버로 옮기지 않는다.
- 비슷한 모델을 추가하는 동안 Python 구현을 하나의 참조 기준으로 사용한다.
- Python 전용 기능에 결합되지 않게 하여 TypeScript, Rust/WASM 또는 ONNX로 옮길 수 있게 한다.
- 같은 입력에 대해 참조 구현과 제품 구현이 같은 결과를 내는지 자동 검증한다.

이 문서는 채택·기각 이유만 기록하는 ADR이 아니다. 저장소 배치, 코드 제약, 계약, 테스트, CI와 단계별 전환 조건까지 다루는 구현 가이드다.

## 2. 현재 결론

검증 단계에서는 고혈압·비만·이상지질혈증·당뇨병 등 유사한 모델을 Python 참조 구현으로 통일한다. 팀에서 계획한 모델들이 모두 구현되고 입력·출력·임상 규칙이 안정되기 전에는 전부를 TypeScript나 Rust로 다시 작성하지 않는다.

단, Python 참조 모델은 다음 위치에서만 실행한다.

| 실행 위치 | 허용 여부 | 용도 |
|---|---:|---|
| 개발자 PC | 허용 | 규칙 작성, EDA, 재현, fixture 생성 |
| CI | 허용 | 테스트, 동등성 검증, 모델 산출물 검사 |
| 사용자 브라우저 | 현재 미사용 | 향후 TypeScript·WASM·ONNX 제품 구현이 담당 |
| 원격 FastAPI | 금지 | 건강정보를 받아 Python 모델로 평가하지 않음 |
| 서버 AI worker | 금지 | 건강정보·건강 모델 실행 경로로 사용하지 않음 |

FastAPI·PostgreSQL·Redis는 원격 서버에서 계정, 구독, 라이선스, 초대와 불투명 연결 메타데이터를 처리한다. 사용자 건강정보와 건강 평가 실행은 브라우저 등 사용자 기기 안에 남긴다.

```text
현재 검증
  Python 참조 모델 ── 개발자 PC·CI에서만 실행
  사용자 브라우저 ── 건강정보 로컬 저장, 제품 모델은 아직 연결하지 않음
  FastAPI 서버     ── 계정·구독·초대 메타데이터만 처리

제품 목표
  사용자 브라우저
    ├─ IndexedDB·OPFS·Web Crypto
    └─ TypeScript / Rust-WASM / ONNX 로컬 모델

  원격 FastAPI
    └─ 건강정보와 건강 평가 입출력을 받지 않음
```

## 3. 지금 포팅하면 생기는 문제

### 구현과 유지보수가 즉시 두 배가 된다

유사 모델 4개를 Python과 TypeScript로 동시에 유지하면 사실상 8개의 구현을 관리해야 한다. 임계값, 단위, 공복 여부, 연령 기준, 결측 처리 중 하나만 한쪽에 늦게 반영되어도 동일 사용자에게 서로 다른 결과가 나온다.

### 모델 오류와 포팅 오류를 동시에 추적해야 한다

입력·출력 계약과 임상 규칙이 변하는 단계에서 결과가 다르면 원인이 원래 규칙인지, 언어 변환인지, 숫자 반올림인지 분리하기 어렵다. 테스트 fixture와 오류 코드도 두 런타임에 맞춰 계속 수정해야 한다.

### 불안정한 계약을 너무 일찍 굳힌다

현재는 연령, 공복 상태, 부분 혈압 입력, 단위와 판정 우선순위가 계속 구체화될 수 있다. 이 시점의 포팅은 잘못된 추상화와 호환성 부담을 장기간 남긴다.

### 현재 계산 성능은 주된 병목이 아니다

현재 규칙 모델은 단순 비교와 계산 중심이다. 포팅의 우선 이유를 성능으로 잡기보다 임상 규칙 정확성, 데이터 경계, 로컬 저장, 브라우저 통합과 복구 가능성을 먼저 해결한다.

따라서 지금의 Python 유지 결정은 제품에서 Python을 사용한다는 의미가 아니라 **안정적인 참조 결과를 먼저 만든다**는 의미다.

## 4. FastAPI import를 구조적으로 막는 방법

Python 코드가 같은 저장소에 있으면 팀원이 편의를 위해 FastAPI 라우터나 서비스에서 직접 import할 가능성이 있다. 이 경우 브라우저 건강정보가 요청 본문, 서버 로그, 오류 추적, Redis 또는 DB를 거칠 수 있다. 이는 코드 스타일 문제가 아니라 로컬 우선 아키텍처의 데이터 경계를 바꾸는 위반이다.

### 목표 디렉터리 경계

PR 병합 후 참조 모델을 정리할 때 다음과 같이 서버 애플리케이션 밖에 둔다.

```text
reference_models/
├─ README.md
├─ python/
│  ├─ pyproject.toml
│  ├─ ieobom_reference/
│  │  ├─ contracts.py
│  │  ├─ rules/
│  │  └─ learned/
│  └─ tests/
└─ fixtures/
   ├─ schema/
   └─ golden/

app/                       # FastAPI 서버
ai_worker/                 # 건강정보 모델 실행에 사용 금지
frontend/src/local-models/ # 향후 제품용 로컬 런타임
```

`reference_models/README.md` 첫 부분에는 다음 경고를 둔다.

> 개발·CI 참조 구현 전용. FastAPI, 서버 worker, 배포 컨테이너에서 import하거나 실행하지 않는다. fixture에는 합성 데이터만 사용한다.

### 배포 경계

- 백엔드 Docker build context 또는 복사 목록에서 `reference_models/`를 제외한다.
- 백엔드 런타임 의존성에 참조 모델 패키지를 등록하지 않는다.
- `app/`과 `ai_worker/`는 참조 모델 경로를 Python path에 추가하지 않는다.
- 서버 요청·응답 DTO에 검사 수치, 가족력, 원본 건강기록, 모델 입력·예측 결과 필드를 만들지 않는다.
- 참조 모델은 FastAPI, SQLAlchemy, Redis, HTTP 클라이언트와 DB 드라이버에 의존하지 않는다.

### CI 아키텍처 검사

CI에서 단순 문자열 검색만 하지 말고 Python AST를 사용해 다음 조건을 검사한다.

1. `app/`과 `ai_worker/`의 import 문을 순회한다.
2. `reference_models`, `ieobom_reference` 또는 금지된 상대 경로 import를 찾는다.
3. 발견하면 파일과 줄 번호를 출력하고 빌드를 실패시킨다.
4. 동적 import와 Python path 변경도 별도 금지 패턴으로 검사한다.

추가로 CODEOWNERS나 PR 체크리스트에 다음 항목을 둔다.

- [ ] 새 서버 API가 건강정보나 모델 입출력을 받지 않는다.
- [ ] 서버 코드가 Python 참조 모델을 import하지 않는다.
- [ ] 참조 모델과 fixture가 백엔드 배포 이미지에 포함되지 않는다.
- [ ] 테스트 데이터가 합성 데이터임을 확인했다.

금지되는 흐름은 다음과 같다.

```text
브라우저 건강정보 → FastAPI → Python 모델 평가 → 결과 반환
```

## 5. 포팅 가능성을 위한 Python 구현 제한

Python을 계속 사용하더라도 Python만 가능한 편의 기능에 의존하지 않는다.

### 권장 규칙

- 입력을 받고 결과를 반환하는 순수 함수 중심으로 작성한다.
- 문자열, 정수, 실수, 불리언, 배열과 명시적 객체 등 JSON으로 표현 가능한 타입만 계약에 사용한다.
- `model_id`, `model_version`, `rule_version`, `schema_version`을 분리해 기록한다.
- 단위, 시간대, 공복 여부와 결측 상태를 입력에서 명시한다.
- 반올림 자릿수, 경계값 포함 여부와 판정 우선순위를 코드와 fixture에 고정한다.
- 같은 입력은 언제나 같은 결과를 내야 한다.
- 사용자 설명문보다 안정적인 결과 코드와 구조화된 수치를 먼저 반환한다.
- 실행 시각이 필요하면 외부에서 전달하고 모델 내부에서 현재 시간을 읽지 않는다.
- 난수가 필요하면 시드를 입력 계약에 포함한다.

### 제한 또는 금지할 기능

- 런타임 규칙에서 pandas DataFrame에 의존
- 동적 import, reflection, monkey patching
- pickle 등 Python 객체 형식 자체를 모델 계약으로 사용
- 파일시스템, DB, 네트워크 또는 환경변수에 따라 결과를 변경
- 변경 가능한 전역 상태와 결과를 숨기는 캐시
- 암묵적인 로컬 시간대와 현재 시간 사용
- 시드 없는 난수
- Python 예외 메시지를 외부 오류 계약으로 사용
- 핵심 규칙에 한국어 UI 문장을 직접 결합
- 모델마다 서로 다른 입력·출력·오류 형식을 사용

EDA와 학습 과정에서는 pandas, DuckDB, scikit-learn을 사용할 수 있다. 다만 제품 실행 계약과 규칙 코어에는 해당 객체가 노출되지 않아야 한다.

## 6. 공통 모델 계약

규칙 모델과 학습 모델은 구현 방식이 달라도 공통 envelope를 사용한다.

```json
{
  "schema_version": 1,
  "model_id": "dyslipidemia-rule",
  "model_version": "0.1.0",
  "rule_version": "2026-08-19",
  "input": {
    "subject_age": 52,
    "measurements": [],
    "conditions": []
  }
}
```

```json
{
  "schema_version": 1,
  "model_id": "dyslipidemia-rule",
  "model_version": "0.1.0",
  "rule_version": "2026-08-19",
  "risk_code": "REVIEW_RECOMMENDED",
  "findings": [],
  "warnings": [],
  "insufficient_fields": []
}
```

공통 오류는 최소한 다음 의미를 구분한다.

- `INVALID_FIELD`: 형식·범위·단위 오류
- `UNSUPPORTED_SUBJECT`: 연령 등 현재 규칙 적용 대상이 아님
- `INSUFFICIENT_INPUT`: 판정에 필요한 값이 부족함
- `MODEL_VERSION_UNAVAILABLE`: 요청한 로컬 모델 버전이 없음
- `MODEL_EXECUTION_FAILED`: 예상하지 못한 로컬 실행 실패

오류에는 안정적인 `error_code`, 필드 경로와 기계 판독 가능한 `reason`을 포함한다. 사용자 문구와 번역은 프론트엔드가 담당한다.

## 7. Golden fixture와 동등성 검사

모든 모델은 다음 사례를 JSON fixture로 제공한다.

- 정상값
- 임계값 바로 아래, 같은 값, 바로 위
- 필수값과 선택값 결측
- 지원하지 않는 단위
- 공복, 비공복, 공복 여부 미상
- 대상 연령 바로 아래와 이상
- 부분 입력과 서로 모순되는 입력
- 매우 큰 값, 매우 작은 값과 숫자가 아닌 값

Python 참조 구현의 기대 결과를 golden fixture로 고정한다. 이후 TypeScript, Rust/WASM 또는 ONNX 제품 구현은 같은 fixture를 실행해 다음 기준을 만족해야 한다.

- 결과 코드와 구조 필드는 100% 동일하다.
- 규칙 모델의 경계 판정은 100% 동일하다.
- 부동소수점 결과는 계약에 명시한 허용 오차 안에서 동일하다.
- 반올림 자릿수와 결측 표현이 동일하다.
- 오류 코드와 오류 필드가 동일하다.

규칙을 바꾸면 `rule_version`, 근거 문헌과 fixture를 한 PR에서 함께 갱신한다. 실제 환자나 사용자 데이터는 fixture와 CI에 넣지 않는다.

## 8. 포팅 전에 안정화할 항목

현재 규칙 모델은 다음 항목을 먼저 확정해야 한다.

- 알 수 없는 입력 필드를 무시할지 오류로 거절할지
- 입력값에서 계산한 BMI와 non-HDL에도 동일한 범위 검증을 적용할지
- 공복 여부 미상과 비공복을 구분하는 방법
- 수축기 또는 이완기 혈압만 있는 부분 입력 처리
- 소아·청소년과 성인의 판정 기준 분리
- 관상동맥질환 등 임상 상태가 LDL 목표치에 미치는 영향
- 단위 변환, 임계값 포함 여부와 다중 판정 우선순위
- 임상 검토자, 근거 문헌과 규칙 버전 기록

학습 모델은 [09_chronic_disease_model_plan.md](09_chronic_disease_model_plan.md)의 제품 적용 보류 조건을 먼저 해결한다. Python `joblib` 산출물을 그대로 브라우저 계약으로 간주하지 않는다.

## 9. 모델 유형별 제품 런타임 선택

| 모델 유형 | 우선 검토 | 선택 기준 |
|---|---|---|
| 단순 임계값·결정 규칙 | TypeScript | 작고 단순하며 프론트에서 디버깅하기 쉬움 |
| 여러 환경에서 공유할 복잡한 규칙 코어 | Rust/WASM | 규칙 안정화, 재사용 필요, 팀 Rust 역량 확보 |
| 선형·트리·scikit-learn 계열 | ONNX Runtime Web | 변환 지원과 연산자 호환성 검증 필요 |
| 딥러닝·영상 모델 | ONNX/WebGPU | 대상 브라우저, 모델 크기, 메모리와 정확도 검증 필요 |
| EDA·학습·규칙 검증 | Python | 개발자 PC·CI 전용, 제품 런타임 아님 |

모델별로 다른 런타임을 선택할 수 있다. 모든 것을 WASM이나 ONNX 하나로 통일하는 것이 목표가 아니라 데이터 경계를 지키면서 유지비와 성능을 균형 있게 맞추는 것이 목표다.

## 10. WASM을 고려할 조건

다음 조건이 충분히 성립할 때 Rust/WASM 전환을 검토한다.

- 계획한 모델들의 입력·출력·오류 계약이 안정되었다.
- 임상 규칙과 경계값 변경 빈도가 낮아졌다.
- Python 검증 환경과 브라우저가 같은 규칙 코어를 재사용할 필요가 커졌다.
- TypeScript 중복 구현의 실제 유지비가 확인되었다.
- 저사양 모바일 브라우저 벤치마크가 정한 응답시간이나 메모리 목표를 넘는다.
- 배열·수치 계산 등 WASM 이점이 큰 연산이 생겼다.
- Rust 코드를 리뷰, 배포, 디버깅할 담당자와 팀 역량이 확보되었다.
- golden fixture 동등성 검사와 브라우저 E2E 테스트가 준비되었다.

단순한 임계값 비교라면 TypeScript가 더 작고 운영하기 쉽다. WASM은 성능이라는 이유만으로 선행 도입하지 않는다.

## 11. Pyodide를 현재 권장하지 않는 이유

Python 코드를 큰 수정 없이 브라우저에서 실행하는 대표적인 방법은 Pyodide 계열이다. 연구 데모에는 유용하지만 현재 이어봄의 제품 기본 구조로는 권장하지 않는다.

- Python 런타임과 패키지 다운로드로 초기 로딩이 커진다.
- 모바일 브라우저의 메모리 사용량과 콜드 스타트가 불리하다.
- 패키지 호환성, Web Worker 통신, 캐싱과 오류 분석이 복잡해진다.
- 단순 규칙 모델에 Python 런타임 전체를 탑재하는 것은 비용 대비 이점이 작다.
- Python을 WASM 환경에서 실행한다고 작고 독립적인 제품 바이너리가 자동으로 생기지 않는다.
- 제품 코드가 Python 패키지와 브라우저 런타임 양쪽에 결합될 수 있다.

다음 조건에서는 제한적인 기술검증을 할 수 있다.

- 단기간 연구 데모에서 Python 라이브러리를 그대로 보여줘야 한다.
- 번들 크기와 시작시간이 제품 요구사항이 아니다.
- 실제 저사양 기기의 다운로드, 시작시간과 메모리 사용량을 측정한다.
- 기술검증 코드가 제품 기본 경로로 유입되지 않게 격리한다.

## 12. Rust/WASM 선택 시 목표 구조

```text
assessment-core/  # Rust 순수 규칙과 공통 타입
├─ assessment-py/ # PyO3 + maturin, Python 검증용 바인딩
└─ assessment-wasm/ # wasm-bindgen, 브라우저 제품 바인딩
```

이 구조는 규칙 코어 하나를 Python 검증과 브라우저 제품 실행에서 재사용한다. Rust 코어는 번역 문장 대신 코드와 수치 결과를 반환하고 프론트엔드가 사용자 문구를 만든다.

WASM은 보안 경계가 아니다. 사용자가 브라우저 실행 결과를 변경할 수 있으므로 구독, 권한, 과금처럼 서버가 신뢰해야 하는 판단에는 사용하지 않는다. 건강 평가를 사용자 기기에서 제공하는 용도로 한정한다.

## 13. 구현 순서

### 1단계: Python 참조 구현 안정화

1. 계획한 규칙 모델을 공통 계약으로 구현한다.
2. 입력 검증, 임상 경계값과 오류 코드를 확정한다.
3. 모델별 임상 근거와 `rule_version`을 기록한다.
4. 경계값과 결측 사례 fixture를 만든다.
5. 참조 모델을 서버 패키지와 배포 이미지에서 분리한다.
6. 서버 import 금지 아키텍처 검사를 CI에 추가한다.

### 2단계: 제품 런타임 선택

1. 규칙 모델, 학습 모델과 영상 모델을 분류한다.
2. 대상 브라우저와 저사양 기기의 성능 목표를 정한다.
3. TypeScript, Rust/WASM과 ONNX 후보의 작은 기술검증을 한다.
4. 번들 크기, 콜드 스타트, 메모리, 실행시간과 동등성 결과를 비교한다.
5. 모델별 제품 런타임을 확정한다.

### 3단계: 브라우저 통합

1. 제품 모델을 Web Worker에서 실행해 UI 스레드와 분리한다.
2. [로컬 데이터 계약](10_local_data_contract.md)의 암호화 해제 결과를 메모리에서만 입력한다.
3. 모델 입력과 결과를 서버 로그·분석 도구로 전송하지 않는다.
4. 모델 버전 전환, 실패 시 이전 버전 복구와 오프라인 동작을 검증한다.
5. Python golden fixture와 브라우저 E2E 동등성 검사를 통과시킨다.

## 14. 포팅 시작 조건

- [ ] 계획한 모델들의 공통 스키마가 확정되었다.
- [ ] 임상 근거와 규칙 버전이 기록되었다.
- [ ] 경계값, 결측과 오류 fixture가 준비되었다.
- [ ] Python 참조 테스트가 안정적으로 통과한다.
- [ ] 건강정보가 서버, 로그와 CI 산출물로 나가지 않는다.
- [ ] 백엔드의 참조 모델 import를 막는 CI가 동작한다.
- [ ] 목표 브라우저와 저사양 기기의 성능 기준이 있다.
- [ ] 포팅 결과의 동등성 기준이 합의되었다.

조건을 만족하지 못하면 포팅을 폐기하는 것이 아니라 후순위로 유지하고 참조 구현 안정화를 계속한다.

## 15. 검토한 대안과 현재 처리

| 대안 | 처리 | 이유 |
|---|---|---|
| 지금 TypeScript로 전부 포팅 | 보류 | 계약 변경 중 이중 유지와 결과 불일치 위험이 큼 |
| FastAPI에서 Python 모델 실행 | 거절 | 건강정보를 원격 서버로 보내 로컬 우선 경계를 훼손함 |
| Pyodide를 제품 기본 런타임으로 사용 | 현재 거절 | 번들·시작시간·메모리·운영 복잡성이 단순 규칙 모델의 이점보다 큼 |
| 지금 Rust로 전부 재작성 | 보류 | 장기 후보지만 임상 규칙이 불안정한 단계의 재작업이 큼 |
| Python 구현을 제약 없이 유지 | 거절 | 포팅 비용과 서버 import 유혹을 함께 키움 |
| 규칙 모델을 TypeScript로 구현 | 후순위 후보 | 규칙이 단순하고 안정되면 가장 작은 제품 경로가 될 수 있음 |
| 규칙 코어를 Rust/WASM으로 공유 | 후순위 후보 | 계약 안정화와 재사용 필요가 확인될 때 유리함 |
| 학습 모델을 ONNX로 변환 | 모델별 검증 | 변환 가능성, 연산자 호환성과 정확도 비교가 필요함 |

## 16. 팀 체크리스트

### ML 담당자

- [ ] 새 모델도 공통 입력·결과·오류 계약을 사용한다.
- [ ] 모델 코어에 네트워크, DB와 파일 I/O가 없다.
- [ ] 단위, 공복 여부, 연령과 결측 상태를 명시적으로 다룬다.
- [ ] 경계값 fixture와 임상 근거를 함께 추가한다.
- [ ] 결과에 모델·규칙·스키마 버전을 포함한다.
- [ ] 실제 건강정보를 테스트 데이터로 사용하지 않는다.
- [ ] Python 전용 기능을 코어에 추가하기 전에 포팅 영향을 검토한다.

### 백엔드 담당자

- [ ] FastAPI와 worker에서 참조 모델을 import하지 않는다.
- [ ] 서버 DTO와 로그에 건강정보·모델 입출력을 추가하지 않는다.
- [ ] 배포 이미지에서 참조 모델과 fixture를 제외한다.
- [ ] import 금지 아키텍처 검사를 유지한다.

### 프론트엔드 담당자

- [ ] 모델은 브라우저 로컬 데이터만 입력으로 사용한다.
- [ ] 모델 실행을 Web Worker로 분리한다.
- [ ] 서버 분석 도구에 모델 입력·결과를 전송하지 않는다.
- [ ] 모델 버전 불일치와 실행 불가 시 사용자 복구 경로를 제공한다.

## 17. 완료 정의

이 가이드의 첫 구현 단계는 다음 상태에서 완료로 본다.

1. Python 참조 모델이 서버 런타임과 배포물에서 분리되어 있다.
2. 모든 대상 모델이 공통 계약과 golden fixture를 사용한다.
3. 서버 import 금지 검사가 CI에서 동작한다.
4. 임상 규칙의 근거·버전·경계값 테스트가 기록되어 있다.
5. 다음 제품 런타임을 비교할 수 있는 브라우저 벤치마크 기준이 정의되어 있다.
