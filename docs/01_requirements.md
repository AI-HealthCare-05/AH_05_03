> 담당: 오성민(주도), 팀 전체 검토

## 1. 문제 정의

건강검진 결과, 예방접종 기록, 병원 서류, 통증과 생활 기록은 종이와 여러 파일로 흩어져 가족 구성원별 장기 변화를 확인하기 어렵다. 일반적인 클라우드 서비스에 건강정보를 저장하는 것에 대한 불안도 서비스 이용의 장벽이 된다.

이어봄은 가족 건강기록을 구성원별로 정리하되 중요한 건강정보는 사용자 기기에 보관하는 로컬 우선 서비스다. 서비스 계정은 인증·구독·가족 초대에 사용하고, 건강정보는 계정 데이터와 분리한다.

## 2. 제품 원칙

- 서비스 계정은 인증, 구독·라이선스, 가족 초대 및 기기 연결 상태를 관리한다.
- 가족 구성원은 먼저 기기 안의 `가족 구성원 로컬 프로필`로 등록한다.
- 건강기록, 가족력, 원본 서류, OCR·예측 결과와 변경 이력은 기기에 저장한다.
- 서비스 계정 초대나 프로필 연결만으로 건강정보를 서버에 업로드하지 않는다.
- 가족이 직접 사용하게 되면 기존 로컬 프로필에 그 가족의 서비스 계정을 연결한다.
- 잘못 만든 중복 프로필은 삭제보다 안전한 병합과 되돌리기를 우선 제공한다.
- 후순위 기능도 제품 범위에서 삭제하지 않고 개발 로드맵에 유지한다.

## 3. 용어

| 용어 | 정의 |
|---|---|
| 서비스 계정 | 사용자가 직접 가입·로그인하며 인증, 구독, 초대 상태를 관리하는 서버 계정 |
| 가족 구성원 로컬 프로필 | 로그인 기능 없이 건강기록의 대상을 구분하기 위해 기기에 저장하는 프로필 |
| 프로필 연결 | 서비스 계정을 이미 존재하는 가족 구성원 로컬 프로필에 연결하는 작업 |
| 프로필 병합 | 실수로 만든 중복 프로필의 정보와 기록을 기존 프로필로 안전하게 합치는 작업 |
| 기기 연결 | 사용자 동의 후 허용된 건강정보를 기기 간 암호화 전송하기 위한 연결 |

`로컬 계정`, `대표 관리자`, `공동 관리자`라는 용어는 현재 확정된 설계에서 사용하지 않는다.

## 4. 기능 요구사항

우선순위는 기능의 삭제 여부가 아니라 구현 순서를 뜻한다.

| ID | 우선순위 | 카테고리 | 요구사항 |
|---|---:|---|---|
| REQ-01 | 1 | 서비스 계정 | 사용자는 서비스 계정을 생성하고 로그인하며 구독·라이선스 상태를 확인할 수 있어야 한다. |
| REQ-02 | 1 | 로컬 프로필 | 사용자는 이름, 관계, 생년 정보를 가진 가족 구성원 로컬 프로필을 기기에 생성·수정할 수 있어야 한다. |
| REQ-03 | 1 | 건강기록 | 사용자는 로컬 프로필별 건강기록을 등록·조회·수정·삭제할 수 있어야 한다. |
| REQ-04 | 1 | 로컬 보관 | 건강기록, 통증 기록, 가족력, 원본 서류와 변경 이력은 서버로 전송하지 않고 기기에 저장해야 한다. |
| REQ-05 | 1 | 조회 | 사용자는 구성원별 건강 이력과 수치형 지표 변화 차트를 확인할 수 있어야 한다. |
| REQ-06 | 1 | 백업·복구 | 사용자는 로컬 건강정보를 암호화 파일로 내보내고 가져올 수 있어야 한다. |
| REQ-07 | 2 | 가족 초대 | 사용자는 기존 가족 구성원 로컬 프로필을 선택해 가족의 서비스 계정을 초대할 수 있어야 한다. |
| REQ-08 | 2 | 프로필 연결 | 초대받은 사용자는 로그인 또는 신규 가입 후 초대를 수락하고 새 프로필 생성 없이 기존 로컬 프로필에 연결되어야 한다. |
| REQ-09 | 2 | 프로필 병합 | 사용자가 실수로 새 프로필을 만들면 기존 프로필과 비교·병합하고 일정 기간 되돌릴 수 있어야 한다. |
| REQ-10 | 2 | OCR | 원본 건강서류의 OCR은 기기에서 처리하고 인식 결과를 사용자 확인 후 로컬에 저장해야 한다. |
| REQ-11 | 2 | 예측 | 지원되는 건강지표의 변화 예측은 로컬 기록을 사용해 기기에서 수행하고 의료적 진단이 아님을 표시해야 한다. |
| REQ-12 | 3 | 접근 범위 | 계정이 연결된 구성원은 사용자가 확인한 범위에서만 건강정보에 접근할 수 있어야 한다. |
| REQ-13 | 3 | 기기 동기화 | 연결된 기기는 허용된 건강정보를 암호화하여 직접 전송하고 각 기기에 로컬 저장해야 한다. |
| REQ-14 | 3 | 충돌 처리 | 기기 동기화와 프로필 병합 중 발생한 중복·충돌을 사용자가 비교하고 선택할 수 있어야 한다. |
| REQ-15 | 3 | 대화형 입력 | 대화형 통증 기록은 지원 기기에서 로컬 모델로 처리하고 실행 불가 시 직접 입력으로 전환해야 한다. |

## 5. 계정 초대 및 연결 흐름

1. 기존 가족 구성원 로컬 프로필 선택
2. 서비스 계정 초대 발송
3. 초대받은 사용자의 로그인 또는 신규 가입
4. 초대 수락
5. 기존 로컬 프로필과 서비스 계정 연결
6. 공유할 건강정보와 접근 범위 확인
7. 사용자 기기 연결
8. 허용된 건강정보를 기기 간 암호화 전송
9. 초대받은 사용자의 기기에 로컬 저장

초대와 프로필 연결만으로 건강정보가 서버에 업로드되거나 서버에서 내려받아져서는 안 된다.

## 6. 중복 프로필 복구 요구사항

### 6.1 건강정보가 없는 새 프로필

- 서비스 계정 연결을 해제한다.
- 연결할 기존 로컬 프로필을 선택한다.
- 서비스 계정을 기존 프로필에 연결한다.
- 잘못 만든 빈 프로필을 삭제한다.

### 6.2 건강정보가 있는 새 프로필

- 병합 전에 자동 복구 지점을 생성한다.
- 기본정보, 건강기록, 원본 서류, 가족력과 메모를 비교한다.
- 중복·충돌 항목별로 유지할 값을 선택한다.
- 서비스 계정을 기존 프로필에 연결한다.
- 잘못 만든 프로필은 즉시 영구 삭제하지 않고 숨김 처리한다.
- 일정 기간 병합 취소를 제공한다.
- 병합 성공 확인 전까지 원본 데이터를 삭제하지 않는다.

하나의 서비스 계정은 같은 가정에서 하나의 가족 구성원 로컬 프로필에만 연결할 수 있다.

## 7. 비기능 요구사항

| ID | 구분 | 요구사항 |
|---|---|---|
| NFR-01 | 개인정보 | 서버는 건강정보 원문, 원본 건강서류, OCR 결과와 예측 결과를 저장하지 않아야 한다. |
| NFR-02 | 최소수집 | 서버에는 인증·구독·초대·프로필 연결·기기 상태에 필요한 최소 정보만 저장한다. |
| NFR-03 | 암호화 | 백업 파일과 기기 간 전송 데이터는 검증된 암호화 방식을 사용한다. |
| NFR-04 | 무결성 | 병합·복구·동기화 실패 시 기존 로컬 데이터를 변경하지 않거나 안전하게 롤백해야 한다. |
| NFR-05 | 감사 | 프로필 연결·병합과 건강정보 변경 이력은 사용자 기기에 기록한다. |
| NFR-06 | 사용성 | 주요 기능은 3~5회 이내의 행동으로 접근할 수 있어야 한다. |
| NFR-07 | 계정 해지 | 서비스 계정 해지나 구독 종료로 기기의 건강정보를 자동 삭제해서는 안 된다. |

## 8. 사용자 시나리오

### 시나리오 A — 가족 기록 시작

사용자가 서비스 계정으로 로그인하고 배우자와 자녀의 로컬 프로필을 만든 뒤 각 프로필에 건강기록을 저장한다.

### 시나리오 B — 가족 계정 연결

사용자가 배우자의 기존 로컬 프로필을 선택해 초대한다. 배우자는 새 서비스 계정을 만들고 초대를 수락한 뒤 기존 프로필에 연결한다. 건강정보는 별도의 접근 범위 확인과 기기 연결을 거쳐 전달된다.

### 시나리오 C — 잘못 만든 프로필 복구

초대받은 배우자가 실수로 새 프로필을 만든다. 시스템은 중복 가능성을 알리고 기존 프로필과의 비교·병합·되돌리기 흐름을 제공한다.

## 9. AI 검증 원칙

- 모델 학습은 비식별 공개 데이터셋으로 수행한다.
- 사용자의 로컬 건강정보는 모델 학습이나 외부 평가 데이터로 전송하지 않는다.
- 예측 모델은 train/validation 분리와 Accuracy, F1, AUROC, Recall 중 2개 이상의 지표로 검증한다.
- 동일 입력 반복 추론과 모델 버전 기록으로 결과 일관성을 확인한다.
- 실제 사용자 피드백은 원문을 수집하지 않고 기기 내 사용성 평가 또는 별도 동의 기반 비식별 방식으로만 검토한다.
