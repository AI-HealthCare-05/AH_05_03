# ADR-001: 데스크톱 앱에서 웹 기반 로컬 우선 서비스로 전환

- 상태: 대체됨 — 건강정보 저장·동기화 결정은 [ADR-011](0011-postgresql-health-data-and-server-ai.md) 참조
- 결정일: 2026-08-18
- 적용 대상: 이어봄 프론트엔드, 로컬 데이터 저장, 백업·복구, 기기 간 데이터 이전
- 관련 문서: [요구사항 정의서](../01_requirements.md), [ERD](../02_erd.md), [기술 아키텍처](../05_tech_architecture.md)
- 구버전 백업: [데스크톱 앱·Wi-Fi 직접 동기화 구버전 PRD](../legacy/desktop-app/2026-08-18-pre-web-prd.md)

## 1. 배경

초기에는 데스크톱 앱이 운영체제의 파일 시스템과 로컬 데이터베이스를 직접 사용하고, 같은 Wi-Fi 네트워크 안의 기기끼리 건강정보를 직접 동기화하는 방식을 검토했다. 이후 설치와 업데이트 부담을 줄이고 데스크톱과 모바일에서 같은 기능을 제공하기 위해 제품 제공 방식을 반응형 웹 서비스로 전환하기로 했다.

웹 전환 이후에도 중요한 건강정보를 서버에 저장하지 않는 로컬 우선 원칙은 유지한다. 이 결정에서 말하는 `웹 서비스`는 화면과 애플리케이션이 브라우저에서 실행된다는 뜻이며, 건강정보를 웹서버로 이전한다는 뜻이 아니다.

## 2. 결정

### 2.1 제품 제공 방식

- 네이티브 데스크톱 앱을 기본 제공 방식에서 제외하고 React·TypeScript 기반 반응형 웹 서비스로 제공한다.
- 설치형 사용 경험이 필요하면 동일 웹 애플리케이션을 PWA로 제공할 수 있지만, PWA 설치 여부에 따라 데이터 정책을 다르게 적용하지 않는다.
- FastAPI 서버는 인증, 구독·라이선스, 가족 초대와 최소 연결정보를 처리하며 건강정보 원문을 저장하지 않는다.

### 2.2 브라우저 로컬 저장

| 저장 영역 | 저장 대상 | 도입 시점 |
|---|---|---|
| IndexedDB | 가족 구성원 프로필, 건강기록, 가족력, 통증 기록, 파일 메타데이터, 변경 이력 | 초기 버전 |
| OPFS | PDF·건강서류 이미지·OCR 원본·로컬 AI 모델·DuckDB 파일 등 큰 바이너리 파일 | 원본 서류 기능부터 단계 도입 |
| 사용자 외부 파일 | IndexedDB와 OPFS 데이터를 묶은 암호화 백업·이전 파일 | 초기 버전 |
| PostgreSQL | 계정·인증·구독·라이선스·초대·최소 연결정보 | 서버 기능 |
| Redis | 인증·초대 만료, 속도 제한, 일회성 코드, 비건강정보 캐시·작업 상태 | 필요한 서버 기능 |

- 구조화 데이터의 기준 저장소는 IndexedDB로 한다.
- 큰 원본 파일은 OPFS에 한 번만 저장하고 IndexedDB에는 파일 식별자, 경로, 해시, 크기, MIME 타입과 연결된 프로필 정보만 저장한다.
- 초기 일정상 OPFS 도입이 지연되면 파일을 포함해 IndexedDB로 먼저 구현할 수 있지만, 저장소 인터페이스를 분리해 이후 파일만 OPFS로 이전할 수 있게 한다.
- OPFS에 보관한 백업 사본은 사이트 데이터 삭제 시 함께 사라질 수 있으므로 독립적인 백업으로 간주하지 않는다.

### 2.3 암호화와 백업

- 건강정보와 원본 파일은 저장 전에 Web Crypto를 사용해 암호화한다.
- 백업은 IndexedDB와 OPFS의 필요한 데이터를 하나의 버전이 있는 암호화 파일로 생성하고 사용자가 브라우저 밖으로 직접 내려받아 보관한다.
- 복구 시 사용자가 백업 파일을 직접 선택하고, 무결성·버전·암호 확인이 끝난 뒤 로컬 저장소에 반영한다.
- 브라우저의 영구 저장 요청은 데이터 삭제 가능성을 낮추는 보조 수단이며 백업을 대체하지 않는다.
- 시크릿 모드, 사이트 데이터 삭제, 저장 공간 부족과 브라우저 프로필 변경에 따른 데이터 손실 위험을 사용자에게 안내한다.

### 2.4 기기 간 데이터 이전과 동기화

- 초기 버전의 기기 이전·복구는 암호화 파일 내보내기와 가져오기를 기준 방식으로 한다.
- 같은 Wi-Fi 네트워크의 브라우저끼리 자동 발견·직접 동기화한다는 문구는 초기 버전의 제품 약속과 수락 기준에서 제거한다.
- WebRTC 기반 직접 전송은 제품 범위에서 삭제하지 않고 후순위 기술검증 항목으로 유지한다.
- WebRTC 검증에서는 별도 시그널링, 사용자 페어링, STUN·TURN 사용 여부, 중계 서버를 통한 암호문 통과, 모바일 백그라운드 연결 종료, 충돌 처리와 브라우저 호환성을 확인해야 한다.
- 검증을 통과하기 전에는 Wi-Fi 직접 동기화를 KPI나 핵심 차별점으로 사용하지 않는다.
- 자동 다중 기기 동기화가 필수가 되면 종단간 암호화된 서버 중계·보관으로 정책을 변경할지 별도 ADR로 결정한다.

## 3. 채택하지 않은 대안

### 3.1 네이티브 데스크톱 앱 유지

파일 시스템과 로컬 데이터베이스 접근은 용이하지만 설치·업데이트·운영체제별 배포 비용이 생기고 모바일과 동일한 경험을 제공하기 어렵다. 현재 제품 일정과 팀 구성에서는 웹 서비스의 접근성과 단일 코드베이스 이점이 더 크다고 판단했다.

### 3.2 IndexedDB만 영구 사용

초기 구현 단순성은 높지만 큰 PDF와 이미지가 누적될 때 파일 관리와 입출력 효율이 떨어질 수 있다. 초기 버전의 임시 선택으로는 허용하되 최종 저장 구조는 IndexedDB와 OPFS의 역할을 분리한다.

### 3.3 OPFS만 사용

원본 파일에는 적합하지만 건강기록 검색, 인덱스, 관계와 트랜잭션을 직접 구현해야 한다. 구조화 데이터 저장소로는 채택하지 않는다.

### 3.4 서버 건강정보 동기화

구현과 사용자 경험은 단순해지지만 서버에 건강정보를 저장하지 않는 현재 개인정보 원칙을 변경해야 한다. 초기 버전에서는 채택하지 않으며, 종단간 암호화 서버 동기화가 필요해지면 별도 정책·보안 검토와 ADR을 요구한다.

## 4. 결과와 영향

### 긍정적 영향

- 데스크톱과 모바일에서 같은 웹 애플리케이션과 데이터 정책을 사용할 수 있다.
- 건강정보 원문을 서버에 저장하지 않는 원칙을 유지한다.
- 구조화 데이터와 큰 파일을 각각 적합한 저장소에 둘 수 있다.
- 암호화 백업 파일이 브라우저 데이터 삭제와 기기 분실에 대한 독립적인 복구 수단이 된다.

### 부정적 영향과 대응

- 브라우저 데이터 삭제 시 로컬 데이터가 사라질 수 있으므로 첫 기록 이후와 정기적인 시점에 백업을 안내한다.
- IndexedDB와 OPFS는 하나의 원자적 트랜잭션을 공유하지 않으므로 파일 임시 저장, 해시 확인, 메타데이터 확정, 실패 파일 정리 순서로 일관성을 관리한다.
- 브라우저·기기별 저장 용량과 기능 차이를 탐지하고 지원되지 않는 기능은 파일 다운로드·가져오기 방식으로 대체한다.
- 초기 버전에는 자동 다중 기기 동기화가 없으므로 사용자가 백업·이전 파일을 직접 관리해야 한다.

## 5. 구현 단계

1. IndexedDB 스키마와 저장소 인터페이스를 정의한다.
2. Web Crypto 기반 레코드·백업 암호화 포맷과 키 복구 정책을 정의한다.
3. 암호화 백업 파일 내보내기·검증·가져오기를 구현한다.
4. 원본 건강서류 기능부터 OPFS 저장 어댑터를 도입한다.
5. 저장 공간 부족, 사이트 데이터 삭제, 시크릿 모드와 백업 미실행 상태를 안내한다.
6. 후순위로 WebRTC 직접 전송의 기술검증을 수행하고 채택 여부를 별도 결정한다.

## 6. 문서 적용 규칙

- PRD, 요구사항, 유저플로우와 와이어프레임에서 웹 서비스와 웹서버를 구분한다.
- `웹서버에 저장`과 `브라우저 로컬 저장`을 같은 의미로 사용하지 않는다.
- 초기 버전의 데이터 이전·복구는 암호화 파일 내보내기·가져오기로 표현한다.
- Wi-Fi 직접 동기화는 확정 기능이 아니라 후순위 기술검증 항목으로 표기한다.
- OPFS 내부 사본은 외부 백업으로 표현하지 않는다.
