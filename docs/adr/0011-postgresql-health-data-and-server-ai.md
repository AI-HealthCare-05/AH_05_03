# ADR-011: PostgreSQL 건강정보 정본과 서버 AI 처리로 전환

- 상태: 승인
- 결정일: 2026-09-04
- 적용 대상: 사용자·가족 건강정보, 건강문서와 OCR 결과, ML 예측, AI 질의와 도구 호출, 다중 기기 동기화
- 대체 결정: [ADR-001](0001-web-local-first-architecture.md)의 건강정보 로컬 정본·서버 미전송 결정, [ADR-002](0002-separate-server-api-and-local-domain-contract.md)의 Local Domain 경계, [ADR-005](0005-vite-spa-local-first-frontend-foundation.md)의 로컬 건강정보·로컬 추론 경계, [ADR-007](0007-account-scoped-encrypted-local-vault.md)
- 부분 대체: [ADR-008](0008-temporary-cloud-ocr-baseline.md)의 서버 비저장·브라우저 보관함 저장 조항. 제3자 OCR 전송 고지·동의·비밀값 관리·사용자 검토 원칙은 유지한다.
- 관련 문서: [ERD](../02_erd.md), [API 명세](../03_api_spec.md), [기술 아키텍처](../05_tech_architecture.md), [로컬 데이터 계약](../10_local_data_contract.md), [ML 모델 계획](../09_chronic_disease_model_plan.md)

## 배경

이어봄은 사용자의 건강정보를 서버로 전송하거나 저장하지 않는다는 전제에서 IndexedDB·OPFS·Web Crypto 기반 로컬 우선 구조를 채택했다. 이 구조는 서버의 건강정보 보유 범위를 최소화하지만 다음 요구를 충족하는 데 지속적인 제약이 됐다.

- 모바일과 PC에서 같은 계정의 최신 기록을 일관되게 조회하기 어렵다.
- 팀원이 동일한 계정과 데이터로 가입부터 기록 입력, OCR, 예측, 챌린지와 챗봇까지 전체 흐름을 검증하기 어렵다.
- ML 입력·예측 결과와 사용자 피드백을 일관된 데이터 계보로 관리하기 어렵다.
- “차트 보여줘” 같은 로컬 조회를 넘어, 인증된 사용자의 건강정보와 현재 상황을 불러와 판단하는 AI 도구 호출을 구현하기 어렵다.
- 브라우저 데이터 삭제, 기기 분실, 계정 전환과 로컬 보관함 복구를 제품이 직접 책임져야 한다.

이 프로젝트의 현재 목표는 로컬 전용 제품의 완성보다, 일반적인 웹 서비스 구조에서 개인정보를 보호하면서 PostgreSQL, OCR, ML과 AI 도구 호출을 하나의 서비스 흐름으로 깊이 있게 구현하고 검증하는 포트폴리오를 만드는 것이다. 이 목표 변경으로 “건강정보 서버 미전송”은 더 이상 유지해야 할 최상위 제약이 아니다.

## 결정

### 1. PostgreSQL을 건강정보의 정본으로 사용

- 서비스 계정, 가족 구성원 프로필, 건강기록, 가족력, 통증 기록, OCR 확정값, 예측 결과, 챌린지와 AI 기능에 필요한 구조화 데이터를 PostgreSQL에 저장한다.
- 모든 건강정보는 인증된 서버 API를 통해 읽고 쓴다. 서버는 요청마다 계정·가정·프로필 소유권과 공유 권한을 검사한다.
- 모바일과 PC는 동일한 서버 정본을 사용한다. 충돌은 서버 버전, 갱신 시각과 낙관적 잠금 규칙으로 처리한다.
- PostgreSQL 마이그레이션을 저장 구조의 계약으로 취급하고 개발·CI·배포 환경에 같은 순서로 적용한다.
- Redis는 세션 보조, 속도 제한과 짧은 작업 상태에만 사용하며 건강정보의 정본으로 사용하지 않는다.

### 2. IndexedDB와 로컬 보관함을 정본에서 제외

- IndexedDB·OPFS 기반 Local Domain API와 계정별 암호화 보관함을 신규 기능의 기준 저장소로 사용하지 않는다.
- 화면 상태와 재요청 가능한 서버 응답 캐시는 메모리 또는 제한된 클라이언트 캐시를 사용할 수 있다. 건강정보를 장기 영속 캐시에 저장하려면 저장 범위, 만료, 로그아웃 삭제와 암호화를 별도로 정의해야 한다.
- 기존 IndexedDB 데이터는 즉시 삭제하지 않는다. 사용자 확인을 거친 일회성 서버 이전 경로를 제공하고, 성공 응답과 레코드 수를 검증한 뒤 로컬 사본 정리 여부를 선택하게 한다.
- 이전 요청은 멱등키를 사용해 재시도 시 중복 레코드를 만들지 않는다. 레거시 ID와 서버 ID의 대응 및 실패 내역을 기록한다.

### 3. 개인정보 보호 수단을 서버 저장 구조에 맞게 변경

서버 저장 허용은 개인정보 보호를 포기한다는 뜻이 아니다. 보호 목표를 “서버에 보내지 않음”에서 다음 통제로 바꾼다.

- 수집 목적에 필요한 필드만 저장하고 식별정보와 건강정보의 논리적 경계를 둔다.
- 전송 구간은 TLS를 사용하고, 데이터베이스·백업·문서 저장소는 배포 환경의 저장 시 암호화를 적용한다.
- API 응답은 현재 사용자에게 허용된 필드만 직렬화하며 IDOR를 막는 소유권·가정 멤버십 검사를 둔다.
- 비밀번호, 토큰, 원본 문서, OCR 전문, 건강정보와 AI 프롬프트 원문을 애플리케이션 로그·프록시 로그·오류 추적·분석 도구에 남기지 않는다.
- 보존 기간, 사용자 다운로드, 정정, 삭제와 계정 탈퇴 시 처리 범위를 정의한다. 백업에서의 만료 시점도 문서화한다.
- 외부 AI·OCR 제공자에게 보낼 때는 목적과 제공자를 고지하고 필요한 경우 동의를 받으며, 가능한 범위에서 이름·연락처·식별자를 제거하거나 가명화하고 최소 필드만 전송한다.
- 개발·데모에서는 합성 또는 비식별 데이터를 기본으로 사용한다. 실제 개인정보를 사용하기 전에는 개인정보 처리방침, 동의, 위수탁·제3자 제공, 접근 통제와 사고 대응을 별도로 검토한다.

### 4. RAG와 AI는 서버 도구 호출 중심으로 구현

- 단순 기록·차트 조회는 일반 API 조회로 처리하고 RAG라고 부르지 않는다.
- 개인화 AI 질문은 인증된 서버가 사용자의 의도를 해석한 뒤 허용된 도구를 호출하는 방식으로 구현한다.
- 첫 수직 기능은 “내 건강 상태에서 오늘 술을 마셔도 돼?”로 한다. 최근 건강기록, 복약·질환 정보와 필요한 외부 상황 정보를 도구로 조회하고, 사용한 근거와 한계를 답변에 함께 제시한다.
- 모델이 SQL을 직접 실행하거나 임의의 사용자 ID를 지정하게 하지 않는다. 도구는 서버가 확정한 계정·프로필 범위와 입력 스키마 안에서만 동작한다.
- 벡터 데이터베이스는 비정형 문서 검색의 필요성과 평가셋이 준비된 뒤 도입한다. 현재 우선순위는 PostgreSQL 개인정보 조회와 외부 정보 조회 도구다.
- 프롬프트, 도구 인자와 응답의 저장 여부·마스킹·보존 기간을 운영 로그와 분리해 결정한다.

### 5. ML 예측은 서버 데이터 계보와 평가 근거를 보존

- 학습 데이터셋의 출처와 선택 배경, 코호트 조건, 표본 수, 특징, 결측치 처리와 라이선스를 기록한다.
- NHANES 등 미국 데이터를 사용할 경우 데이터 규모와 접근성뿐 아니라 국내 사용자에 대한 대표성 한계를 명시한다.
- 학습·검증·테스트 분할과 테스트셋 규모를 고정하고 ROC-AUC, PR-AUC, 민감도, 특이도와 calibration 결과를 기록한다.
- 예측 결과에는 모델 버전, 입력 스냅샷의 버전, 실행 시각과 평가 대상 기간을 연결한다.
- 연령이 장기 예측을 과도하게 지배하는지 확인하고, 10년 예측과 5년 이내 발병 확률 중 설명력과 제품 목적에 맞는 기간을 비교한다.
- 예측은 의료 진단이 아니며 불확실성, 제한사항과 의료기관 상담 기준을 사용자에게 표시한다.

## 검토한 대안

### 로컬 우선 구조를 유지하고 기능만 추가

기각한다. 개인정보의 서버 보유 범위는 작지만 다중 기기 동기화, 동일 계정 QA, 서버 ML과 개인화 AI 도구 호출을 위해 별도의 암호화 이전·중계·충돌 해결 구조를 계속 만들어야 한다. 남은 프로젝트 기간과 포트폴리오 목표에 비해 핵심 기능보다 저장 경계에 과도한 비용이 든다.

### 서버에는 비식별 특징값과 예측 결과만 저장

보류한다. ML 실행 범위는 줄일 수 있지만 건강기록 조회와 설명 가능한 AI 답변을 위해 원본과 특징 사이의 복잡한 동기화가 다시 필요하다. 추후 실제 운영에서 데이터 최소화 요구가 커지면 기능별로 재검토한다.

### 종단간 암호화한 데이터를 서버에 저장

현재는 기각한다. 서버가 평문을 볼 수 없어 개인정보 노출 면적은 줄지만 서버 ML, OCR 후처리와 AI 도구 호출이 곤란하고 키 복구·공유·검색 설계가 추가된다. 암호화 검색 또는 클라이언트 추론이 핵심 목표가 되면 별도 ADR에서 재검토한다.

### 벡터 데이터베이스부터 도입

보류한다. 현재의 개인화 질문은 구조화된 최신 건강기록을 정확한 권한 범위로 조회하는 것이 우선이다. 검색 품질을 측정할 문서 집합과 평가 질문이 생기기 전에는 PostgreSQL 도구 호출로 시작한다.

## 결과와 감수할 단점

### 긍정적 영향

- 같은 계정의 모바일·PC 데이터가 자동으로 일치한다.
- 가입, 건강기록/OCR, 예측, 챌린지와 챗봇의 A부터 Z까지를 배포 환경에서 재현할 수 있다.
- ML 입력과 결과의 버전·계보를 서버에서 일관되게 관리할 수 있다.
- AI가 권한이 검증된 최신 건강정보를 도구로 조회해 개인화된 추론을 수행할 수 있다.
- 브라우저 저장소 삭제나 교체가 건강정보 정본의 손실로 이어지지 않는다.

### 부정적 영향과 대응

- 서버 침해 시 개인정보 영향 범위가 커진다. 최소 수집, 접근 통제, 암호화, 비밀 관리, 로그 필터링, 백업 정책과 삭제 절차를 필수 구현 범위에 포함한다.
- 개인정보 처리방침·동의·보존·제3자 제공에 대한 설명 책임이 증가한다. 포트폴리오 데모와 실제 운영의 데이터 정책을 구분하고 실제 운영 전 법률·보안 검토를 진행한다.
- 기존 로컬 데이터 이전 중 중복·충돌·부분 실패가 발생할 수 있다. 멱등 업로드, 건수 대조, 실패 재시도와 이전 완료 표시를 제공한다.
- 네트워크 장애 시 전체 기능을 사용할 수 없을 수 있다. 조회 캐시와 재시도는 허용하되 서버 정본과 충돌하지 않는 범위로 제한한다.
- 외부 AI 제공자에게 전달되는 정보가 새로운 처리 경로가 된다. 서버에서 마스킹·최소화를 수행하고 제공자·목적·보존 정책을 문서화한다.

## 이행 순서

1. PostgreSQL에 프로필·건강기록·문서/OCR·예측·챌린지 스키마와 소유권 제약을 추가한다.
2. FastAPI CRUD와 계정·가정·프로필 권한 검사를 구현한다.
3. 프론트엔드 조회·저장을 서버 API와 TanStack Query로 전환한다.
4. 기존 IndexedDB 데이터를 멱등하게 업로드하는 일회성 이전 기능을 구현한다.
5. OCR 확정값과 ML 예측 결과를 서버 정본에 연결한다.
6. 건강정보 조회와 외부 상황 조회를 사용하는 최소 AI 도구 호출을 구현한다.
7. 로그 마스킹, 삭제·보존, 백업 복구와 다중 기기 동기화 E2E 테스트를 추가한다.
8. `01_requirements`, ERD, API/OpenAPI, 기술 아키텍처, 로컬 데이터 계약, 화면/API 매핑과 개인정보 안내를 ADR-011에 맞게 갱신한다.

## 재검토 조건

- 실제 운영 또는 기관 도입으로 법적·계약상 서버 저장 제한이 생긴다.
- 민감정보 규모와 위협 모델 때문에 필드 암호화, 별도 데이터 저장소 또는 종단간 암호화가 필요해진다.
- 오프라인 사용이 핵심 요구가 되어 로컬 복제와 충돌 없는 동기화가 필요해진다.
- 외부 AI 없이 온프레미스·자체 모델로 처리해야 하는 요구가 생긴다.
- 비정형 건강문서 검색의 평가셋과 품질 기준이 준비되어 벡터 검색을 비교할 수 있게 된다.

## 한 문장 요약

> 이어봄은 건강정보 서버 미전송과 IndexedDB 정본 원칙을 폐기하고, 개인정보 최소화·마스킹·권한 통제를 전제로 PostgreSQL을 정본으로 사용해 다중 기기 동기화, ML과 개인화 AI 도구 호출을 구현한다.
