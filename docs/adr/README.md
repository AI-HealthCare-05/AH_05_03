# Architecture Decision Records

ADR은 당시의 선택뿐 아니라 선택하지 않은 방향과 그 이유를 보존한다. 시간이 지나 담당자가 바뀌어도 같은 논의를 근거 없이 반복하거나, 이미 기각한 설계를 다시 도입하지 않게 하는 것이 목적이다.

## 작성 원칙

- 승인된 ADR의 결정과 근거를 덮어쓰지 않는다.
- 결정을 변경할 때는 기존 ADR을 수정하는 대신 새 번호의 ADR을 작성하고 대체 대상을 명시한다.
- 구현 파일, 클래스, 함수와 작업 순서보다 오래 유지되는 설계 이유를 기록한다.
- 채택한 대안과 함께 검토한 대안, 기각·보류 이유와 예상 위험을 남긴다.
- 영구적인 기각과 현재 조건에서의 보류를 구분한다.
- 전제가 바뀌었을 때 다시 판단할 수 있도록 재검토 조건을 명시한다.
- 장문의 요구사항이나 API 명세를 복제하지 않고 관련 문서에 연결한다.

## 권장 구성

1. 상태와 결정일
2. 배경과 결정해야 할 문제
3. 결정
4. 검토한 대안과 기각·보류 이유
5. 결정의 결과와 감수할 단점
6. 재검토 조건
7. 한 문장 요약

오탈자나 깨진 링크처럼 의미를 바꾸지 않는 정정 외에는 승인된 ADR을 편집하지 않는다.
