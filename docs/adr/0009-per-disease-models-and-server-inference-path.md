## 배경

멘토가 물은 것은 "고혈압·당뇨 모델을 각각 둘지, 앞단 분류기나 앙상블로 라우팅할지"였다. 이 질문에는 서로 다른 세 개가 섞여 있어 갈라서 답해야 한다.

1. 질환을 고르는 앞단 라우터가 필요한가
2. 여러 모델을 앙상블로 묶을 것인가
3. 그 추론이 어디에서 실행되는가

세 번째가 가장 크다. 지금까지의 문서는 건강 모델 실행을 사용자 기기 안에 두는 것을 전제로 썼고, 11번 문서 §2는 원격 FastAPI와 서버 AI worker를 실행 위치에서 아예 금지했다. 멘토가 설명한 `nginx → FastAPI → PostgreSQL → Redis → ai-worker`는 그 금지와 정면으로 부딪힌다. 결정하지 않고 놔두면 모델 구조 결정도 의미가 없다 — 실행 위치가 바뀌면 번들 포맷, 지연 예산, 실패 처리가 전부 다시 잡힌다.

### 지금 저장소에 실제로 있는 것

| 구성 | 실물 | 상태 |
|---|---|---|
| E1 규칙 엔진 | `chronic_disease_engine/` (vendored, `PROVENANCE.md`가 수정 금지) | 동작. 9개 영역 판정 |
| E2 ML | `app/services/risk.py` — 로지스틱 JSON 계수 + `SeedEnsembleRiskModel` | 동작. 번들 20개가 `modeling/artifacts/models_ensemble/` |
| E3 공개공식 | 없음 | 미착수 (대사증후군 카운트·eGFR·HSI·Lee 2012) |
| 수치→질환 매트릭스 | `app/services/disease_risk_matrix.py` | 동작. 질환 축 4개 |
| 수치 단계 판정 | `app/services/lab_staging.py` | 동작 |
| **중재자** | **없음** | 지금 이 판단을 데모 화면의 클라이언트 JS가 한다 |
| 비동기 워커 | `ai_worker/` 골격 (config·logger·main·tasks 빈 껍데기), `app/workers/`에는 초대 메일 워커만 | 미착수 |

중재자가 없는 것이 이 ADR이 메우는 가장 큰 구멍이다. "검사값이 있으면 규칙, 없으면 ML"이라는 판단이 이미 제품 동작인데 정본이 화면 스크립트에 있다.

### 판단에 쓴 실측치

당뇨 AUROC 0.810, 고혈압 0.796. 모든 연령 구간에서 당뇨가 낫다. 그리고 고혈압 모델은 `sbp`·`dbp`를 입력으로 받지 않는다 — 라벨이 `SBP≥140 or DBP≥90`이라 학습에서 차단했다. 54세 남성 기준으로 혈압을 118/74에서 175/110으로 바꿔도 확률이 소수점까지 고정이다. 정당한 누출 차단의 필연적 결과이고, 이 ADR은 그 사실을 없애는 대신 검사값이 들어온 순간 정본을 규칙 엔진으로 넘기는 쪽으로 답한다.

## 결정

### 1. 질환별 독립 모델을 유지한다. 앞단 질환 분류기는 두지 않는다

고혈압과 당뇨는 동시에 존재할 수 있다. 하나를 골라야 하는 상호 배타 문제가 아니므로 라우터가 앉을 자리가 없다. 화면도 질환 카드를 동시에 그린다.

### 2. 멀티태스크 공유 표현을 기각한다

라벨 누출 차단 집합이 질환마다 다르다. 당뇨는 FPG·HbA1c, 고혈압은 SBP·DBP, 이상지질혈증은 지질 4종을 각각 막아야 한다. 하나의 공유 은닉층으로 묶으면 어느 타깃의 금지 피처가 다른 타깃에서 허용되는 상태가 표현 안에서 뭉개진다. 차단 집합이 감사 가능해야 하고, 그건 모델이 질환별로 분리되어 있을 때만 성립한다.

### 3. 앙상블의 적용 범위를 질환 안으로 한정한다

앙상블은 `질환 A와 B 중 하나를 고르는 라우터`가 아니다. **같은 질환을 예측하는 멤버들을 합치는 용도로만 쓴다.**

- 채택: 질환 하나당 XGBoost 3시드 + CatBoost 3시드. 번들 20개(10질환 × 일반형·정밀형)가 이미 나와 있다.
- 근거: AUROC로만 보면 시드 앙상블은 아무것도 하지 않는다(중앙 ΔAUROC +0.0020). 채택 근거는 판별력이 아니라 **재현성**이다. 시드를 바꾸면 개인별 확률이 흔들리는데, 이 제품은 그 확률에서 백분위·등급·경보가 전부 파생된다.
- 감수하는 비용: 번들이 gzip 기준 2.3 MB → 7.2 MB (3.1배). 채점은 1.3 ms/명으로 순수 파이썬 계약을 유지한다.
- 기각: 질환 간 스태킹. 메타러너가 질환 경계를 넘어 정보를 옮기면 2번의 차단 집합 논리가 무너진다.

### 4. 라우팅의 대상은 질환이 아니라 엔진이다

필요한 것은 질환 라우터가 아니라 **엔진 중재자**다. 규칙과 ML은 경쟁 관계가 아니라 순서 관계다.

| 질환 | 검사값 있음 | 검사값 없음 |
|---|---|---|
| 고혈압 | E1 규칙 (정본) | E2 ML — "재면 기준을 넘을 가능성" |
| 당뇨 | E1 규칙 (정본) | E2 ML + E3 한국인 점수 병기 |
| 이상지질혈증 | E1 규칙 | E2 ML 선별 (P1) |
| 비만·복부비만 | E1 규칙 | 키·몸무게만 있으면 항상 E1 |
| 대사증후군 | E3 (5요소 카운트) | 부분 카운트만 표시 |
| 지방간 | E3 (HSI) | 표시하지 않음 |
| 신기능 | E3 (eGFR) | 표시하지 않음 |

정본은 `app/services/assessment.py`(신규)에 둔다. 응답에는 질환마다 `engine`, `engine_reason`, `superseded_by`를 싣는다. 화면은 어느 엔진이 답했는지와 왜 그 엔진인지를 읽을 수 있어야 한다.

### 5. 등급 체계를 규칙 엔진의 5단계로 통일한다

ML은 3단계(low/moderate/high), 규칙은 5단계(NORMAL/CAUTION/HIGH/VERY_HIGH/INSUFFICIENT_DATA)를 쓰고 두 체계에서 "주의"가 서로 다른 등급을 가리킨다. 규칙 5단계를 정본으로 삼고 ML 백분위를 사상한다(≥90 → HIGH, 70~90 → CAUTION, 그 외 NORMAL, 참조표 없으면 INSUFFICIENT_DATA). 벤더 엔진 파일은 건드리지 않고 어댑터에서만 변환한다.

### 6. 추론은 서버에서 실행한다

`nginx → FastAPI → PostgreSQL → Redis → ai-worker`를 사용자 작업 요청의 표준 경로로 채택한다. 11번 문서 §2의 금지 두 행은 이 결정으로 대체된다.

### 7. 동기 경로와 비동기 경로를 지연으로 가른다

같은 서버 경로 안에서도 큐를 타는 작업과 타지 않는 작업을 나눈다. 기술을 썼다는 사실이 아니라 지연과 실패 처리가 기준이다.

| 작업 | 경로 | 근거 |
|---|---|---|
| 만성질환 위험 판정 (E1·E2·E3 중재) | FastAPI 인프로세스 동기 응답 | 순수 파이썬 채점 1.3 ms/명. 큐를 태우면 직렬화·폴링 왕복이 본 작업보다 커진다 |
| 건강문서 OCR | Redis 큐 → ai-worker | 외부 API 의존, 초 단위 지연, 재시도가 필요 |
| 챗봇·RAG 생성 | Redis 큐 또는 스트리밍 | 토큰 단위 응답. SSE 적용 대상 |
| 배치 재계산·재보정 | Redis 큐 → ai-worker | 요청-응답 수명과 무관 |

판정 규칙: **p95 응답이 300 ms 미만이고 외부 의존과 재시도가 없으면 동기.** 하나라도 어기면 비동기.

### 8. 화면이 붙는 진입점은 하나다

`POST /v1/assessments/summary`. 온보딩 입력 한 벌을 받아 질환별 통합 결과를 낸다. 기존 `/v1/predictions/risk`와 `/v1/assessments/rules`는 디버깅·엔진 비교용으로 남긴다.

### 9. 모델 서버를 별도 프로세스로 분리하지 않는다

채점이 JSON 계수와 순수 파이썬 내적이다. sklearn·numpy·torch 런타임 의존이 0이므로 FastAPI 프로세스 안에서 그대로 돈다. 별도 추론 서버를 세우면 배포 단위와 네트워크 홉만 늘고 얻는 것이 없다. 분리 조건은 재검토 조건에 적었다.

### 10. 저장 정책은 이 ADR이 건드리지 않는다

추론과 저장은 다른 문제다. FastAPI는 요청 본문으로 받은 값을 메모리에서 채점하고 응답한다. 건강 수치를 PostgreSQL·Redis·요청 로그·APM payload에 쓰는 것은 ADR-002의 경계에 그대로 남고, 필요하면 동의·보관기간·삭제 보증을 담은 별도 ADR로 결정한다.

구현 선행 조건이 하나 있다. 현재 서버 예측 라우터는 무인증으로 건강 수치를 요청 본문에 받는다. 인증과 레이트리밋을 붙이기 전에는 이 경로를 `/api/v1`에 공개하지 않는다.

## 검토한 대안

### 앞단 질환 분류기로 모델을 고르기

기각한다. 질환이 상호 배타가 아니다. 화면이 카드를 동시에 그리므로 고를 일이 없고, 라우터를 두면 오분류가 곧 카드 누락이 된다.

### 멀티태스크 단일 모델

기각한다. 질환별 누출 차단 집합이 공유 표현에서 뭉개진다. 파라미터 공유로 얻을 표본 효율도 이 데이터에서는 근거가 약하다 — 표본을 두 배로 늘렸을 때 AUROC가 0.002 움직였다. 천장은 표본이 아니라 정보량이다.

### 질환 간 스태킹 앙상블

기각한다. 3번과 같은 이유이고, 메타러너 학습에 홀드아웃을 한 겹 더 써야 해서 남은 3주 안에 평가가 성립하지 않는다.

### 예측도 Redis 큐로 넘기기

기각한다. 1.3 ms 작업에 큐를 붙이면 사용자가 체감하는 지연이 늘고, 폴링 또는 SSE 상태 관리 코드가 얻는 것 없이 생긴다. 큐를 쓸 자리는 OCR과 LLM이다.

### 브라우저 전용 실행 (TypeScript 계수 · ONNX Runtime Web · Rust/WASM)

보류한다. 데이터 경계로는 가장 깨끗하지만 유사 모델 10개를 두 언어로 유지하면 구현이 즉시 두 배가 되고, 모델 오류와 포팅 오류를 동시에 추적해야 한다. 배포까지 3주다. 11번 문서의 동등성 검증 계약(같은 입력 → 같은 결과)은 유지하고, 브라우저 구현은 재검토 조건을 충족할 때 착수한다.

### 별도 추론 서버 프로세스 (TorchServe·BentoML·Triton 등)

보류한다. 지금 번들이 JSON이고 채점이 순수 파이썬이다. GPU도, 모델 로딩 지연도, 프레임워크 런타임도 없으니 분리할 대상이 없다.

### 종합 건강 지수 하나로 합치기

보류한다. 벤더 규칙 엔진이 "영역을 하나의 종합 점수로 합치지 않는다"를 설계 원칙으로 못 박았다(`engine.py` docstring). 링 게이지는 "n개 영역 판정 완료" 진행 표시로 대체한다.

## 결과와 감수할 단점

- 엔진 중재의 정본이 화면 스크립트에서 서버로 올라온다. 검사값을 넣었을 때 결과가 실제로 바뀌는 계약을 골든 픽스처로 고정할 수 있다.
- 사용자가 검사값을 다 넣으면 7개 영역, 0개면 4칸을 본다. 지금은 각각 4개와 2개다.
- 워커·Redis·SSE를 "왜 여기에만 썼는지"로 설명할 수 있다. 전부에 붙이지 않은 것이 설명의 내용이 된다.
- 번들이 3.1배 커진다. 판별력이 아니라 재현성을 산 값이다.
- 로컬 우선 서술의 범위가 줄어든다. 저장은 여전히 기기 안이지만 추론 입력은 서버를 통과한다. 제품 설명 문구와 개인정보 처리 안내를 이 결정에 맞춰 다시 써야 한다.
- 서버가 건강 수치를 요청으로 받는 순간 인증·레이트리밋·로그 마스킹이 선택이 아니라 선행 작업이 된다.
- 브라우저 추론을 보류했으므로 ADR-001의 로컬 우선 원칙 중 "평가 실행" 부분은 이 릴리스에서 달성하지 않는다. 미달성을 미결정으로 적지 않고 미달성으로 적는다.

## 재검토 조건

- 개인정보가 포함된 실제 건강문서·수치를 서버가 받는 것이 제품 요구가 되어 저장·보관·삭제 결정이 필요해진다.
- 브라우저 구현의 동등성 검증이 자동화되고 유사 모델의 입력·출력·임상 규칙이 안정된다. 그때 5번·6번을 다시 판단한다.
- 채점이 순수 파이썬 계약을 벗어난다(트리 수 급증, GPU 필요, 프레임워크 런타임 의존 발생). 그때 9번을 다시 판단한다.
- 위험 판정 p95가 300 ms를 넘는다. 그때 7번의 경로 배치를 다시 판단한다.
- 발병 라벨(incident) 데이터를 확보해 ML 타깃 정의가 바뀐다. `label_kind`가 `prevalent`에서 `incident`로 갈 때 확률의 의미가 조용히 바뀌지 않게 한다.

## 한 문장 요약

> 질환별 독립 모델을 유지하고 앙상블은 같은 질환 안의 시드 앙상블로만 쓰며, 라우팅은 질환이 아니라 엔진(검사값 있으면 규칙, 없으면 ML·공식)에 적용하고, 추론은 FastAPI 안에서 동기로 실행하되 OCR·챗봇처럼 느리고 재시도가 필요한 작업만 Redis 큐와 ai-worker로 보낸다.
