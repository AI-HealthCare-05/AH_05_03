# ADR-007: 공용 브라우저에서 계정별 암호화 로컬 보관함 분리

- 상태: 대체됨 — IndexedDB 정본·로컬 보관함 결정은 [ADR-011](0011-postgresql-health-data-and-server-ai.md) 참조
- 결정일: 2026-08-20
- 적용 대상: 브라우저 로컬 프로필·건강기록·원본 문서·복호화 키, 서비스 계정 전환, 초대 수락과 기기 연결
- 관련 결정: [ADR-001](0001-web-local-first-architecture.md), [ADR-002](0002-separate-server-api-and-local-domain-contract.md), [ADR-006](0006-lifecycle-scoped-profile-reference.md)

## 배경

현재 구현은 같은 Origin에서 고정된 IndexedDB `ieobom-local`, OPFS 디렉터리와 비추출형 `CryptoKey`를 사용한다. 이 구조는 서버로 건강정보를 보내지 않는다는 목표는 충족하지만, 같은 OS·브라우저 프로필을 여러 사람이 공유할 때 사용자 간 경계를 만들지 못한다.

실제 변경 계기는 가족이 고성능 데스크톱 한 대와 같은 브라우저 프로필을 함께 사용하는 상황이다. `kor` 계정으로 가족 프로필과 건강기록을 만든 뒤 로그아웃하고 `se` 또는 `evophygene` 계정으로 로그인해도, 브라우저가 같은 IndexedDB·OPFS와 키를 다시 열어 이전 기록을 그대로 표시했다. 카드의 `본인` 관계는 건강기록의 대상일 뿐 현재 로그인한 서비스 계정의 신원을 뜻하지 않으므로 이 문제를 해결하지 못한다.

이는 화면 표시 오류가 아니라 로컬 저장 경계의 결함이다. 계정 이름 배지나 목록 필터만 추가하면 데이터와 복호화 키는 여전히 같은 브라우저 컨텍스트에서 열려 있다.

## 결정

- 건강정보의 로컬 저장 단위를 Origin 전체가 아니라 **암호화 로컬 보관함(vault)** 으로 정의한다.
- 보관함은 무작위 `vaultId`, 독립된 IndexedDB 이름, 독립된 OPFS 경로와 별도 DEK를 가진다. 이메일·이름을 DB명이나 파일 경로에 사용하지 않는다.
- 서비스 계정과 보관함의 관계는 이 기기의 비민감 레지스트리에만 기록한다. 서비스 계정 로그인만으로 보관함을 자동 복호화하지 않는다.
- 보관함 DEK는 로컬 잠금 수단으로 보호한다. 서비스 계정 비밀번호를 DEK 또는 키 파생 입력으로 직접 사용하지 않는다. 구체적인 PIN·복구 암호·패스키 조합과 복구 정책은 별도 결정으로 확정한다.
- 로그아웃·계정 전환·계정 종료 시 열린 저장소와 Worker를 닫고, 복호화된 상태와 메모리 키를 폐기하며 모든 탭에서 이전 보관함을 잠근다.
- 초대 수락은 서비스 계정과 발신자가 지정한 불투명 프로필 참조를 연결할 뿐이다. 수신 기기의 보관함을 열거나 발신 기기의 건강정보를 자동 노출하지 않으며, 상태는 `계정 연결 완료·기기 연결 대기`가 된다.
- 허용된 건강정보는 암호화 이전 파일 가져오기 또는 향후 승인된 직접 전송을 거쳐 수신자의 열린 보관함에 새로 저장한다.
- 계정 없이 쓰는 로컬 전용 보관함은 유지할 수 있지만 서비스 계정 보관함과 명시적으로 구분하고 같은 화면에서 자동 합치지 않는다.
- 기존 단일 `ieobom-local` 데이터는 **소유자 미지정 레거시 보관함**으로 취급한다. 최근 로그인 계정이나 최초 로그인 계정에 자동 귀속하지 않고, 백업과 소유자 확인을 거친 명시적 이전만 허용한다.
- 계정별 보관함과 잠금이 구현되기 전까지 같은 브라우저 프로필을 여러 사람이 공유하는 사용 방식은 지원하지 않는다. 제품 화면도 이를 안전한 구성처럼 표현하지 않는다.

## 검토한 대안

### 현재 단일 보관함을 유지하고 별도 OS·브라우저 프로필 사용을 안내

기본 대안으로 기각한다. 브라우저 프로필 분리는 방어층으로는 유효하지만 서비스가 강제할 수 없고, 가정용 공용 PC라는 정상 사용 상황에서 한 번의 실수로 기록이 노출된다.

### 로그인 계정에 해당하지 않는 카드만 화면에서 숨김

기각한다. UI 필터는 IndexedDB·OPFS와 복호화 키 접근을 차단하지 않는다. 개발자 도구, 다른 화면 또는 구현 실수로 데이터가 다시 나타날 수 있어 보안 경계가 아니다.

### 계정 ID를 IndexedDB 이름 앞에 붙여 논리적으로만 분리

기각한다. 목록 혼합은 줄지만 같은 Origin에서 각 DB와 자동 사용 가능한 키를 열 수 있고 OPFS 경계도 남는다. 식별 가능한 계정값이 저장 경로에 노출될 수 있으며 로그아웃 시 복호화 권한도 회수되지 않는다.

### 하나의 가정 공용 보관함을 모든 계정이 함께 사용

기각한다. 유전정보·가족력·입양 관련 정보처럼 구성원별로 숨겨야 하는 데이터에 최소 권한을 적용할 수 없다. 향후 명시적 공용 데이터 공간이 필요하면 개인 보관함과 분리된 새 결정으로 검토한다.

### 서비스 계정 비밀번호로 로컬 데이터를 직접 암호화

기각한다. 비밀번호 변경·재설정·계정 해지가 로컬 복호화와 결합되고 서버 인증 정책이 로컬 데이터의 수명과 복구 가능성을 결정하게 된다. 서비스 계정과 건강정보 저장을 분리한다는 원칙에도 어긋난다.

### 건강정보를 서버에 올리고 서버 권한으로 사용자별 접근을 제어

기각한다. 접근 제어는 단순해지지만 건강정보를 서버에 저장하지 않는 제품의 핵심 데이터 경계를 뒤집는다.

### 기존 단일 보관함을 다음 로그인 계정에 자동 귀속

기각한다. 공용 PC에서 우연히 먼저 로그인한 사람이 다른 가족의 기록 소유자로 확정되는 더 큰 사고를 만든다.

## 결과와 감수할 단점

### 장점

- 서비스 계정 전환이 다른 사람의 로컬 건강정보 열람으로 이어지지 않는다.
- IndexedDB, OPFS와 키의 수명이 같은 보관함 경계에 맞춰진다.
- 초대·계정 연결과 실제 건강정보 전달이 분리되어 기존 로컬 우선 원칙을 유지한다.
- 백업·복구·기기 이전의 대상이 명확해지고 보관함 단위 감사를 할 수 있다.

### 단점

- 첫 사용, 잠금 해제, 계정 전환과 레거시 데이터 이전 단계가 추가된다.
- 로컬 잠금 비밀을 잃었을 때 서버가 건강정보를 복구해 줄 수 없으므로 백업·복구 UX가 필수다.
- 여러 탭의 잠금 전파, 중단된 이전, 저장공간 부족과 OPFS 고아 파일 처리가 복잡해진다.
- 같은 사람의 기록을 여러 기기에서 쓰려면 자동 서버 조회가 아니라 명시적 암호화 이전 절차가 필요하다.

## 재검토 조건

웹 플랫폼의 패스키 PRF·보안 키 기능이 목표 브라우저에서 충분히 보편화되거나, 네이티브 앱의 OS 키체인을 함께 지원하거나, 명시적 가정 공용 보관함 요구가 확정되면 키 잠금·복구 수단과 공용 공간을 별도 ADR에서 비교한다. 건강정보 서버 저장 전환은 이 ADR을 조용히 수정하지 않고 데이터 경계 자체를 대체하는 새 ADR로만 결정한다.

## 한 문장 요약

> 공용 브라우저의 건강정보는 Origin 공용 DB가 아니라 계정과 별도로 잠금 해제하는 암호화 보관함에 격리하고, 계정 전환만으로 다른 보관함을 열 수 없게 한다.
