# ADR-010: 건강문서 인식 경로 — OCR 파이프라인과 멀티모달 직송

- 상태: 제안 — 팀 승인 대기
- 작성일: 2026-08-25
- 적용 대상: 검진결과지·처방전 이미지의 인식 방식, 실행 위치, 동기·비동기 경로, 평가 축
- 대체 대상: [24_ocr_implementation_alignment](../24_ocr_implementation_alignment.md) §2 정렬 원칙 2번, §3.2의 `app/services/ocr/engine.py` 폐기 판정과 `202 + job_id` 비동기 계약 폐기 판정
- 보완 대상: [ADR-008](0008-temporary-cloud-ocr-baseline.md) — 기각·허용 조항은 유지하고 기본 엔진의 자리를 새로 채운다
- 관련 결정: [ADR-009](0009-per-disease-models-and-server-inference-path.md), [ADR-001](0001-web-local-first-architecture.md), [ADR-002](0002-separate-server-api-and-local-domain-contract.md)
- 근거 문서: [16_ocr_cloud_baseline_local_replacement_challenge](../16_ocr_cloud_baseline_local_replacement_challenge.md), [24_ocr_implementation_alignment](../24_ocr_implementation_alignment.md), [18_core_feature_gap_and_mentoring_action_plan](../18_core_feature_gap_and_mentoring_action_plan.md) §4

## 배경

멘토가 물은 것은 "OCR을 따로 만들지, 멀티모달 모델에 이미지를 바로 보낼지"였고, 로컬 모델을 쓸 거라면 홈서버·보안·처리량·품질·비용을 같이 보라는 조건을 달았다.

이 질문도 세 축이 겹쳐 있다.

1. 무엇을 인식하는가 — 문서인가 영상인가
2. 어떻게 인식하는가 — OCR과 규칙을 조립하는가, 멀티모달에 던지고 JSON을 받는가
3. 어디서 실행하는가 — 브라우저, 우리 서버, 외부 API

### 지금 저장소에 실제로 있는 것 — 브랜치를 구분해서 읽어야 한다

**부품은 대부분 `feat/OCR_n_ai-worker` 에만 있다.** 모델링 작업 브랜치(`feat/ML_enhance`)와 `dev` 에는 없다. 이걸 뭉개면 "이미 동작한다"가 "우리 작업 브랜치에서 동작한다"로 오해된다.

| 자산 | 규모 | 위치 | 있는 브랜치 |
|---|---|---|---|
| RapidOCR 런타임 (PP-OCR ONNX) | — | `app/services/ocr/engine.py` | **`feat/OCR_n_ai-worker` 만** |
| 검진표 항목 사전 | 252줄 | `app/services/ocr/lexicon.py` | **`feat/OCR_n_ai-worker` 만** |
| 표 행 조립기 | 206줄 | `app/services/ocr/extractor.py` | **`feat/OCR_n_ai-worker` 만** |
| 문서 검증·라우터 | — | `app/services/documents.py`, 문서 라우터 | **`feat/OCR_n_ai-worker` 만** |
| Redis Streams 큐 | 174줄 + 소비자 | `app/core/jobs/*`, `ai_worker/consumer.py` | **`feat/OCR_n_ai-worker` 만.** 소비자 그룹, ack, `XAUTOCLAIM` 재배달, 재시도 상한, SIGTERM |
| 브라우저 영역 기반 OCR | 793줄 | `frontend/local-domain/ocr/*` | **`feat/OCR_n_ai-worker` 만** |

| **채점 데이터셋** | **0건** | — | **없다. 이게 없으면 어느 경로도 숫자로 비교 못 한다** |

정리하면 이렇다. **멘토가 말한 흐름의 부품은 존재하지만 우리 작업 브랜치에는 하나도 없고, 워커 컨테이너는 이름만 있다.** 그래서 이 ADR 의 §3 이 "이미 동작한다"고 적은 것은 이식 후를 전제한 말이다. 이식이 곧 작업량이고, 없는 것은 부품이 아니라 두 가지다 — **이식**과 **비교할 자료**.

### 이 결정의 전제가 바뀐 경위

24번 문서는 "서버에서 건강문서를 추론하지 않는다"를 정렬 원칙으로 삼아 서버 OCR 런타임과 비동기 큐 계약을 폐기 대상으로 판정했다. 그 판정의 근거는 ADR-001·ADR-002·11번 문서의 서버 추론 금지였다. ADR-009가 그 전제를 바꿨으므로 판정을 다시 한다. 결론을 뒤집는 것이고, 뒤집는 이유는 새 측정이 아니라 상위 전제의 변경이다.

## 결정

### 1. 이름을 가른다 — 이번 릴리스가 하는 것은 건강문서 이해다

정식 명칭을 **건강문서 OCR·구조화**로 쓴다. 검진결과지와 처방전의 인쇄된 글자를 읽어 검사명·값·단위·기준범위·날짜로 구조화하는 일이다.

X-ray·CT·초음파·피부 병변처럼 영상 자체에서 질환을 분류하는 일은 이번 릴리스 범위 밖이다. 데이터셋, 라벨, 평가 방법, 규제 위험, 사용자 출력이 전부 다르다. 화면·문서·발표에서 두 영역을 `의료 이미지 인식` 하나로 묶지 않는다. 묶으면 우리가 하지 않은 일을 했다고 말하게 된다.

### 2. OCR + 도메인 규칙 파이프라인을 기본으로 채택한다

멀티모달 직송을 기본 엔진으로 쓰지 않는다. 근거는 세 가지이고 첫 번째가 결정타다.

**근거 위치를 짚을 수 있어야 한다.** 우리 제품은 인식 결과를 자동 확정하지 않는다. 사용자가 검토하고 고쳐서 확정한 값만 기록이 된다(ADR-008). 그 검토 화면이 성립하려면 "이 숫자가 원본 이미지의 어디에서 나왔는지"를 알아야 한다. OCR은 bounding box를 준다. 멀티모달 직송은 JSON만 주고 좌표를 주지 않는다. 검사 항목이 30개인 결과지에서 하나가 틀렸을 때, 사용자가 그것을 찾을 방법이 사라진다.

**위험 오류를 규칙으로 막아야 한다.** `120 → 170`, `5.6 → 56`, `mg/dL → mmol/L`, `음성 → 양성`은 일반 글자 오류와 다른 등급의 사고다. 값·단위·기준범위가 서로 맞는지 검사하려면 구조화된 중간 표현이 있어야 한다. `lexicon.py`가 라틴 접두사와 단위와 참고치를 함께 보고 항목을 특정하는 방식이 그 중간 표현을 만든다. 직송은 그 단계를 건너뛰므로 검사할 대상 자체가 없다.

**팀이 보여줄 깊이가 남아야 한다.** 직송은 API 호출 한 줄이다. 후보에 등재해두면 왜 쓰지 않았는지가 근거 있는 결론이 되고, 등재하지 않으면 검토조차 하지 않은 것이 된다.

따라서 16번 문서 §4 후보표에 **B6 — 멀티모달 VLM 직송**을 행으로 추가하고, 같은 고정 평가 세트로 채점한다. 채택하지 않기로 한 것이 아니라 이번 릴리스의 기본이 아니라는 뜻이다.

### 3. 기본 실행 위치는 우리 서버 ai-worker다

```text
브라우저                nginx      FastAPI              Redis Streams    ai-worker
────────────────────────────────────────────────────────────────────────────────────
파일 선택 ─────────────────▶ 형식·크기·해상도 검증
                             인증·레이트리밋
                                    │
                                    ├─ 작업 등록 ─────────▶ 큐
                                    ◀─ 202 job_id                        │
                                                                          ├─ PP-OCR ONNX 인식
                             폴링 또는 SSE                                ├─ 표 행 조립
                                    ◀─ 결과 ◀──────────────────────────── ┘  항목 사전 매칭
사용자 검토·수정                                                              위험 오류 검사
확정값만 저장
```

이유는 셋이다.

- **외부 전송이 0이다.** Naver 경로보다 개인정보 경계가 오히려 깨끗하다. "로컬 모델"이라는 말의 실질을 브라우저가 아니라 우리가 운영하는 서버에서 확보한다.
- **인식기와 큐를 새로 쓰지 않는다.** RapidOCR이 PP-OCR ONNX이고 큐는 소비자 그룹·재배달·재시도 상한까지 만들어져 있다. 단 §배경 표대로 **둘 다 `feat/OCR_n_ai-worker` 에만 있다.** 그래서 첫 작업은 인식기 구현이 아니라 이식이고, `ai-worker` 컨테이너의 `echo 'hello world'` CMD를 실제 소비자로 바꾸는 일이 그 안에 들어간다.
- **처리량과 비용이 우리 통제 안에 있다.** 호출당 과금도 rate limit도 없다. 대신 상한이 `mem_limit: 4G` 컨테이너 하나라는 사실이 우리 몫으로 남는다. 이 상한을 측정해서 적는 것이 멘토가 말한 홈서버 조건에 대한 답이다.

이 결정이 24번 문서 §3.2의 `app/services/ocr/engine.py` 폐기 판정을 대체한다. `feat/OCR_n_ai-worker` 브랜치의 상태도 `이식 원본`에서 `부분 병합 대상`으로 바뀐다.

### 4. Naver CLOVA는 비교 기준선으로만 남는다

ADR-008을 그대로 유지한다. 합성·비식별 문서만 보내고, 사용자가 명시적으로 선택할 때만 실행하며, 제품의 기본 엔진이 아니다. 역할은 하나다 — 우리 엔진의 정확도가 상용 수준에서 얼마나 떨어지는지 재는 자.

키 발급 주체와 월 비용 한도 확정은 트랙 A 착수 선행조건이다. 저장소에 단가 수치가 한 건도 없다.

### 5. 브라우저 OCR은 보류한다

기각이 아니다. `frontend/local-domain/ocr/*` 793줄은 살리고 `frontend/src/shared/ocr/` 아래로 옮긴다(24번 문서 §3.3의 통합 경로는 유효하다). 오프라인 요구나 서버 전송을 거부하는 사용자 경로가 제품 요구가 될 때 다시 판단한다.

### 6. OCR은 비동기다. 24번 문서가 없애려던 `202 + job_id`를 유지한다

ADR-009 §7의 판정 규칙을 적용한 결과다. OCR은 p95가 초 단위이고 무거운 모델 로딩과 재시도가 있다. 요청 수명에 묶으면 타임아웃이 사용자 재업로드가 된다.

**여기에 정직하게 적을 충돌이 하나 있다.** 워커가 이미지를 읽어야 하므로 이미지 바이트가 Redis를 통과한다. ADR-008은 원본을 Redis에 짧은 TTL로 두는 안을 기각했다. 이 ADR은 그 기각을 이번 릴리스에 한해 다음 조건으로 뒤집는다.

- TTL 10분 이하, 작업 완료 즉시 명시적 삭제
- 키에 계정·프로필 식별자를 넣지 않는다. 무작위 job_id만 쓴다
- OCR payload 전용 Redis DB 인덱스를 분리하고 그 인덱스에 RDB·AOF 지속화를 켜지 않는다
- 요청·응답 본문과 인식 텍스트를 로그·APM payload에 남기지 않는다
- 이 네 조건을 자동 테스트로 증명한다. 증명이 없으면 경로를 켜지 않는다

TTL이 외부 전송을 없애지 않는다는 ADR-008의 논리는 여전히 맞다. 다만 여기서는 외부로 나가지 않고 우리 인프라 안에 머물며, 대안이 요청 수명 안의 동기 처리뿐이라 성립하지 않는다. 조건을 못 지키면 동기 중계로 되돌린다.

### 7. 평가 축에 멘토가 말한 다섯 개를 넣는다

16번 문서 §6에 두 축을 추가한다 — **외부 전송 여부**, **동시 처리량·rate limit·호출당 비용**. 그리고 세 경로를 같은 표에서 비교한다.

| 축 | 서버 ai-worker (채택) | Naver CLOVA (기준선) | VLM 직송 (후보 B6) |
|---|---|---|---|
| 홈서버 운영 | 컨테이너 가동률, 모델 다운로드, 재시작 복구가 우리 몫 | 없음 | 없음 |
| 보안 | 외부 전송 0. Redis payload TTL이 유일한 노출면 | 외부 사업자 전송. 합성·비식별만 | 외부 사업자 전송. 문서 전체가 나간다 |
| 처리량 | 4G 컨테이너 1대가 상한. 측정 대상 | 계약 rate limit | 계약 rate limit + 토큰 상한 |
| 품질 | 측정 대상 | 상용 상한 기준선 | 표 구조에 강할 가능성, 근거 좌표 없음 |
| 비용 | 서버 상시 비용. 호출당 0 | 호출당 과금 | 호출당 과금, 이미지 토큰이 비싸다 |

각 칸의 숫자는 이 ADR이 채우지 않는다. 채점 데이터셋으로 채우고 16번 문서 §14 양식에 기록한다.

### 8. 채점 데이터셋 구축이 모든 비교의 선행조건이다

지금 0건이다. 최소 규모와 정답 스키마는 16번 문서 §11을 따른다. Naver 출력으로 다른 엔진의 정답을 만들지 않는다. 고정 평가 세트의 정답은 최종 비교 전까지 수정하지 않는다.

## 검토한 대안

### 멀티모달 직송을 기본 엔진으로 채택

기각한다. 근거 좌표가 없어 사용자 검토·수정 화면이 성립하지 않고, 값·단위·기준범위 정합성 검사의 대상이 되는 중간 표현이 생기지 않는다. 건강문서에서 숫자 하나가 조용히 틀리는 것은 글자가 틀리는 것과 다른 등급의 사고다.

### 좌표를 포기하고 원본 이미지와 결과를 나란히 보여주기

보류한다. 사용자가 눈으로 대조하는 것은 가능하지만 항목이 30개일 때 어느 값이 틀렸는지 지목할 수 없다. 항목 수가 적은 문서 유형에 한정해 다시 검토할 여지는 있다.

### OCR 먼저 돌리고 저신뢰 항목만 VLM으로 재확인하는 하이브리드

**가장 유망한 후속안으로 보류한다.** 근거 좌표는 OCR이 이미 갖고 있고 VLM은 판독이 어려운 셀에만 호출하므로 비용도 통제된다. 이번 릴리스에 넣지 않는 이유는 하나다 — 저신뢰 판정 기준을 만들 채점 데이터셋이 아직 없다. 데이터셋이 서면 첫 번째로 검토한다.

### Naver CLOVA를 제품 기본 엔진으로 채택

기각한다. ADR-008의 기각 이유가 그대로 유효하다. 외부 전송이 예외가 아니라 기본 동작이 되고 공급자 장애·비용·약관·네트워크에 종속된다.

### 브라우저 전용 실행

보류한다. 데이터 경계로는 가장 깨끗하지만 저사양 기기 실패율과 최초 모델 다운로드 비용을 배포까지 3주 안에 측정할 수 없다. 자산은 살려둔다.

### 서버에서 동기 중계만 하고 큐를 쓰지 않기

기각한다. 초 단위 작업을 요청 수명에 묶으면 타임아웃이 사용자 재업로드로 나타나고 재시도를 서버가 못 맡는다. 다만 §6의 네 조건을 증명하지 못하면 이 안으로 되돌린다.

### X-ray·CT 등 의료 영상 분류를 이번 릴리스에 추가

기각한다. 공개 데이터셋으로 분류기를 만드는 것 자체는 가능하지만, 사용자에게 보여주는 순간 우리가 감당할 수 없는 출력이 된다. 어떤 영상인지, 어떤 문제를 푸는지, 틀렸을 때 무엇을 말할지가 하나도 정해져 있지 않다.

## 결과와 감수할 단점

- 인식 결과에 근거 좌표가 남아 검토·수정 화면과 위험 오류 검사가 둘 다 성립한다.
- `feat/OCR_n_ai-worker`의 서버 자산이 버려지지 않는다. 폐기 대상이던 인식기와 큐가 제품 경로가 된다.
- 멘토가 물은 다섯 축을 하나의 표에서 답할 수 있다. 다만 표의 숫자는 아직 없고, 채우는 일이 이 결정의 실제 작업량이다.
- Redis를 이미지 payload가 통과한다. ADR-008의 기각 하나를 조건부로 뒤집었고, 조건 네 개를 테스트로 증명하지 못하면 경로를 켜지 못한다.
- 홈서버 운영 부담이 우리에게 남는다. 4G 컨테이너 한 대가 동시 처리량의 상한이고, 그 수치를 모르면 시연에서 큐가 밀린다.
- 브라우저 OCR을 보류했으므로 오프라인 인식은 이번 릴리스에서 제공하지 않는다.
- VLM을 후보로만 두었으므로 "최신 멀티모달을 썼다"는 어필은 하지 않는다. 대신 비교해서 고른 근거를 남긴다.

## 재검토 조건

- 채점 데이터셋 첫 고정 결과가 나온다. 세 경로의 품질 격차가 예상과 다르면 2번을 다시 판단한다.
- 서버 OCR의 동시 처리량이 시연 부하를 못 받친다. 그때 워커 수평 확장, GPU, 또는 클라우드 경로 승격을 판단한다.
- 실제 개인정보 문서를 다루는 것이 제품 요구가 된다. 그때 저장·보관·삭제 결정을 담은 별도 ADR이 선행한다.
- §6의 네 조건 중 하나라도 테스트로 증명하지 못한다. 동기 중계로 되돌린다.
- 저신뢰 판정 기준이 서면 하이브리드안을 검토한다.
- 실제 의료 영상을 다루는 별도 피처가 제품 요구가 된다. 그때는 이 ADR을 확장하지 않고 새 ADR을 쓴다.

## 한 문장 요약

> 건강문서 인식은 근거 좌표를 남기는 OCR + 도메인 규칙 파이프라인으로 가고, 우리 서버 ai-worker에서 Redis 큐를 거쳐 비동기로 실행하며, Naver CLOVA는 비교 기준선으로 멀티모달 직송은 후보 B6으로 등재만 하고 이번 릴리스의 기본으로 쓰지 않는다.
