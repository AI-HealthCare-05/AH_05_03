# ADR-004: 가족 초대 상태와 Redis 책임 경계

- 상태: 제안
- 결정일: 2026-08-19
- 적용 대상: 가정 구성원 초대·수락·거절·취소
- 관련 결정: [ADR-001](0001-web-local-first-architecture.md), [ADR-002](0002-separate-server-api-and-local-domain-contract.md)

## 배경

가족 초대에는 감사 가능한 최종 상태와 짧은 수명의 원문 토큰·남용 방지가 함께 필요하다. 건강정보는 서버에 저장하지 않으면서도 중복 초대, 동시 수락, 취소 후 수락과 토큰 재사용을 일관되게 막아야 한다.

## 결정

- PostgreSQL을 가정 멤버십과 초대 상태의 유일한 정본으로 사용한다.
- 상태 전이는 PostgreSQL 행 잠금, FK, CHECK와 부분 유일 인덱스로 직렬화하고 검증한다.
- DB에는 초대 토큰의 SHA-256 해시만 저장한다.
- Redis는 원문 초대 토큰 allowlist, 소비 토큰 마커, 계정·이메일·초대별 속도 제한과 메일 워커 인계에 사용한다.
- 원문 토큰은 짧은 TTL 키에만 두고 Redis Stream에는 초대 ID만 기록한다.
- 초대 생성과 토큰 소비에서 Redis 장애가 나면 실패를 허용하지 않는다. DB 종단 상태가 이미 확정된 뒤의 임시 키 정리 실패만 TTL 정리에 맡긴다.
- Redis 분산 잠금으로 DB 상태 전이를 조정하지 않는다.

## 검토한 대안

### Redis를 초대 상태의 정본으로 사용

기각한다. 재시작·eviction·TTL 설정 실수로 최종 상태와 감사 이력이 사라질 수 있고, FK·부분 유일성·다중 행 상태 전이를 DB보다 약하게 보장한다.

### PostgreSQL만 사용

보류한다. 최종 상태에는 적합하지만 원문 토큰을 메일 전송 시점까지 보관하려면 별도 암호화 키 관리와 outbox 설계가 필요하다. 현재 단계에서는 짧은 TTL의 재발급 가능한 초대에 Redis가 단순하다.

### 서명된 무상태 초대 토큰만 사용

기각한다. DB 조회는 줄지만 취소, 1회성 소비, 재사용 탐지와 대상별 속도 제한을 다시 별도 상태로 구현해야 한다.

### Redis 분산 잠금으로 수락 경쟁 제어

기각한다. 최종 변경은 PostgreSQL에서 일어나므로 DB 행 잠금과 유일 제약이 더 가까운 일관성 경계다. Redis 잠금을 추가하면 잠금 만료와 DB 커밋 사이의 이중 장애 모드만 늘어난다.

## 결과와 감수할 단점

- Redis를 충분히 활용하면서도 영속 상태의 정확성을 Redis 가용성에 맡기지 않는다.
- 토큰 원문은 API 응답·DB·로그에 남지 않으며 소비와 재사용을 구분할 수 있다.
- DB 커밋 실패 시 소비 토큰을 보상 복구하지만, Redis까지 동시에 장애가 나면 안전한 방향으로 재사용 불가가 된다.
- Redis가 전송 TTL 동안 데이터를 잃으면 기존 초대 상태는 남아도 메일을 재전송할 수 없다. 사용자는 초대를 취소하고 새로 발급해야 한다.

## 재검토 조건

메일 전달 보장이나 장기 재전송 SLA가 필요해지면 PostgreSQL transactional outbox와 애플리케이션 수준 암호화를 새 ADR에서 비교한다. 다중 리전 DB, 외부 메시지 브로커 또는 초대 대량 발송이 도입될 때도 속도 제한과 전달 방식을 다시 평가한다.

## 한 문장 요약

> 초대의 진실은 PostgreSQL에, 짧은 수명의 보안·남용 방지·전송 신호는 Redis에 둔다.
