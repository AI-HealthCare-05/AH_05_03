## 1. 검토 전제

Manyfast는 이어봄 서비스에 탑재되는 기술이 아니라 PRD, 기능명세서, 유저플로우 및 와이어프레임을 정리하는 기획 도구다.

이어봄은 Manyfast를 이용해 기획 산출물을 재정비하는 과정에서 다음과 같은 로컬 우선(Local-first) 원칙을 도입했다.

- 중요한 건강정보는 사용자의 기기에 저장하고 처리한다.
- 건강정보를 기본적으로 외부 서버에 전송하지 않는다.
- 기기 이전과 복구에는 사용자가 직접 관리하는 암호화 백업 파일을 사용한다.
- 복수 기기 사용 시 동일한 로컬 네트워크 내에서 암호화 동기화를 제공한다.
- 고객 건강정보는 AI 모델 학습에 사용하지 않는다.

본 리뷰는 이 원칙이 기능명세서, 유저플로우 및 와이어프레임에 일관되고 구현 가능한 형태로 반영되었는지를 기준으로 작성했다.

## 2. 종합 평가

| 산출물 | 점수 | 판단 |
|---|---:|---|
| 기능명세서 | 8/10 | 로컬 우선 원칙과 예외 처리가 상세하다. |
| 유저플로우 | 7/10 | 주요 기능 경로는 충실하지만 복잡하고 일부 예외 경로가 빠져 있다. |
| 데스크톱 와이어프레임 | 8/10 | 명세 반영도가 높고 핵심 안내 및 확인 화면이 잘 설계되어 있다. |
| 산출물 간 일관성 | 6/10 | 동기화, 계정, OCR 및 공유 정책에서 충돌이 있다. |
| 개발 착수 준비도 | 6.5/10 | 핵심 정책 결정과 MVP 범위 축소가 선행되어야 한다. |

전체적으로 로컬 우선 콘셉트의 도입은 성공적이다. 단순히 개인정보 안내 문구만 추가한 것이 아니라 백업, 복구, 동기화, 기록 수정 및 삭제 흐름까지 설계가 확장되었다.

다만 일부 기능은 산출물마다 서로 다른 아키텍처를 전제한다. 개발을 시작하기 전에 데이터가 저장되는 위치와 네트워크 경계를 하나의 정책으로 확정해야 한다.

## 3. 잘된 부분

### 3.1 기능명세서

- 제품 목표, 해결 방안 및 차별점에 로컬 저장 원칙이 명확히 반영되어 있다.
- 외부 서버 미전송과 AI 모델 학습 미사용 원칙이 명시되어 있다.
- 브라우저 데이터 삭제, 기기 분실, 저장공간 부족 등 로컬 저장의 위험을 함께 다룬다.
- 암호화 백업 내보내기와 가져오기를 독립적인 복구 수단으로 정의한다.
- 데이터 충돌, 잘못된 비밀번호, 손상 가능성 등 주요 예외 상황을 고려한다.
- OCR, LLM 및 예측 기능이 의료 진단이나 처방을 제공하지 않는다는 한계를 명시한다.
- 건강기록 수정 및 삭제 작업을 로컬 변경 이력과 연결한다.

### 3.2 유저플로우

다음 주요 정상 흐름이 연결되어 있다.

- 최초 실행 → 개인정보·로컬 보관 안내 → 가정 생성
- 구성원 선택 → 건강 대시보드 → 이력·차트·예측·유전정보
- 직접 입력·OCR·대화형 입력 → 건강기록 저장
- 건강기록 상세 → 수정·삭제
- 데이터 관리 → 백업·가져오기·변경 이력·복구·동기화

기능이 단순 화면 목록으로만 존재하지 않고 사용자의 행동 순서로 연결된 점이 좋다.

### 3.3 와이어프레임

- 최초 진입 과정에 개인정보 및 로컬 보관 안내 화면이 존재한다.
- 안내 화면에서 로컬 저장, 외부 서버 미전송, 데이터 손실 위험, 암호화 백업 및 변경 이력을 함께 설명한다.
- 백업 파일의 포함 범위와 비밀번호 분실 위험을 안내한다.
- 가져오기 충돌 확인, 변경 이력 조회 및 시점 복구 화면이 별도로 설계되어 있다.
- OCR 결과를 저장 전에 검토하는 단계가 존재한다.
- LLM 통증 입력 화면에 의료적 한계와 외부 미전송 안내가 표시되어 있다.
- 건강 변화 예측 화면에 기기 저장 기록 기반이라는 설명과 의료적 한계가 표시되어 있다.

## 4. 우선 해결해야 할 불일치

### 4.1 동기화 아키텍처 — 최우선

기능명세서와 와이어프레임이 서로 다른 구조를 설명한다.

- 기능명세서: 같은 Wi-Fi 네트워크에서 기기끼리 직접 암호화 동기화하며 클라우드를 사용하지 않는다.
- 와이어프레임: 서버가 복호화할 수 없는 암호화 데이터와 최소 메타데이터를 보관한다.

이는 문구의 차이가 아니라 P2P 로컬 동기화와 클라우드 암호화 동기화라는 서로 다른 아키텍처다.

로컬 우선 원칙을 유지한다면 다음처럼 통일하는 것이 적절하다.

> 승인한 동일 네트워크의 기기끼리 직접 암호화 데이터를 전송하며, 중계 서버에 건강 데이터나 암호문을 저장하지 않습니다.

개발 전 다음 항목도 확정해야 한다.

- 기기 발견 방식
- 연결 승인 및 인증 방식
- 동시 수정 충돌 규칙
- 연결 중단 후 재개 방식
- 신뢰하지 않는 Wi-Fi에 대한 경고
- 기기 해제 시 데이터 처리

### 4.2 서버 계정의 범위

산출물 내에서 다음 정의가 충돌한다.

- 로컬 데이터 보관 기능에서는 서버 계정을 제공하지 않는다고 정의한다.
- 가족 계정 기능에서는 초대, 계정 연결, 구독 및 라이선스 관리를 정의한다.
- 와이어프레임에는 계정 해지 화면이 존재한다.

권장 구조는 다음과 같다.

- 서비스 계정은 구독과 라이선스 관리에만 사용한다.
- 건강정보는 계정 데이터베이스와 분리하고 기기에만 저장한다.
- 가족 구성원은 우선 서버 계정이 아닌 로컬 프로필로 관리한다.
- 온라인 초대, 공동 관리자 및 세부 권한 기능은 후속 단계로 미룬다.

### 4.3 기간 제한 링크 및 QR 공유

기능명세서에는 높은 중요도로 정의되어 있지만 유저플로우와 와이어프레임에서 확인되지 않는다. 인터넷에서 열리는 임시 링크는 외부 서버에 데이터를 두지 않는다는 원칙과도 충돌한다.

MVP에서는 다음 방식으로 대체하는 것이 적절하다.

- 선택한 기록을 암호화 파일로 내보낸다.
- 동일 Wi-Fi에서 일회성 QR을 이용해 기기를 직접 연결한다.
- 파일 비밀번호는 별도 채널로 전달한다.

인터넷 임시 링크가 반드시 필요하다면 외부 전송 예외 기능으로 분류하고 다음 내용을 명시해야 한다.

- 서버가 보관하는 데이터
- 암호화 및 키 관리 주체
- 보관 시간
- 열람 횟수
- 철회 방식
- 서버 운영자의 복호화 가능 여부

### 4.4 OCR 결과 수정 정책

- 기능명세서: OCR로 인식한 의료기관명과 문서 일련번호를 사용자가 수정할 수 없다.
- 와이어프레임: OCR 결과를 검토하고 수정할 수 있다.

OCR 오인식 가능성을 고려하면 와이어프레임의 방향이 더 현실적이다.

권장 정책:

> 사용자는 OCR 결과를 수정할 수 있으며 원본 인식값, 사용자 수정값, 인식 신뢰도 및 수정 시각을 로컬 변경 이력에 보관한다.

저신뢰도 결과는 저장을 차단하기보다 직접 입력이나 수정으로 전환할 수 있게 하는 것이 좋다.

### 4.5 백업 파일에 포함되는 원본 서류

기능명세 일부에서는 원본 서류의 참조 정보만 백업한다고 표현하지만 와이어프레임은 원본 파일까지 포함한다고 설명한다.

참조 정보만 백업하면 다른 기기에서 원본 서류를 복구할 수 없다. 암호화 백업에는 다음 항목이 실제로 포함되어야 한다.

- 구성원 프로필
- 건강기록
- 원본 건강 서류 파일
- OCR 인식값 및 수정값
- 변경 이력
- 데이터 스키마 버전
- 백업 생성 시각과 앱 버전

### 4.6 건강 변화 예측 범위

첫 버전에서 모든 건강 기록 유형에 예측을 제공한다는 범위는 지나치게 넓다. 데이터 형태와 기록 수가 서로 다른 항목을 같은 방식으로 예측하면 신뢰도가 떨어진다.

권장 범위:

- 혈압, 혈당, 체중처럼 충분한 수치 시계열이 있는 항목만 우선 지원한다.
- 비수치형 기록은 예측 대신 최근 기록과 단순 추세만 표시한다.
- 최소 기록 개수와 최소 관찰 기간을 정의한다.
- 사용한 모델, 모델 버전, 산출 시각 및 데이터 범위를 표시한다.
- 데이터가 부족하면 예측값을 만들지 않고 기록 부족 상태를 표시한다.
- 결과의 근거와 신뢰도 또는 불확실성을 제공한다.

### 4.7 로컬 LLM의 구현 조건

와이어프레임에는 대화 내용이 외부 서버로 전송되지 않는다고 표시되어 있어 로컬 우선 콘셉트와 일치한다. 하지만 기능명세에는 실제 구현 조건이 부족하다.

다음 사항을 확정해야 한다.

- 사용할 온디바이스 모델과 라이선스
- 최초 모델 다운로드 여부와 용량
- 오프라인 동작 여부
- 지원 브라우저와 최소 메모리
- 모델 실행이 불가능할 때 직접 입력으로 전환하는 방법
- 저장 전 대화 초안의 보관 위치와 폐기 시점
- 사용자 입력이 모델 학습 또는 운영 로그에 사용되지 않는다는 범위

## 5. 유저플로우 보완 사항

현재 유저플로우에는 주요 정상 경로가 잘 반영되어 있지만 다음 예외 및 복구 경로를 추가해야 한다.

### 5.1 최초 설정

- 새 가정 생성
- 기존 백업 파일에서 복구
- 개인정보 안내에 동의하지 않을 때 종료 또는 제한 사용
- 브라우저 저장소를 사용할 수 없을 때 안내

### 5.2 건강기록과 OCR

- 카메라 권한 거부
- 지원하지 않는 파일 형식
- 저장공간 부족
- OCR 저신뢰도
- OCR 실패 후 직접 입력 전환
- 다중 페이지 일부 처리 실패

### 5.3 백업과 복구

- 잘못된 비밀번호
- 손상되거나 지원하지 않는 백업 파일
- 이전 앱 버전에서 만든 백업의 마이그레이션
- 가져오기 전 현재 데이터의 안전 복구 지점 생성
- 가져오기 중단과 롤백
- 중복 및 충돌 항목별 처리

### 5.4 기기 간 동기화

- 상대 기기 승인 또는 거절
- 다른 Wi-Fi에 연결된 상태
- 연결 중단 후 재개
- 동시 수정 충돌
- 마지막 동기화 시각 확인
- 연결 기기 해제

### 5.5 로컬 AI와 예측

- 로컬 모델 미설치
- 기기 성능 부족
- 모델 다운로드 실패
- 응답 생성 실패 후 직접 입력 전환
- 예측에 필요한 데이터 부족
- 모델 업데이트 전후 결과 차이 안내

## 6. 유저플로우 구조 개선

현재 유저플로우는 기능 범위가 넓어지면서 선이 길고 서로 교차한다. 하나의 대형 흐름도보다는 다음 네 개로 분리하는 것이 개발과 QA에 유리하다.

1. 최초 설정 및 가정 관리
2. 건강기록 등록 및 조회
3. 백업, 복구 및 기기 동기화
4. 설정, 지원 및 계정 관리

각 흐름에는 정상 경로와 예외 경로를 구분하고, 모든 종료점에 사용자가 돌아갈 화면을 표시하는 것이 좋다.

## 7. 와이어프레임 보완 사항

### 7.1 공통 상태 표현

다음 상태를 공통 컴포넌트나 패턴으로 정의할 필요가 있다.

- 이 기기에 저장됨
- 처리 중
- 저장 완료
- 저장 실패
- 저장공간 부족
- 오프라인 상태
- 마지막 백업 시각
- 마지막 동기화 시각
- 동기화 충돌
- 데이터 부족
- 로컬 AI 사용 불가

### 7.2 로컬 저장 안내의 계층화

모든 화면에 긴 개인정보 문구를 반복할 필요는 없다.

- 최초 안내 화면에서는 전체 정책을 자세히 설명한다.
- 입력 및 OCR 화면에서는 `기기에서 처리 · 외부 전송 없음`처럼 짧게 표시한다.
- 백업과 동기화처럼 위험도가 높은 작업에서는 데이터 범위와 영향을 다시 자세히 안내한다.

### 7.3 파괴적 작업

삭제와 시점 복구 화면에는 다음 정보가 필요하다.

- 대상 구성원과 기록
- 삭제 또는 복구되는 항목 수
- 원본 파일에 미치는 영향
- 되돌릴 수 있는지 여부
- 작업 직전 자동 복구 지점 생성 여부

### 7.4 접근성과 반응형 설계

- 주요 버튼과 입력 요소의 포커스 상태를 정의한다.
- 오류 메시지를 색상만으로 구분하지 않는다.
- 키보드만으로 주요 작업이 가능해야 한다.
- 표와 차트에는 텍스트 요약을 제공한다.
- 데스크톱의 넓은 여백과 긴 가로 동선을 모바일에서 어떻게 재배치할지 별도 규칙이 필요하다.

## 8. 권장 MVP 범위

현재 명세는 상·하위 기능이 넓고 대부분 작성 중 상태다. 초기 구현에서는 로컬 우선의 핵심 가치를 검증할 수 있는 범위에 집중하는 것이 안전하다.

### 8.1 1차 MVP 포함

- 로컬 가정 생성
- 가족 구성원 프로필 관리
- 건강기록 등록, 조회, 수정 및 삭제
- 시간순 건강 이력
- 수치형 지표 변화 차트
- 원본 건강 서류의 로컬 보관과 열람
- 암호화 백업 파일 내보내기
- 암호화 백업 파일 가져오기와 기본 충돌 처리
- 개인정보 및 데이터 손실 위험 안내

### 8.2 후속 단계 권장

- 동일 Wi-Fi 기기 간 동기화
- 로컬 LLM 대화형 입력
- 건강 변화 예측
- 가족 유전정보 참고
- 로컬 시점 복구
- 외부 건강기록 공유
- 가족 계정 초대와 세부 접근 권한
- 의료 데이터 자동 연동

## 9. 개발 착수 전 결정 목록

다음 항목이 합의되면 산출물 간 불일치를 크게 줄일 수 있다.

- [ ] 동기화는 동일 Wi-Fi P2P 방식인가, 서버 암호화 동기화 방식인가?
- [ ] 서버 계정은 존재하는가? 존재한다면 어떤 정보만 저장하는가?
- [ ] 인터넷 임시 링크 공유를 MVP에 포함하는가?
- [ ] OCR 결과를 사용자가 수정할 수 있는가?
- [ ] 백업에 원본 서류 파일 자체를 포함하는가?
- [ ] 로컬 LLM의 모델, 지원 환경 및 실패 대체 경로는 무엇인가?
- [ ] 예측을 제공할 건강 지표와 최소 데이터 조건은 무엇인가?
- [ ] 사용 지표는 기기에만 보관하는가, 익명 집계를 전송하는가?
- [ ] 브라우저 데이터 삭제에 대비한 백업 유도 정책은 무엇인가?
- [ ] 데이터 스키마 변경 시 이전 백업을 어떻게 마이그레이션하는가?

## 10. 결론

Manyfast를 활용해 기획 산출물을 재정비하면서 로컬 우선 콘셉트를 반영한 작업은 전반적으로 성공적이다. 특히 개인정보 안내에 그치지 않고 백업, 복구, 동기화, OCR, AI 입력, 수정 및 삭제까지 데이터 통제 관점을 확장한 점이 좋다.

현재 가장 중요한 작업은 화면을 더 추가하는 것이 아니다. 다음 다섯 가지 정책을 확정하고 기능명세서, 유저플로우 및 와이어프레임의 표현을 동일하게 맞추는 것이 우선이다.

1. 동기화 방식
2. 서버 계정의 범위
3. 외부 공유 방식
4. OCR 결과 수정 정책
5. 백업 파일의 실제 포함 범위

이 정책이 확정된 후 MVP 범위를 축소하면 개발 착수와 테스트가 가능한 수준으로 산출물을 정리할 수 있다.
